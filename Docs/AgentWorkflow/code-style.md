# Стиль и организация кода

Перед созданием или изменением кода прочитай относящийся к компоненту раздел.
Пиши новый код сразу в принятом стиле; не рассчитывай на будущий format-on-save.
Руководство объединяет правила исходного CLAUDE и уточнения владельца,
с приоритетом действующих конфигураций и решений. Архив не нужен для
повседневной работы.

## Область действия и источники

- Проектный C++ — **C++23**, окончания строк **CRLF**. Layout определяют
  [TweakerPlugin/.clang-format](../../TweakerPlugin/.clang-format) и
  [ASBridge/.clang-format](../../ASBridge/.clang-format), naming — соответствующие
  [.clang-tidy плагина](../../TweakerPlugin/.clang-tidy) и
  [.clang-tidy моста](../../ASBridge/.clang-tidy). На момент восстановления
  конфигурации этих двух компонентов совпадают.
- Исторический `Standard: c++20` — параметр разбора кода форматтером, а не
  стандарт компиляции. Комментарии про чужую библиотеку в `.clang-tidy` также
  не определяют архитектуру или namespace проекта. Конфигурации здесь не меняются.
- Описанные ниже `tw::*`, устройство PCH и паттерны игровых хуков относятся
  к **TweakerPlugin**. ASBridge сохраняет собственные namespace `as::*` и
  организацию заголовков. Совпадение style configs не требует добавить ему PCH.
- В новом проектном native-коде используй `.hxx` для заголовков и `.cxx` для
  translation units. Это не поручение переименовать существующий `main.cpp`
  InjectHelper или файлы внешних зависимостей.
- Правила C++ snake_case/скобок не распространяются на C#, AXAML, Lua или
  vendored-код. **ImGui, Detours, SDK и другие vendored-библиотеки не менять**
  ради соответствия нашему стилю.

При несовпадении примера с конфигурацией layout/naming руководствуйся
конфигурацией; противоречие отдельного проектного требования зафиксируй и обсуди.
Не форматируй всё дерево установленной новой версией ради локальной правки.

## Translation unit как модуль состояния

В проектном C++ **translation unit — самостоятельная первичная единица
организации кода**. Если модуль независим и обслуживает одно состояние,
используй пару `.hxx`/`.cxx` с функциями в namespace. Это модуль с единственным
состоянием, а не повод создавать класс Singleton, `instance()` или класс
со статическими методами.

Заголовок содержит только публичный интерфейс модуля. Его приватные данные,
вспомогательные типы и функции объявляются и используются только в `.cxx`,
в anonymous namespace. Не раскрывай их через заголовок, `extern` или
публичный `detail`-namespace ради удобства реализации.

**Класс вводи только там, где он необходим:** когда связанные данные,
операции и инварианты состояния действительно требуют совместной инкапсуляции.
Не оборачивай независимый модуль в класс только ради группировки функций
или хранения единственного состояния. Необходимость класса должна следовать
из модели состояния, а не из предпочтения объектной оболочки.

Пример единственного состояния модуля:

```cpp
// counter.hxx
#pragma once

namespace tw::example::counter
{
void reset();
int increment();
} // namespace tw::example::counter
```

```cpp
// counter.cxx
#include "pch.hxx"

#include "example/counter.hxx"

namespace
{
int g_count = 0;
} // namespace

namespace tw::example::counter
{
void reset()
{
    g_count = 0;
}

int increment()
{
    ++g_count;

    return g_count;
}
} // namespace tw::example::counter
```

## Классы и скрытые детали реализации

Если класс необходим, в его заголовке оставляй публичный API, поля данных
и объявления приватных методов, **непосредственно работающих с полями**.
Вспомогательная функция, которой не нужен доступ к полям, не должна становиться
приватным методом класса ради группировки.

**Приватные статические функции и поля запрещены**, включая приватные
`static constexpr` поля. Публичные статические функции также оформляются
свободными функциями соответствующего namespace.

| Требуемая роль | Как оформлять |
|---|---|
| Публичная операция без состояния экземпляра | Свободная функция в namespace; объявление — в публичном `.hxx` |
| Приватный helper без доступа к полям экземпляра | Свободная функция в anonymous namespace соответствующего `.cxx` |
| Приватное состояние или константа модуля | Данные в anonymous namespace `.cxx`, без объявления в заголовке |
| Приватная операция над полями экземпляра | Нестатический метод класса; объявление в `.hxx`, реализация в `.cxx` |

Не выставляй приватные статические детали наружу и не переноси их в другой
общий заголовок. Потребителям не нужно знать о них: лишние объявления мешают
читать API и создают зависимости сборки. Изменение такой детали реализации
не должно требовать перестроения всех потребителей из-за изменения заголовка.

## Читаемость и сокращения

Во всём новом проектном коде **разделяй логические блоки пустой строкой**:
проверки, подготовку данных, изменение состояния, передачу результата.
Не пиши функцию сплошным полотном. Разделение определяется смыслом, а не
механическим добавлением строки после каждого выражения; лимит одной подряд
пустой строки сохраняется. Форматтер не выбирает смысловые границы за автора.

Имена должны объяснять назначение. Сокращения допустимы только общеупотребительные,
разумные и однозначные в контексте. **Самодельные аббревиатуры, акронимы
и однобуквенные имена для проектных сущностей не использовать.** Допустимы
обычные локальные обозначения: `i` у счётчика цикла, `e` у исключения.
Эти исключения не оправдывают такие имена у полей, модулей или публичного API.

Чужой API сохраняет собственный стиль: `HWND`, `LPCWSTR` и другие имена WinAPI
используются как есть. Это не образец для изобретения собственных аббревиатур.

## Именование C++

Источник — `readability-identifier-naming` в `.clang-tidy`.
Имена библиотечных и системных типов/функций сохраняются:
`IDirect3DDevice9`, `HMODULE`, `HRESULT`, `DetourAttach`.
`.clang-format` задаёт layout, а не naming.

| Сущность / clang-tidy key | Case | Префикс | Пример |
|---|---|---|---|
| Namespace | `lower_case` | — | `tw::framework::detour` |
| Class / Struct | `lower_case` | — | `binding`, `resource` |
| Function / Method | `lower_case` | — | `attach`, `draw_frame` |
| Variable / Parameter | `lower_case` | — | `device`, `module_handle` |
| TypeAlias | `lower_case` | — | `end_scene_fn`, `ui_plugin_draw_fn` |
| Enum / EnumConstant | `lower_case` | — | `resource_type::texture` |
| MemberPrivate | `lower_case` | `m_` | `m_device` |
| MemberProtected | `lower_case` | `m_` | `m_engine` |
| MemberPublic | `lower_case` | нет | `target`, `replacement` |
| TemplateParameter | `CamelCase` | — | `T`, `TValue`, `TResult` |
| TemplateTemplateParameter | `CamelCase` | — | `TContainer` |

Дополнительные соглашения плагина, не задаваемые naming-check:

| Сущность | Соглашение | Пример |
|---|---|---|
| Необходимое file-local/global состояние | `g_` + snake_case | `g_bound_device`, `g_ui_draw` |
| Hook | `hk_*` или `*_hook` | `hk_end_scene` |
| Указатель на оригинал | `o_*` или `true_*` | `o_reset` |
| Тип функции-оригинала | `*_fn` | `end_scene_fn` |

PascalCase/camelCase не использовать для проектных native-имён, кроме
оговорённых template-параметров. Глобальное состояние вводи только там,
где оно необходимо; наличие префикса само по себе его не оправдывает.

## Layout C++

### Отступы и строки

- Отступ — **4 пробела**, табы запрещены; continuation indent — также 4.
- Ширина строки — **140**; максимум одна подряд пустая строка.
- Namespace не добавляет отступ содержимому. Компактное объединение отдельных
  namespace-блоков не делать; закрывающие комментарии писать полностью:
  `} // namespace tw::framework::d3d9`.
- Метки доступа `public:`/`protected:`/`private:` имеют смещение −4 относительно
  членов. `case` и блоки case — с отступом. У `#`-директив нет дополнительного
  отступа. `#include` и `using` сортируются по конфигурации.

### Скобки и короткие тела

- У **функций и namespace** открывающая `{` — на новой строке, включая пустые тела.
- У **class/struct/enum/union, if/for/while/switch** и лямбд `{` — на той же строке.
- `else` и `catch` начинаются с новой строки после закрывающей `}`.
- Короткие функции, блоки, if, циклы, лямбды и case не сжимать в одну строку.
  Короткие enum допускаются конфигурацией.
- Тела `if`/`for`/`while` и подобных конструкций **всегда заключать в фигурные
  скобки**, даже для одного выражения. Это отдельное проектное требование:
  форматтер сам не гарантирует добавление отсутствующих скобок. `case` может
  обходиться без отдельного блока для однострочного выражения.

```cpp
void draw_frame(IDirect3DDevice9* device)
{
    if(device == nullptr) {
        return;
    }
    else {
        render(device);
    }
}

namespace tw::ui
{
} // namespace tw::ui
```

У класса в следующем примере `{` стоит на той же строке, согласно
`BraceWrapping.AfterClass: false`. Старый пример CLAUDE с переносом был ошибочен.
Пример показывает только layout объявления, а не основание выбирать класс
вместо самостоятельного модуля translation unit.

```cpp
template<typename TValue>
class resource {
public:
    TValue* data;

private:
    int m_refcount;
};
```

### Пробелы и указатели

- `PointerAlignment: Left`: `int* p`, `const T& ref`, `const int* const p`.
  Перед квалификатором указателя — пробел.
- Нет пробела перед `(` у `if`/`for`/`while`/`switch` и вызовов; нет внутренних
  пробелов в `()`/`[]`/`<>`, пробела после C-cast, `!` и слова `template`.
- У присваивания/`+=` и подобных операторов — обычные разделяющие пробелы.
  Перед `:` у range-for, наследования и ctor-initializer — пробел; перед `:`
  у `case` пробела нет.
- Перед `{` у braced-init есть пробел; `Cpp11BracedListStyle: false` в исходной
  конфигурации задаёт оформление блока, а не компактный C++11 list-style.

```cpp
bool ok = attach({
    { &o_reset, reinterpret_cast<void*>(hk_reset) },
    { &o_end_scene, reinterpret_cast<void*>(hk_end_scene) },
});

if(!ok || device == nullptr) {
    return false;
}
```

### Переносы

- Не bin-pack'ать аргументы и параметры: либо вся сигнатура/вызов помещается
  в строку до 140, либо каждый аргумент/параметр на своей строке.
- После открывающей `(` не выравнивать продолжение в колонку: обычный отступ 4.
- Неassignment бинарные операторы и тернарные `?`/`:` переносятся **перед**
  оператором. Присваивания не включать в это правило.
- После `template<...>` у декларации всегда перенос строки.
- Список наследования и ctor-initializer начинается с переноса перед `:`.

Форматирование в IDE плагина настроено через clangd и format-on-save в
`TweakerPlugin/.vscode/settings.json`, но соблюдение стиля не должно зависеть
от того, был ли открыт файл в IDE.

## Организация TweakerPlugin

### API, реализации и namespace

Корневой namespace — `tw`, вложенные соответствуют слоям:
`tw::plugin`, `tw::framework`, `tw::engine`, `tw::ui` и профильным модулям.
**Публичный API объявляй в заголовках; детали реализации** — helpers, hooks,
указатели оригиналов и file-local state — в anonymous namespace файла `.cxx`.
Этот namespace объявляется **снаружи и выше** именованного `tw::*`, сразу
после блока include; не вкладывай anonymous namespace внутрь `tw::*`.

```cpp
#include "pch.hxx"

#include "framework/foo.hxx"

namespace
{
// File-local helpers, hooks and state.
} // namespace

namespace tw::framework
{
// Public API definitions.
} // namespace tw::framework
```

Назначение слоёв и направление зависимостей — в
[architecture.md](architecture.md). В частности, framework подключает UI
callback-ом (`attach_ui_plugin`), без жёсткой зависимости framework → ui.

### PCH, include и forward declarations

- Используется `TweakerPlugin/src/pch.hxx`. Прежде чем добавлять системный,
  SDK, STL или библиотечный header, проверь PCH. Если его там нет — добавь туда,
  а не непосредственно в проектный `.hxx`/`.cxx`.
- В `.cxx` первым идёт `#include "pch.hxx"`, затем собственный заголовок,
  затем остальные проектные include, сгруппированные по корневому пути.
  Между группами — пустая строка, внутри — сортировка clang-format.
- Не forward-declare системные/библиотечные типы (`HMODULE`, `HWND`,
  `IDirect3DDevice9`): они уже приходят из PCH. Forward declaration допустима
  для собственных неполных типов в заголовках.
- Порядок Quest3D SDK include в PCH фиксирован. Блок `clang-format off/on`
  вокруг него не трогать.
- Include-пути считаются от `src`: `"framework/foo.hxx"`, а не `../...`;
  это соответствует `target_include_directories(TweakerPlugin PRIVATE src)`.

```cpp
#include "pch.hxx"

#include "framework/foo.hxx"

#include "plugin/bar.hxx"

#include "ui/baz.hxx"
```

Новый `.cxx` добавляй в `CMakeLists.txt` соответствующего подкаталога `src`.
Плагин только x86; проектный стандарт C++23 (MSVC `/std:c++latest`).
Команды, зависимости и отдельные build-деревья — в [development.md](development.md).

### Ошибки и перехваты

- Проектный код по умолчанию без exceptions: `std::expected<T, E>`, bool или
  enum error-code. Для Win32/D3D — `SUCCEEDED`/`FAILED`, проверки `nullptr`,
  для Detours — `NO_ERROR`.
- При ошибке откатывай частично изменённое состояние, включая обнуление
  указателей после failed attach; не оставляй наполовину установленный хук.
- `try/catch` допустим только при обёртке внешнего API, действительно бросающего
  исключения, и только вне горячего пути. В горячем пути запрещены exceptions,
  try/catch, RTTI и вызовы бросающих API.
- `assert` — проверка debug-инварианта, не обработчик runtime-ошибки.
- Типы оригиналов оформляй как `using ..._fn = ...` рядом с указателями.
  Для нескольких Detours используй `tw::framework::detour::attach({...})`,
  а не копию кода транзакции.
- D3D9 vtable resolve — cold-path bootstrap, не повторяй его в кадре.
  В DllMain — только минимальный bootstrap; ограничения loader lock,
  синхронного WndProc/IPC, bg_work и горячего пути остаются в
  [native-правилах](development.md#native-правила).

## Организация C# и AXAML

Это правила организации из прежнего CLAUDE, а не перенос C++ naming на C#.

- ViewModel наследуются от `ViewModelBase : ObservableObject`. ViewLocator
  резолвит `FooViewModel` → `FooView` по имени типа через рефлексию: для новой
  пары нужны совпадающие имена и namespace, отдельная ручная регистрация не нужна.
- Каждой вкладке соответствует свой `<Prefix>Styles.axaml` в `Themes/`.
  Палитры, темы и общие шаблоны — в общих словарях, через `DynamicResource`,
  чтобы смена темы не требовала перезапуска.
- Общие templates используются из `Themes/SharedControlTemplates.axaml`
  (`FlatButtonTemplate`, `FlatTextBoxTemplate`, `FlatListItemTemplate`).
  Общие строительные блоки — из `Themes/SharedStyles.axaml`
  (`Card`, `Switch`, `ToggleRow`, `IconButton`, `ActionButton`, `TextField`, `RowList`).
  В модульном файле только собственное; другой размер/отступ — модификатор
  общего класса, а не его копия. Общие классы не получают префикс модуля.
- Модельные слои не зависят от UI и передают обычные C#-события; файлы данных
  приложения определяются через AppPaths, а не cwd. Подробности границ —
  [architecture](architecture.md), UI/памяти —
  [project-principles](project-principles.md#ui-и-данные-приложения).
