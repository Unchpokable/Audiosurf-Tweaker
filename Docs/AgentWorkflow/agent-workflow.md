# Рабочий процесс, приёмка и Git

## Начало и границы задачи

Прочитай AGENTS, проверь status/ветку и документ работы через
[карту](documentation-map.md). Текущий запрос владельца определяет поручение.
Исследование не означает разрешения исправить код; реализация согласованной
фазы не означает разрешения начать следующую, ожидающую его команды.
При недостатке сведений продолжай независимую часть работы, явно фиксируя
неопределённость. Не переспрашивай решения, уже принятые для этой задачи.

Базовая ветка — `Revive`. Новую фичу начинай в новой ветке от неё; уже начатые
в Revive работы, включая Skyboxes Tab и миграцию инструкций, продолжаются там.
Старые ветки `Skybox_Replacer`, `CppRecode`, `Legacy`, `master` не изменяй.
Используй Git CLI; `gh` — когда требуется GitHub.

## Реализация и приёмка

1. Установи назначение функции и ожидаемое поведение. В согласованном фазовом
   плане реализуй текущий шаг; существенные отклонения объясни и запиши.
2. Собери затронутые цели и выполни подходящие офлайн-проверки. Для UI сравни
   снимки и просмотри каждую изменённую область; объясни различия.
3. Сообщи результат, оставшиеся ограничения и конкретно что проверить в игре.
   Владелец запускает реальную игру и сообщает результат; офлайн-проверка не
   подменяет его подтверждение. Ожидание относится к этой работе, не к любому
   новому поручению.
4. Запиши результат в канонический документ работы. **После подтверждения, что
   фича реализована и работает, и после Code Review владельца агент делает
   коммит.** До этого оставь изменения для просмотра, без автокоммитов.

Неблокирующие находки запиши в относящийся к ним план/журнал как дальнейшую
работу. `Temp/KnownBugs.md` — личный блокнот владельца: не редактируй его
автоматически и не используй старые пункты как свою очередь задач.

## Коммиты и внешние действия

- Одна законченная логическая правка — один коммит или осмысленная серия.
  Генерация (`api.json`, `tw.def.lua`, bundle, `.lua.map`) и описывающая её
  документация идут с породившим изменением. Чистая механика — отдельно.
- Коммит должен собираться. Красные проверки не прячь: укажи точный результат,
  причину и ограничения. Не называй skipped/unavailable зелёной проверкой.
- Добавляй свои пути поимённо, без `git add -A`/`git add .`. При пересечении
  с чужими правками в файле согласуй разделение, не откатывай чужой труд.
- Сообщения на английском, imperative, заголовок примерно до 72 символов.
  Без префиксов Conventional Commits, внутренних номеров фаз и ссылок на
  приватные журналы. Опиши изменение так, чтобы его понял читатель без плана.
- Push, релизы, номер версии и переписывание опубликованного — по команде
  владельца. Теги новых релизов `vX.Y.Z`, старые не переименовывай. Release
  notes предназначены пользователям, а не описывают ход внутренних фаз.
- Не переноси старое разрешение свободно переписывать локальную историю.
  Значение `Co-Authored-By` для нового агента пока не определено; не подставляй
  имя Claude или вымышленного автора. Уточни при подготовке первого коммита,
  если attribution требуется; это не блокирует реализацию.

## Области записи

`Audiosurf_Steam/` — исследовательская копия для экспериментов. Базы IDA уже
содержат результаты крупных исследований: сохраняй комментарии, типы и имена;
не пересоздавай их как пустые. Приёмку записи выполняй на выделенной тестовой базе.

В Steam-установку разрешены новые **скрипты и скайбоксы**, которых там прежде
не было, либо установка/замена по явному разрешению или прямой просьбе владельца.
Перед установкой проверь назначение. Изменение API/сборка сами по себе не дают
разрешения заменить существующий пользовательский материал. DLL плагина в
рабочую игру развёртывает владелец. Продуктовая кнопка установки и разрешения
агента — разные вещи.

## Документы и память

Постоянные правила — в `Docs/AgentWorkflow`, факты реверса — в тематическом
журнале, состояние — в одном документе конкретной работы. Укажи дату и статус:
реализовано, проверено офлайн, ждёт владельца, следующий разрешённый шаг.
Не дублируй шапку плана в памяти клиента.

Завершённый план превращается в руководство модуля, а roadmap и процесс
архивируются. По месту сохраняй уникальные решения, измерения и доказательства;
проверь ссылки `§N` из документов и комментариев перед сменой секций. Не
переименовывай секции, на которые ссылается код, без полного учёта этих ссылок.
Архивные цитаты не являются действующими нормами. Новые противоречия фиксируй
с обеими ссылками и отдельным вопросом владельцу.
