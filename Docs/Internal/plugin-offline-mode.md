# TweakerPlugin: оффлайн-режим, ранняя загрузка и установка в игру

Статус: **план согласован, идёт реализация.** Текущее состояние, карта кода и команды — в §0, состояние по
фазам — таблица §0.1, результаты и расхождения с планом — в разделе каждой фазы (§8). Статус ведётся только в
§0.1, чтобы его не приходилось править в двух местах.

Документ описывает переход `TweakerPlugin.dll` с модели «хост инжектит DLL в запущенную игру» на модель
«DLL лежит в папке игры, игра грузит её сама, хост лишь подключается, если он есть». Сюда же сведены
решения по деталям. Метки: **[ответ]** — решение владельца проекта, **[принято]** — предложение из плана,
согласованное на ревью без правок. Открытых решений на ревью нет.

**Совместимости нет.** Проект не выпущен, ни одной рабочей копии этой версии Tweaker и плагина, кроме
машины разработчика, не существует. API, ABI, протокол `TW_OVL`, форматы конфигов и раскладка файлов
меняются свободно. Код совместимости со старыми сборками плагина и хоста, миграции конфигов и чтение
устаревших ключей **не пишутся**; то, что уже есть, удаляется. Живые установки разработчика переносятся
вручную (приложение А). Единственный слой совместимости в Tweaker — `LegacyDataConverter` для скинов очень
старых версий, и этот план его не касается.

Связанные документы: `overlay-protocol.md` (TW_OVL, защита от повторного инжекта — её механика здесь
заменяется), `overview.md`, `skybox-replacer-roadmap.md`, `lua-scripting.md`, публичные
`Docs/skyboxes/getting-started.md` и `Docs/scripting/getting-started.md` (описывают старые пути).

### 0.4. Как гонять на живой игре

- Игра: `D:\SteamLibrary\steamapps\common\Audiosurf`, установка Tweaker: `C:\Users\Unchp\Desktop\TweakerUI nonstable`.
- Ранний режим: положить `build\x86-release\bin\TweakerPlugin.dll` в `engine\channels\`. Пробу
  `TweakerLoadProbe*.dll` оттуда убрать — она вешает свои хуки на те же функции.
- Поздний режим (регрессия): убрать DLL из `channels\` и инжектить из TweakerUI, как раньше.
- **TweakerUI для тестов нужен пересобранный из репозитория** (`dotnet run --project TweakerUI` или
  `DeployDebug.ps1`): сборка в `TweakerUI nonstable` не примет `HANDSHAKE_ACK` с токенами и не знает ни про
  установку плагина, ни про событие `Ready`.
- Папку поставки `PluginPayload\` собирает сборка `TweakerUI` (`CopyTweakerPlugin`): DLL в `channels\`, скрипты
  в `TweakerStuff\Scripts\`. Руками её собирать не надо — раскладка там значащая, и ручная сборка уже один раз
  стоила испорченного манифеста (см. «Ф5: правка по итогам первой проверки»).
- Лог плагина: `engine\TweakerStuff\Logs\TweakerPlugin.log`. Владелец обычно кладёт копию в корень репозитория.
- Все прогоны на игре делает владелец проекта. Матрица сценариев — §9.

## 1. Зачем

- Skybox Replacer и Lua-скрипты не зависят от хоста: они работают только с ресурсами игры. Сейчас без
  запущенного TweakerUI их не получить.
- Инжектор не нужен: Quest3D при старте сам загружает DLL из `engine\channels\`. На этом живёт
  `wavebreaker_client.dll`.
- `InjectHelper.exe` — неподписанный PE, единственная задача которого — `CreateRemoteThread`-загрузка DLL
  в чужой процесс. Эвристики антивирусов на такое срабатывают. Если он перестанет запускаться в обычном
  сценарии, ложных срабатываний станет меньше.
- Файлы плагина сейчас разбросаны: `.cfg` и `Skies\` лежат рядом с TweakerUI (где угодно), скайбоксы — там,
  куда укажет `skybox_dir` (у разработчика — `engine\skyboxes\`), в `.cfg` лежат абсолютные пути.

## 2. Что установлено при изучении

### 2.1. Quest3D загружает каждую DLL из `channels\` и сразу её выгружает

`HighPoly.dll`, `ChannelList::AddDirectory` (RVA `0x2800`), при построении списка типов каналов для каждого
файла в `channels\` вызывает `EngineInterfaceExt::GetDLLType(const char*)` → `0x10004f80`:

```
LoadLibraryA(<channels>\<file>)
GetProcAddress(h, "GetType")      ; 0x10004ee0
FreeLibrary(h)
```

DLL без экспорта `GetType` не становится типом канала, но `DllMain(PROCESS_ATTACH)` у неё уже отработал.
После `FreeLibrary` образ выгружается, и поток, запущенный из `DllMain`, выполняет код, которого уже нет
в памяти.

Скан идёт **при каждом старте** — подтверждено статически в Ф0 (§8, «Ф0: результаты»): инициализация
движка безусловно вызывает `CreateChannelList`, а тот загружает-выгружает каждую `.dll`, которой нет в
`channels.lst`. DLL без `GetType` в список не попадает никогда, значит, пробуется при каждом запуске.

Вывод: первое, что плагин делает в `DllMain`, — **закрепляет свой модуль в памяти**
(`GetModuleHandleExW(GET_MODULE_HANDLE_EX_FLAG_PIN | ..._FROM_ADDRESS)`). После этого `FreeLibrary` из скана
модуль не выгрузит, а повторные `LoadLibrary` лишь увеличат счётчик ссылок без нового `DllMain`.

`wavebreaker_client.dll` экспортирует только `DllMain` и свои хуки, `GetType` у него нет. Он переживает скан и
затем ждёт появления нужных модулей (строки в бинаре: `HTTP_Fetch_Unicode.dll`, `bass.dll`,
`BASS_PreCalcSong.dll`, `GetFileAttributes.dll`, `FolderExploder.dll`, `17C5B19F-...dll`, лог
`Necessary DLLs loaded, attaching hooks`). Это ровно модель, которую мы делаем.

### 2.2. CWD игры — ненадёжная опора

В игре есть каналы `Unicode_CurrentDirectory.dll` и `GetProgramPath.dll`, и она пользуется `comdlg32`
(`GetOpenFileName` без `OFN_NOCHANGEDIR` меняет CWD). Поэтому CWD может смениться посреди сессии.
Корень всех путей — каталог исполняемого файла процесса (`GetModuleFileNameW(nullptr)` →
`...\engine\QuestViewer.exe`), вычисленный один раз при запуске (Р-9).

### 2.4. Мусор в `skybox.cfg` и вокруг него

Ключи в `skybox_config.cxx` и кто их реально читает:

| Ключ | Статус |
|---|---|
| `enabled` | живой, тумблер на вкладке Skybox |
| `skybox` | ключ встроенного cube-ресурса; один из трёх способов сказать «какое небо» |
| `skybox_file` | путь к картинке или папке граней; перекрывает `skybox` |
| `sky_program` | id встроенного шейдера **или** путь к `.hlsl`/`.sky`; перекрывает оба предыдущих |
| `skybox_dir` | корень каталога небес, пути от трёх корней |
| `hdr_exposure`, `min_face_size` | живые, только для cube map, в UI нет |
| `yaw_degrees`, `pitch_degrees`, `z_up` | живые (`rebuild_orientation`, матрица идёт и в cube map, и в шейдер), в UI нет |
| `shader_quality` | живой, выбор на вкладке Skybox |
| `probe_markers` / `shader_test_markers` | отладка: маркеры осей встроенного неба `probe` |
| `shader_test` | миграция Phase 0 → `sky_program=probe` |
| `param.*` | читаются и выбрасываются — остаток от времён до `Skies\*.json` |

Выбор неба размазан на три ключа с неявным приоритетом, который `selected_catalog_index` повторяет вручную
и сравнивает пути через `std::filesystem::equivalent`. Встроенная программа `probe`
(«Axis Probe (diagnostic)», `sky_probe.ps.hlsl`) — инструмент калибровки осей, задачу свою выполнил.

### 2.5. При ранней загрузке нынешнее рукопожатие не работает

`claim_single_instance` создаёт мьютекс в самом начале `load_thread`. Перехват `WndProc`, без которого плагин
не услышит `HANDSHAKE_BEGIN`, ставится только в `bind_device`, то есть после создания D3D-устройства. Хост на
`Registered` видит мьютекс, шлёт `HANDSHAKE_BEGIN`, не получает ответа за 5 с и останавливает службу. При
ранней загрузке окно «плагин загружен, но ответить ещё нечем» — обычное состояние на старте игры. Хосту нужен
явный сигнал готовности (§5.1).

### 2.6. Прочее

- Release-сборка плагина логов не пишет вообще (`TW_DIAGNOSTICS_ENABLED 0`). Для оффлайн-пользователя это
  значит, что сбой ранней загрузки ничем не диагностируется.
- В debug-сборке `diagnostics::initialize` делает `AllocConsole` — теперь это будет при каждом запуске игры с
  debug-DLL в `channels\`. Для разработки это нормально, в бандл debug-DLL не попадает.
- Скан `channels\` берёт только файлы с расширением `DLL` (фильтр в `AddDirectory`), так что не-DLL файлы там
  (`Microsoft.VC80.CRT.manifest`, `search_symbol.py`) он не трогает вовсе.
- Харнесс `harness/skyload/settings.cxx` подменяет `tw::skybox::dll_directory()` своей функцией. Новый модуль
  путей должен сохранить такой шов.

### 4.2. Запуск по этапам

Основано на Ф0 (§8, ревизии 1–3 пробы). Главное из замеров:

- плагин загружается главным потоком внутри перебора каналов; окно игры уже есть (скрытое), `d3d9.dll` ещё нет;
- через ~35 мс `d3d9.dll` загружается **пробно** (зависимость канала `E2D1C95B`), выгружается и загружается снова;
- через ~90 мс игра зовёт `Direct3DCreate9`, через ~130 мс создаёт оконное устройство, через ~250 мс грузит
  Texture-канал (тоже дважды), через ~620 мс создаёт `IDirectInput8A`;
- временное устройство в этот период тормозит инициализацию D3D игры на ~1 с, а опрос `GetModuleHandleW`
  проигрывает гонку за первый `Direct3DCreate9`.

Поэтому режимов два, и выбираются они в `DllMain` по одному признаку — **загружен ли уже `d3d9.dll`**:

- **ранний** (`d3d9.dll` нет) — загрузка из `channels\`. Хуки ставятся цепочкой от создания настоящих объектов
  игры: временных устройств и временных объектов DirectInput нет вовсе (Р-23, Р-24);
- **поздний** (`d3d9.dll` есть) — инжект через «Загрузить сейчас». Нынешний проверенный путь без изменений:
  временное устройство, временные объекты DirectInput, поздняя привязка через `EndScene`/`Present`.

#### Правила для кода под loader lock

Касаются `DllMain` и обработчика уведомлений загрузчика. Выведены из зависания ревизии 2 пробы (§8):

- код выполняется под loader lock, обработчик уведомлений — на **произвольном** потоке, не обязательно главном;
- нельзя ничего, что ждёт другой поток: оконные функции, отправляющие сообщения (`GetWindowTextW`,
  `SendMessage`, создание окон), ожидания событий/мьютексов, запуск потоков с ожиданием, COM;
- нельзя приостанавливать другие потоки (`DetourUpdateThread` на чужие потоки): замороженный поток может
  держать heap lock, а Detours выделяет память;
- можно: `GetModuleFileNameW`, `GetFileAttributesW`, `CreateMutexW`/`CreateEventW`, `GetProcAddress` по
  загружаемому модулю, одна транзакция Detours **без чужих потоков**, атомарные флаги, запись в лог
  жизненного цикла (только kernel32);
- патч без приостановки потоков допустим, только когда целевой код **гарантированно никто не выполняет**:
  экспорт модуля, который прямо сейчас загружается, либо функция, которую до этого момента не вызывал никто.

`framework/detour_transaction` получает для этих случаев параметр `detour::suspend::none`. По умолчанию `attach`
по-прежнему приостанавливает все остальные потоки. Все транзакции процесса выполняются по очереди под общей
блокировкой. Detours держит одну незавершённую транзакцию на процесс, и две параллельные установки провалили бы
одну из них. Ждать эту блокировку под loader lock безопасно: транзакция сама loader lock не берёт.

#### Этап 0 — `DllMain(PROCESS_ATTACH)`

1. `DisableThreadLibraryCalls`.
2. Проверка процесса: исполняемый файл не `QuestViewer.exe` → выход, модуль инертен. DLL из `channels\` может
   загрузить любой инструмент на движке.
3. Корень путей (`GetModuleFileNameW(nullptr)`) и проверка `TweakerStuff\DISABLE` (Р-17) — голым Win32, без
   создания каталогов. Есть `DISABLE` → выход.
4. `claim_single_instance()` (мьютекс) и создание несигнального события `Ready` (§5.1). Копия уже живёт в
   процессе → выход без PIN, без хуков, без потока.
5. PIN (Р-10).
6. Режим: `GetModuleHandleW(L"d3d9.dll") == nullptr` → ранний, иначе поздний.
7. **Ранний режим:**
   - `LdrRegisterDllNotification` (Р-23) — до возврата из `DllMain`, иначе пробная загрузка `d3d9.dll` через
     ~35 мс пройдёт мимо;
   - детур `A3d_Channel::CallChannel` (`HighPoly.dll` уже загружен) без приостановки потоков — во время перебора
     каналов его никто не выполняет;
   - детур экспорта `DirectInput8Create` без приостановки потоков — плагин импортирует `DINPUT8.dll`
     статически, модуль уже загружен, а игра впервые вызовет его через ~0.6 с (Р-24).
8. `_beginthreadex(load_thread)`.

#### Обработчик уведомлений загрузчика (ранний режим)

Подчиняется правилам выше. Реагирует только на свои модули, остальные игнорирует без записи в лог.

| Модуль | Загружен | Выгружен |
|---|---|---|
| `d3d9.dll` | закрепить модуль (`GetModuleHandleExW(FROM_ADDRESS \| PIN, base)`, Р-25), затем детур экспорта `Direct3DCreate9` без приостановки потоков | не происходит — модуль закреплён; если уведомление всё же пришло, это аномалия: флаг для лога жизненного цикла, хуки не трогаются |
| `BC052C38-2D5D-4F0C-A0CA-654D0AFC584A.dll` (Texture-канал) | закрепить модуль (Р-25), затем `install_texture_hook()` без приостановки потоков (разрешает свои экспорты и `GetChannelName` из `HighPoly`) | не происходит — то же, что для `d3d9` |

`HighPoly` грузит каждый канал дважды (пробно ради `GetType` и рабочей загрузкой), и без закрепления оба модуля выгружались бы между загрузками вместе со своими хуками (Ф0, ревизия 3). Закрепление на первой, пробной загрузке оставляет в процессе один образ: пробный `FreeLibrary` снимает только чужую ссылку, рабочая загрузка получает уже загруженный модуль, хуки ставятся один раз. Цена — `DllMain` этих модулей выполняется однажды, а не дважды (загрузка–выгрузка–загрузка); подтверждено ревизией 4 пробы (§8, Ф0).

#### Цепочки на главном потоке игры (ранний режим)

Вызываются кодом игры во время инициализации, **не** под loader lock. Каждая транзакция Detours здесь
выполняется один раз на образ модуля и **без приостановки остальных потоков** (пересмотрено при реализации Ф2).

Почему без приостановки. Каждое звено цепочки патчит код, который ещё никто не выполнял. `Direct3DCreate9`
перехвачен из уведомления о загрузке `d3d9.dll` — до первого вызова. Значит, первый `IDirect3D9`, который он
вернул, — первый в процессе, и его `CreateDevice` ещё не вызывался. Методы первого устройства не вызывались до
того, как `CreateDevice` отдал это устройство. С DirectInput так же: `DirectInput8Create` перехвачен в `DllMain`.

Приостановка же здесь опасна. В это время поток запуска и поставленные им в пул компиляции шейдеров неба
постоянно выделяют память. Поток, замороженный с блокировкой кучи, вешает игру прямо внутри транзакции:
Detours сам выделяет память, пока остальные потоки стоят.

1. `hk_direct3d_create9` → оригинал → на первом успешном вызове для текущего образа `d3d9`: детур
   `IDirect3D9::CreateDevice` (vtable[16] **настоящего** объекта игры).
2. `hk_create_device` (существующий) → оригинал → на первом устройстве образа: детуры `Reset`, `Present`,
   `EndScene`, `SetTexture`, `DrawPrimitive`, `DrawIndexedPrimitive` по vtable настоящего устройства и
   `IDirect3DSwapChain9::Present` по его цепочке обмена — те же точки, что сейчас берутся от временного
   устройства. Затем обычная логика `bind_device` (с учётом готовности, см. ниже).
3. `hk_direct_input8_create` → оригинал → на первом объекте каждого вида (A/W по `riid`): детур
   `IDirectInput8::CreateDevice` (vtable[3]) → `hk_dinput_create_device` → оригинал → на первом устройстве:
   детуры `GetDeviceState`/`GetDeviceData` (vtable[9]/[10]) **настоящего** устройства игры. Временных объектов
   DirectInput и связанной с ними намеренной утечки (комментарий в `dinput8_hooks.cxx`) в раннем режиме нет.

**Транзакции на главном потоке.** Главный поток Quest3D — он же рендер-поток. Транзакции Detours в пунктах 1–3 —
системные вызовы на этом потоке, и это **разрешено**: они выполняются во время инициализации игры, внутри
`Direct3DCreate9`/`CreateDevice`/`DirectInput8Create`, а не во время кадра (правило рендер-потока, §4.5,
**[ответ]**). Инициализация имеет право подтормозить игру.

#### Готовность подсистем (`g_ready`)

Хуки раннего режима начинают срабатывать через ~90 мс, а поток запуска за это время может не успеть загрузить
ресурсы, конфиги и подписчиков. Сегодняшнее правило «подписаться до хуков» в раннем режиме заменяется
флагом:

- `std::atomic_bool g_ready`, взводит поток запуска после всех регистраций (этап 1 ниже);
- до `g_ready` все хуки — чистый проброс в оригинал: без `bind_device`, без перехвата отрисовки, без
  подписчиков текстур; установка цепочек (детуры) при этом **не** откладывается;
- первая привязка после `g_ready` идёт уже существующим поздним путём: `hk_end_scene`/`hk_present` видят
  `g_bound_device == nullptr` и вызывают `bind_device`;
- векторы подписчиков заполняются до `g_ready` и дальше не меняются — флаг и есть точка их публикации.

Текстуры неба, загруженные до `g_ready`, скайбокс не опознает до их следующей перезагрузки. Поэтому длительность
этапа 1 меряется логом жизненного цикла, а каждая текстура, прошедшая мимо до `g_ready`, пишется туда поимённо.
Порядок регистраций внутри этапа 1 на это не влияет: флаг один и взводится после всех регистраций. Поэтому
скайбокс не переставлен в начало, порядок остался прежним (пересмотрено при реализации Ф2).

В коде флаг — `framework/ready` (`publish()` / `published()`).

#### Этап 1 — поток запуска

1. `diagnostics::initialize()`, `paths::create_directories()` (сами пути вычислены ещё в `DllMain`,
   `paths::resolve()`).
2. `resource::initialize`, `d3d9::initialize` (подписка `WM_ACTIVATEAPP`, раньше жила в `install_d3d9_hooks`),
   `ui::initialize`, `skybox::initialize`, `skybox::ui::initialize`, `lua::ui::initialize`, `lua::host::initialize`
   (разрешает точки входа `HighPoly`), слушатель первой привязки (этап 2).
3. `ready::publish()`.
4. **Только поздний режим:** нынешняя последовательность установки — `install_channel_hook`,
   `install_texture_hook` (с повтором из `on_device_bound`), `install_d3d9_hooks` (временное устройство),
   `dinput::install_hooks` (временные объекты).

#### Этап 2 — готовность к `TW_OVL`

Слушатель привязки устройства взводит атомарный флаг и сам переключает `Ready` в сигнальное состояние
(`SetEvent`): привязка — инициализация, системный вызов там разрешён (§4.5). Поток запуска ждёт тот же флаг,
чтобы перейти к этапу 3. Причина места: подписка `ipc`
на `WM_COPYDATA` существует с этапа 1, но сам хук окна ставится в `bind_device`.

#### Этап 3 — завершение

Запуск сторожа хоста (§4.5), запись «запуск завершён», поток запуска завершается.

Ожидания без общего таймаута: оффлайн-плагину некуда торопиться. Если этап ждёт дольше 30 с, в лог пишется,
чего именно нет.

### 4.5. Связь с хостом: `g_host_present`

`std::atomic_bool g_host_present { false }`, все чтения и записи — `std::memory_order_relaxed`. Наружу —
`tw::ipc::host_present()`.

**Кто взводит `true`:** IPC-поток, при `HANDSHAKE_BEGIN`, если `FindWindowA` нашёл окно моста. Затем
`HANDSHAKE_ACK` (§5.2).

**Кто сбрасывает в `false`** (любой из трёх, вместе с `g_bridge_hwnd = nullptr`):

1. **`HOST_DISCONNECT`** от хоста — явное «я закрываюсь» (§5.2). IPC-поток.
2. **Сторож** — `std::jthread`, стартует на этапе 3. Цикл: `std::this_thread::sleep_for(1s)`; если
   `g_host_present` — `IsWindow(g_bridge_hwnd)`; окна нет → сброс. Всё время жизни процесса поток спит;
   `stop_token` проверяется в цикле ради порядка, хотя пути выгрузки у плагина нет. Нужен на случай, когда
   хост умер, не успев послать `HOST_DISCONNECT` (краш, убит из диспетчера задач): `asbridge` умирает вместе с
   ним по защите от осиротения, окно исчезает.
3. **Неудачный `SendMessage`** в `send_payload_to_bridge`. Поток отправителя.

**Сброс состояний при уходе хоста.** Владение данными остаётся прежним:

- `overlay_state` и `qp::state` (писатели под мьютексом) сбрасывает поток, сбросивший флаг.
- `pending_actions` и `qp::pending` принадлежат рендер-потоку. Он сам замечает фронт: сравнивает
  `host_connected` из своего снимка `overlay_state` с прошлым кадром (сравнение `bool`, без системных вызовов;
  в Ф3 вместо чтения атомика — см. «Ф3: результаты»). На
  фронте `true → false` — сброс pending и тост «Audiosurf Tweaker отключён»; на фронте `false → true` — тост
  «Подключено к Audiosurf Tweaker».

**Правило рендер-потока** **[ответ]**. Запрет на системные вызовы касается **работы во время игры**, когда
всё проинициализировано и идут кадры: всё, что вызывается каждый кадр из `Present`/`EndScene`/draw-хуков,
`CallChannel`, dinput-хуков, `WndProc`, включая `ui::draw_frame`. Там — никаких системных вызовов, кроме
DirectX API: ни `IsWindow`, ни `SetEvent`, ни записи в лог, чтобы не просаживать FPS.

**Инициализация под запрет не попадает**, даже если она идёт на том же потоке: цепочки создания
`Direct3DCreate9`/`CreateDevice`/`DirectInput8Create`, привязка и перепривязка устройства (`bind_device`,
в том числе при переходе в fullscreen и `Reset`), первый кадр после привязки. Пока игра грузится, плагин
имеет право её подтормозить: Detours-транзакции, запись в лог жизненного цикла, установка хука окна.

Всё новое в этом плане подчиняется правилу. Уже существующие нарушения в покадровом коде, если найдутся,
этим планом не чинятся, но и не размножаются.

**Переподключение:** новый TweakerUI → новый `asbridge` → `Registered` → `HANDSHAKE_BEGIN`. Отдельной логики
не нужно.

**UI:**

- Вкладки Skins / Tweaks / Player при `!host_present()` рисуют заглушку: «Audiosurf Tweaker не подключён.
  Скайбоксы и скрипты работают без него.» (Р-4). Индексы вкладок не меняются.
- Пин «Offline» — отдельной строкой в `pins`, с приглушённым акцентом, если `offline_pin` включён (Р-7).
- Пока хоста нет, `pending_actions`/`qp::pending` запросы не создают: кликать на заглушках нечего.

### 4.6. Лог жизненного цикла (Р-18)

Политика «Release вырезает все логи» сохраняется для `TW_LOG_*`. Рядом появляется отдельный узкий канал
`TW_BOOT_LOG`, который пишется в Release:

- что пишется: этапы 0–3 и режим загрузки, установка и сброс хуков по образам модулей, найденные и не найденные модули, результаты установки хуков, handshake, уход хоста
  (с причиной: `HOST_DISCONNECT` / сторож / `SendMessage`), ошибки создания каталогов и чтения `module.json`;
- откуда можно звать: поток запуска, IPC-поток, сторож, а на главном (рендер-) потоке — только из
  инициализации (цепочки создания, `bind_device`, `Reset`), по правилу §4.5. **Из покадрового кода —
  никогда**;
- синхронный `WriteFile` в `TweakerStuff\Logs\TweakerPlugin.log`; при открытии файл обрезается, если больше
  1 МБ.

### 4.7. `SkyboxReplacer\module.json` (Р-19, Р-20, Р-22)

```json
{
  "enabled": true,
  "sky": { "kind": "package", "id": "ODC_VolTex.sky" },
  "cubemap": { "hdr_exposure": 1.0, "min_face_size": 0 },
  "orientation": { "yaw_degrees": 0.0, "pitch_degrees": 0.0, "z_up": false },
  "shader": { "quality": 100 }
}
```

**Выбор неба — один объект `sky`** вместо трёх ключей с приоритетом. `kind` совпадает один в один с
`tw::skybox::entry_kind` каталога:

| `kind` | `id` | Откуда |
|---|---|---|
| `program` | `gradient`, `night` | встроенные шейдеры в DLL |
| `packed` | ключ ресурса, например `skyboxes/cloudy_01.png` | встроенные cube-картинки в DLL |
| `package` | имя папки или zip `.sky` прямо в `Skyboxes\` | диск |
| `shader_file` | имя `.hlsl` прямо в `Skyboxes\` | диск |
| `file` | имя картинки (крест 4×3 или панорама 2:1) прямо в `Skyboxes\` | диск |
| `face_dir` | имя папки шести граней прямо в `Skyboxes\` | диск |

- **Id дисковых небес — одно имя, не путь** (уточнено при реализации Ф1). Каталог перечисляет только прямых
  детей `Skyboxes\`, так что более длинному id назвать нечего. Имя без разделителей не может выйти за папку.
  Проверка — `sky_paths::skybox_path`: пустое имя, `.`, `..`, `/`, `\`, `:` и управляющие символы
  отвергаются. Абсолютные пути не поддерживаются.
- Выбор хранит `kind` явно, а не угадывает его по файлу заново. `selected_catalog_index` становится
  сравнением двух строк и перечисления.
- `id` неизвестен (файл удалён, `kind` не распознан) → предупреждение в лог и небо по умолчанию.

**Остальные ключи:**

- `cubemap.hdr_exposure`, `cubemap.min_face_size` — действуют только на `packed`/`file`/`face_dir`.
- `orientation.*` — матрица из `rebuild_orientation`, общая для cube map и шейдеров, как сейчас.
- `shader.quality` — проценты разрешения шейдерного неба (сейчас `shader_quality`, шаги 100/67/50/33).

**Нет файла** — пишутся значения по умолчанию: `enabled=true`, `sky = { packed, skyboxes/cloudy_01.png }`,
`hdr_exposure=1`, `min_face_size=0`, ориентация нулевая, `quality=100`. **Неизвестные ключи** не читаются и при
следующей записи не сохраняются. **Битый JSON** — предупреждение в лог, работа на значениях по умолчанию, файл
не перезаписывается, пока пользователь не изменит настройку из UI (иначе ручную правку с опечаткой молча
затрёт).

Разбор — `yyjson` (уже в вендоре); запись — через `yyjson` mutable API или ручной сериализацией по образцу
`sky_settings`, что короче. Комментариев в JSON нет: пояснения к ключам переезжают в
`Docs/skyboxes/manifest.md` (или новый раздел getting-started).

**Удаляется из кода:** ключи `skybox`, `skybox_file`, `sky_program`, `skybox_dir`, `probe_markers`,
`shader_test_markers`, `shader_test` и его миграция, пропуск `param.*`, программа `probe` и её шейдер, тумблер
маркеров, функции `select_packed` / `select_file` / `select_program` в нынешнем виде (заменяются одной
`select(kind, id)`), `resolve_source_path` с тремя корнями.

## 5. Протокол (правки `overlay-protocol.md`)

Старая логика защиты от повторного инжекта (проба без мьютекса, поиск модуля по пути и имени, ветки для
плагинов без мьютекса) удаляется. Совместимости с прежними хостами и плагинами нет.

### 5.1. Присутствие и готовность

Плагин на этапе 0 (`DllMain`) создаёт:

- мьютекс `Local\AudiosurfTweaker.Overlay.<pid>` — «плагин загружен в этот процесс» (он же страховка от второй
  копии при «Загрузить сейчас»);
- событие `Local\AudiosurfTweaker.Overlay.<pid>.Ready` (manual-reset, изначально несигнальное) — на этапе 2
  становится сигнальным: «`TW_OVL` принимается».

Оба хендла живут до конца процесса.

Хост (`OverlayHelper`) на `Registered`:

| Мьютекс | `Ready` | Действие |
|---|---|---|
| нет | — | плагин не загружен → §6.5 |
| есть | не сигнальное | ждать сигнал до 60 с (`WaitForSingleObject` в `Task.Run`); не дождался — запись в лог, службу не останавливать |
| есть | сигнальное | `HANDSHAKE_BEGIN`, до 3 попыток по 5 с; ответа нет — остановка службы, как сейчас (`SuspendService`) |

### 5.2. Операции

| OP | Направление | Токены | Смысл |
|---|---|---|---|
| `HANDSHAKE_BEGIN` | host → plugin | `<caption>` | без изменений |
| `HANDSHAKE_ACK` | plugin → host | `<version> <protocol> <load_mode>` | `version` — `major.minor.patch.build` из VERSIONINFO; `protocol` — целое, растёт при несовместимых изменениях L3; `load_mode` — `channels` или `injected` (путь модуля сравнивается с `engine_root()\channels`) |
| `HOST_DISCONNECT` | host → plugin | — | хост закрывается; плагин сбрасывает `g_host_present` |
| `HANDSHAKE_PING` | — | — | удаляется: сторож и `HOST_DISCONNECT` закрывают его задачу |

Хост разбирает `HANDSHAKE_ACK` по префиксу. `protocol` не совпал с ожидаемым → handshake считается
неудачным, пользователь видит «версия плагина в игре не совпадает с Tweaker — обновите плагин» (обновление —
§6.3–6.4).

`HOST_DISCONNECT` хост отправляет при штатном закрытии (`App` shutdown) до остановки моста. Доставка
best-effort: `OverlayCommand` синхронно ставит сообщение в пайп, мост успевает его отправить до своей
остановки. Не дошло — через ~1 с отработает сторож.

## 6. Хост

### 6.1. Раскладка поставки в папке TweakerUI

Бандл содержит зеркало целевой раскладки, и установка сводится к копированию дерева:

```
TweakerUI\
|- TweakerUI.exe, asbridge.exe, LegacyDataConverter.exe
|- InjectHelper.exe                      <- запасной путь (Р-5)
|- PluginPayload\
   |- channels\TweakerPlugin.dll
   |- TweakerStuff\Scripts\*.lua
```

Встроенные небеса живут ресурсами внутри DLL, а **поставляемые пакеты `.sky` едут отдельно** — их источник
папка `Skyboxes\` в корне репозитория, а место в поставке `PluginPayload\TweakerStuff\SkyboxReplacer\Skyboxes\`
(Р-22). Правила Р-2 для них те же, что для скриптов: пакет, который пользователь правил, при обновлении
сохраняется рядом как `.old`.

**Что вообще попадает в поставку, решает одно место — `CopyTweakerPlugin` в `TweakerUI.csproj`**, и правило
одно на оба источника: **подпапка `dev\` не едет никуда**. В `TweakerPlugin\assets\scripts\dev\` лежат пробы,
которые проверяют работоспособность API (печатают вердикт «сходится/не сходится») или требуют фикстуры, которой
у пользователя нет; в `Skyboxes\dev\` — зазипованная копия `OurDraftsCollides`, существующая ради второй формы
формата. Подпапка, а не пометка внутри файлов, потому что игровую папку `Scripts\` плагин сканирует
**не**рекурсивно: то, что разработчик хочет видеть в игре, он кладёт туда плоско вручную — и такой файл остаётся
его собственным, потому что в поставке его нет, а значит нет и в манифесте (§6.3).

### 6.2. Манифест `TweakerStuff\.deploy.json`

```json
{
  "plugin_version": "1.4.0.0",
  "files": {
    "channels/TweakerPlugin.dll": { "sha256": "..." },
    "TweakerStuff/Scripts/puzzlepro_hud.lua": { "sha256": "..." }
  }
}
```

Хранит ровно то, что хост положил сам, и хеш **положенного** содержимого. Пользовательские файлы в манифест не
попадают и хостом не трогаются никогда.

### 6.3. Установка и обновление (`TweakerCore`, `PluginInstallation`)

Вход: папка `engine` (родитель `GameTexturesPath`; проверка — рядом лежат `QuestViewer.exe` и `channels\`),
папка поставки. **Предусловие:** игра не запущена, либо это первая установка (§6.4) — `PluginInstallation`
сама процессы не проверяет, это делает вызывающий в `TweakerUI`.

Для каждого файла поставки:

| На диске | В манифесте | Действие |
|---|---|---|
| нет | нет | положить, записать в манифест |
| нет | есть | пользователь удалил поставляемый файл — **не** восстанавливать; будущая кнопка «Восстановить поставляемые скрипты» |
| есть, хеш = манифест, хеш ≠ поставке | есть | не менялся — перезаписать молча |
| есть, хеш ≠ манифест, хеш ≠ поставке | есть | менял пользователь — переименовать в `<name>.old` (занято — `<name>.old.2`, `.old.3`…), положить новый, добавить в отчёт «обновлён, ваша версия сохранена» (Р-2) |
| есть, хеш = поставке | любое | ничего, обновить манифест |
| есть | нет | файл пользователя с тем же именем — поступить как с изменённым пользователем |

- Файлы из манифеста, которых больше нет в поставке: не менялись — удалить; менялись — оставить и убрать из
  манифеста (файл стал пользовательским).
- Плагин сканирует строго `*.lua` (`extension() == L".lua"`), поэтому `.old`-копии в `Scripts\` не запустятся.
- DLL сравнивается по версии из `FileVersionInfo`, а при равной версии — по хешу. Для неё правило «менял
  пользователь» не действует, DLL всегда наша.
- Удаление плагина: удаляется `channels\TweakerPlugin.dll` и её строка в манифесте. `TweakerStuff\` не
  трогается — пользовательские данные при удалении плагина не удаляются никогда.
- Отчёт (список обновлённых и сохранённых как `.old`) хост показывает уведомлением.

### 6.4. Запущенная игра (Р-16)

Перед любой установкой, обновлением или удалением `TweakerUI` проверяет `QuestViewer.exe`:

- **Не запущена** → действие выполняется.
- **Запущена, первая установка** (в `channels\` нет `TweakerPlugin.dll`) → файлы кладутся сразу, дальше —
  предложение загрузить плагин в текущую сессию (§6.5).
- **Запущена, обновление или удаление** → диалог: «Нужно обновить модули Tweaker в игре, но Audiosurf
  запущен. Закройте игру сами или разрешите закрыть её».
  - «Закрою сам» → хост ждёт выхода процесса (кнопка «Отмена» в ожидании), затем действие. Игру после этого
    не запускает — закрывал пользователь.
  - «Закрыть» → подтверждение про потерю прогресса заезда → закрытие (§6.5) → действие → **запуск игры**.
  - «Отмена» → ничего; при старте TweakerUI и при следующем `Registered` предложение повторится.

Никаких переименований загруженной DLL, промежуточных каталогов и отложенных замен.

### 6.5. `OverlayHelper`: поток подключения

Настройки (Р-6):

- `PluginInstalled` не хранится в конфиге хоста, а выводится из диска: DLL в `channels\` есть / нет. Тумблер
  вызывает установку или удаление (§6.4). Меняется `GameTexturesPath` — состояние перечитывается.
- `SyncOverlayWithTweaker` — новая настройка вместо `EnableInGameOverlay`. Старый ключ удаляется из
  `ConfigurationManager` без переноса значения.

При старте TweakerUI, если плагин установлен, а поставка новее — обновить по §6.3–6.4 и показать отчёт.

На `Registered`, если `SyncOverlayWithTweaker`:

```
мьютекс?
|- есть -> ждать Ready -> HANDSHAKE_BEGIN (3 x 5 с) -> ACK: разбор version/protocol/load_mode -> ready
|                                                 \-> SuspendService
\- нет  -> плагин установлен на диске?
           |- нет -> ничего
           \- да  -> игра запущена раньше установки: предложение (Р-5), один раз на PID игры
```

Предложение (**один раз на PID игры** — повторный `Registered` в той же сессии его не повторяет):

- `InjectHelper.exe` на месте → диалог «Плагин установлен, но эта сессия игры запущена без него» с кнопками
  «Загрузить сейчас», «Перезапустить игру», «Позже».
  - «Загрузить сейчас» → `RunInjectorAsync(pid, <engine>\channels\TweakerPlugin.dll)` → ожидание `Ready` →
    handshake.
- `InjectHelper.exe` нет → «Перезапустить игру» и «Позже», плюс текст: «InjectHelper.exe не найден — вероятно,
  его удалил антивирус. Загрузить сейчас без него нельзя. Скачать заново:
  https://github.com/Unchpokable/Audiosurf-Tweaker/releases — и добавьте папку Tweaker в исключения
  антивируса».
- `ApplicationNotificationManager.AskForAction` возвращает `bool` — для трёх исходов нужен новый метод
  (выбор из N кнопок) в `TweakerDialogWindow`.

**Закрытие и запуск игры (Р-21)** — общий сервис `GameProcessService` в `TweakerUI`; им же пользуется
`ColorsConfiguratorViewModel.ApplyPaletteToGame`, где сейчас свой `taskkill` и запуск через `cmd`.

- Закрытие: `WM_CLOSE` в главное окно `QuestViewer.exe`, ожидание выхода до 10 с; не вышла —
  `taskkill /f /pid`.
- Запуск: `Process.Start(new ProcessStartInfo("steam://rungameid/12900") { UseShellExecute = true })`.
  Обработчика протокола нет (`Win32Exception`) → уведомление «Steam не найден. Похоже, это не Steam-копия
  Audiosurf — купите игру в Steam» и запуск `Audiosurf.exe` из корня игры.

Порядок при закрытии TweakerUI: `HOST_DISCONNECT` → остановка моста.

### Ф0. Замеры на реальной игре

Песочница игру не запускает — прогоняет пользователь. Инструмент — отдельная измерительная DLL
`TweakerPlugin/probe/load_probe.cxx` (`TweakerLoadProbe.dll`, пресет `loadprobe`), а не урезанный плагин:
так замер не зависит от готовности Ф2 и не тащит в процесс хуки оверлея.

Что выяснить:

1. Переживает ли закреплённый модуль скан `channels\` (нет краша на первом и последующих запусках).
2. Пересобирается ли `channels.lst` при каждом старте. Статически — кто вызывает
   `ChannelList::CreateChannelList` и при каком условии (`Tools/CgrPy` `disasm`); эмпирически — время
   изменения файла.
3. Хронология с отметками времени от `DllMain`: в каком потоке и когда пришёл `PROCESS_ATTACH`; когда
   появляются `HighPoly.dll`, `d3d9.dll`, `dinput8.dll`, Texture-канал; когда окно игры и первый
   `CreateDevice`; CWD в момент загрузки.
4. Успевает ли временное устройство этапа 3 до `CreateDevice` игры и нет ли побочных эффектов
   (fullscreen-старт, alt-tab).

Решения по этапу 3 и по Р-11 принимаются по результатам ревизии 2 пробы (см. ниже).

#### Ф0: результаты статического разбора (`HighPoly.dll`, `Tools/CgrPy`)

- Инициализация движка (функция `0x100051a0`, без экспортного имени): если `PATH` ещё не содержит папку
  движка, дописывает к нему `<engine>\channels;<engine>\3rd;<engine>;`, затем вызывает у `ChannelList`
  `SetChannelDir` (слот 11) и **безусловно** `CreateChannelList` (слот 1).
- `CreateChannelList` (`0x27a0`): `LoadChannelList` (слот 3, читает `channels.lst`), затем
  `AddDirectory(<engine>\channels, -1)` (слот 6), затем `SortChannelList`.
- `AddDirectory` (`0x2800`): перечисляет файлы с фильтром `DLL`; для каждого сравнивает имя (`_stricmp`) с уже
  известными записями списка; **нет в списке** → `GetDLLType` → `LoadLibraryA` / `GetProcAddress("GetType")` /
  `FreeLibrary`. Записью становится только DLL с `GetType`. Второй проход с фильтром `DLE` — только для
  приложения `Quest3D Editor`.
- Следствие: DLL без `GetType` (`wavebreaker_client.dll`, `TweakerPlugin.dll`) загружается и тут же
  выгружается **при каждом старте**, и больше движок её не грузит. Постоянное присутствие такого модуля
  возможно только если он сам удержит себя в памяти — PIN (Р-10) обязателен.
- Слоты `ChannelList` (vtable `0x13400`): 1 `CreateChannelList`, 2 `SaveChannelList`, 3 `LoadChannelList`,
  4 `SortChannelList`, 6 `AddDirectory`, 11 `SetChannelDir`.

#### Ф0: результаты рантайма, ревизия 2 (14.09.2026) — зависание

Три прогона. **A (observe) отработал**, **B и C повесили игру** до показа окна: процесс жив, CPU 0%, закрывался
через Steam или диспетчер задач.

Прогон A:

- `attach` на главном потоке, стек из `HighPoly` (тот же, что в ревизии 1), и **через 1 мс
  `detach (FreeLibrary)`**. Рантайм-подтверждение §2.1: без PIN DLL из `channels\` выгружается сразу.
- На момент `attach` у процесса **уже есть окно** `class='Start'`, `title='QuestViewer'`, 1280×720, **скрытое**,
  плюс `Default IME`, оба на главном потоке. Гипотеза владельца проекта в этой части верна: окно создаётся до
  перебора каналов. `d3d9.dll` при этом ещё не загружен.

Прогоны B и C: после `LdrRegisterDllNotification status=0` в лог не попало больше ни одной строки — ни
`thread: started`, ни одного `module: loaded`. Первый же вызов обработчика уведомления не дошёл до своей записи
в лог.

Причина — ошибка пробы: до первой записи обработчик перечислял окна процесса через `GetWindowTextW`. Для окна
**другого потока** это `SendMessage(WM_GETTEXT)` в поток-владелец. Уведомление загрузчика выполняется под loader
lock и на том потоке, который грузит DLL. Если это не главный поток (в процессе есть потоки Steam-оверлея
`gameoverlayrenderer.dll`), то он держит loader lock и ждёт главный поток, а главный поток, владелец окна, стоит
в очереди за тем же loader lock на загрузке следующего канала. Взаимная блокировка, 0% CPU. Поток пробы при этом
не стартует: инициализация нового потока тоже ждёт loader lock.

Это не просто баг инструмента, а **правило для плагина** (вошло в §4.2, «Правила для кода под loader lock»):

- обработчик уведомления выполняется под loader lock на произвольном потоке;
- в нём нельзя ничего, что ждёт другой поток: оконные функции, отправляющие сообщения (`GetWindowTextW`,
  `SendMessage`, создание окон), ожидания событий и мьютексов, запуск и присоединение потоков;
- нельзя приостанавливать другие потоки (`DetourUpdateThread` на чужие потоки): замороженный поток может
  держать heap lock, а Detours выделяет память. Для экспорта модуля, который прямо сейчас загружается,
  приостановка и не нужна — его код ещё никто не выполняет;
- допустимо: `GetProcAddress` по загружаемому модулю, одна транзакция Detours без чужих потоков,
  атомарные флаги.

#### Ф5: проверка на игре (22.09.2026)

Владелец прогнал вживую. Плагин несколько дней используется вообще без хоста: небо, скрипты и оверлей
работают, Lua-движок переживает кривое состояние игры на раннем старте (сама лагающая загрузка — пункт Ф8,
договорились чинить после основной работы). Установка и удаление плагина из Твикера работают, тумблер
синхронизации переключается. Найдены три расхождения, два из них — один и тот же пропуск.

**1. Предложение «Загрузить сейчас» никогда не появлялось** (матрица 8 и 9). Установка плагина при запущенной
игре клала файлы в `channels\` и на этом заканчивалась: ни «Загрузить сейчас», ни «Перезапустить игру». Сценарий
с пропавшим `InjectHelper.exe` из-за этого был непроверяем — до него просто не доходило.

Причина: `ConnectAsync` запускалась **только** по событию `Registered`, то есть один раз за сессию игры. К
моменту установки игра уже зарегистрировалась, второго `Registered` не будет, и весь ответ на вопрос «есть ли
плагин в процессе» оставался замороженным на состоянии «не установлен», каким он был при подключении. §6.4
описывает вторую половину сценария («файлы кладутся сразу, дальше — предложение загрузить в текущую сессию»),
но её нечем было запустить.

Исправлено: `OverlayHelper.Reevaluate()` — повторный прогон потока подключения против уже зарегистрированной
игры. Зовётся из `PluginService.InstallAsync` после успешной установки и при включении тумблера синхронизации.
Плюс `ForgetLoadOffer()` — снятие защиты «спрашиваем один раз на PID игры» при удалении плагина: удаление
отвечает на тот вопрос, который задавало предложение, поэтому повторная установка в той же сессии — новый
вопрос, а не повтор старого.

**2. Тумблер синхронизации не действовал на уже поднятую связь.** `OnIsOverlaySyncEnabledChanged` только писал
настройку; проверялась она в `OnRegistered`, то есть выключение вступало в силу со следующего запуска игры. Пока
связь жива, плагин продолжал видеть окно моста: вкладка Player и обратная синхронизация работали, переставало
обновляться только то, что хост пушит сам.

Исправлено: выключение зовёт `Disconnect()` (`HOST_DISCONNECT` + сброс состояния), включение — `Reevaluate()`.
Теперь выключенный тумблер означает ровно то, что написано: плагин уходит в оффлайн, вкладки Skins, Tweaks и
Player становятся заглушками, появляется пин Offline — то же состояние, что при закрытом Твикере (Ф3).

**3. Название тумблера обещало не то.** «Sync the overlay with Tweaker» живой человек, впервые увидевший
программу, прочитал как «разрешить оверлею управлять Твикером» и ожидал, что выключение отрубит вкладки твиков,
скинчейнжера и плеера целиком. Ожидание было правильным — расходилось поведение (пункт 2), а не ожидание.
Исправив поведение, заодно поправили и формулировку: «Connect the in-game overlay to Tweaker», подсказка —
«Off disconnects the overlay from Tweaker right away: skyboxes and scripts keep running in the game, but the
overlay's Skins, Tweaks and Player tabs go offline». Строка статуса §6.6 для этого случая теперь
«not connected to Tweaker (overlay runs offline)» вместо «syncing with Tweaker is off».

Проверка: `dotnet build TweakerUI` чисто, `TweakerCore.Tests` 36/36.

**Повторный прогон на игре после правок (22.09.2026) — принято.** Диалог при живой игре предлагает все три

#### Ф6: результаты (22.09.2026)

Оба оставшихся пункта закрыты, оба — не так, как было записано в плане.

- **`TWEAKER_DEPLOY_ENGINE_DIR` — отменена решением владельца.** Смысл опции был в том, чтобы POST_BUILD сам
  раскладывал свежую сборку в живую папку игры. Отказ: «не хочу разбираться, где действительно мои скрипты и
  скайбоксы, а где деплой из среды разработки решил похозяйничать». Возражение принято — папка игры содержит
  пользовательские файлы, а автоматика, которая туда пишет при каждой сборке, ровно этим и опасна. Ручной
  цикл (положить DLL в `channels\` самому, остальное через тумблер установки) остаётся единственным.
- **POST_BUILD не перенесён, а удалён.** План предлагал копировать `assets/scripts` в
  `$<TARGET_FILE_DIR>/TweakerStuff/Scripts` вместо `scripts`. Выяснилось, что копию не читает **никто**: с Ф1
  плагин берёт пути от `QuestViewer.exe`, то есть скрипты — из `engine\TweakerStuff\Scripts\`; харнессы читают
  `assets/scripts` прямо из дерева исходников; smoke-тест Lua не трогает; в бандл поставку собирает
  `CopyTweakerPlugin`. Правило появилось, когда DLL инжектилась из папки TweakerUI и скрипты действительно
  лежали рядом с ней. Перенос сохранил бы мёртвый вывод, а вторая папка `.lua` рядом с DLL, молча устаревающая,
  — готовый вопрос «а какая из них настоящая».

**Найдено сквозной проверкой (прогон `Deploy.sh` целиком):** в бандл уехали dev-скрипты — `arrayprobe`,
`spectrum_calibration`, `vecwrite`. Причина не в отборе (он верный), а в том, что **`PluginPayload\` в `bin\`
только накапливала файлы**: MSBuild `Copy` добавляет и перезаписывает, но никогда не удаляет то, что исчезло
из источника, поэтому все восемь скриптов остались там с прошлых сборок и уехали в бандл, который копирует
папку целиком и ей доверяет. Исправлено `RemoveDir` на `$(OutDir)PluginPayload\TweakerStuff` перед копированием:
чистятся только содержательные поддеревья, `channels\` не трогается — там один файл с фиксированным именем,
устареть таким образом он не может, а перекладывать 9 МБ каждую сборку ради этого незачем.

Заодно: у `.sh`-скриптов не было retry на удаление `distr\`, который есть у `.ps1` (Explorer/Defender держат
хэндл каталога сразу после удаления крупного exe). Прогон на этом и упал — «Device or resource busy». Добавлен
в оба `.sh`.

Проверка: `Deploy.sh` прогнан целиком дважды подряд. Бандл — 21 файл: `TweakerUI.exe`, `asbridge.exe`,
`InjectHelper.exe`, `LegacyDataConverter.exe` и `PluginPayload\` из DLL в `channels\`, пяти поставляемых
скриптов и двух пакетов неба со всей внутренней структурой. Мёртвой папки `scripts\` в бандле больше нет.
Установка из бандла на чистую копию игры — за владельцем.

  загрузке и установке, значило бы смешать два разных проекта.

  Поэтому здесь этот пункт остаётся **только как запись симптома и его причины**, а сама работа выносится за

## 10. Риски

- **Краш плагина теперь крашит игру и без TweakerUI.** Раньше достаточно было не включать оверлей. Меры:
  `DISABLE` (Р-17), удаление плагина из хоста, лог жизненного цикла (Р-18).
- **Код под loader lock.** `DllMain` и обработчик уведомлений — источник взаимоблокировок (ревизия 2 пробы
  повесила игру). Меры: правила §4.2, `loader_watch` без логов и ожиданий внутри, ревью каждого подписчика.
- **Патч без приостановки потоков** безопасен, только пока целевой код действительно никто не выполняет.
  Для экспортов загружаемого модуля это гарантировано; для `CallChannel` в `DllMain` — по наблюдению (перебор
  каналов идёт до загрузки групп). Если окажется иначе — детур `CallChannel` переезжает в поток запуска.
  Для цепочек D3D9/DirectInput гарантия держится на том, что экспорты перехвачены до первого вызова. Её ломает
  только объект, созданный в обход экспорта: `CoCreateInstance(CLSID_DirectInput8)` или устройство, созданное до
  загрузки плагина. Ни того, ни другого в Ф0 не видели.
- **Закрепление модулей игры (Р-25)** меняет их жизненный цикл: `DllMain` у `d3d9` и Texture-канала
  выполняется один раз вместо загрузки–выгрузки–загрузки. Проверено ревизией 4 пробы: игра работает как
  обычно. Кроме того, MSDN не рекомендует звать загрузчик из обработчика
  уведомления; вызов идёт на потоке, уже держащем loader lock, и лишь добавляет ссылку на загруженный модуль.
- **`g_ready` позже первых текстур.** Небо, загруженное до готовности подсистем, не опознаётся до перезагрузки
  текстур. Мера: скайбокс регистрируется первым, длительность этапа 1 меряется (Ф2, матрица п. 17).
- **Новый код хуков DirectInput** (Р-24) заново проверяется с вводом игры: матрица п. 18.
- **Скан при каждом старте** подтверждён статически и стеком загрузки в Ф0. При PIN
  `DllMain(PROCESS_ATTACH)` приходит один раз за сессию.
- **Код завершения не выполняется**: `DLL_PROCESS_DETACH` при выходе из игры в Ф0 не пришёл ни разу.
  Всё сохраняемое пишется в момент изменения.
- **Антивирус и DLL в папке игры.** Неподписанная DLL в `channels\` тоже может сработать, но реже, чем
  инжектор. Подпись кода — вне этого плана.
- **Проверка целостности Steam** не удаляет лишние файлы, но может вернуть `channels.lst`. На плагин это не
  влияет.
- **Хост с не заданным или неверным `GameTexturesPath`** не может установить плагин. Статус «Не установлен»
  плюс ссылка на Settings, как у Skin Changer.
- **`steam://` при установленном Steam, но не-Steam копии игры**: Steam откроется с ошибкой владения, а
  хост об этом не узнает. Принимается как есть.

## Приложение А. Ручной перенос живых установок разработчика

Выполняется один раз, после Ф1–Ф2, при закрытой игре. Tweaker этого не умеет и уметь не будет (Р-8).

Источники:

- `T` = `C:\Users\Unchp\Desktop\TweakerUI nonstable`
- `E` = `D:\SteamLibrary\steamapps\common\Audiosurf\engine`

```powershell
$T = 'C:\Users\Unchp\Desktop\TweakerUI nonstable'
$E = 'D:\SteamLibrary\steamapps\common\Audiosurf\engine'
$S = "$E\TweakerStuff"
$R = "$S\SkyboxReplacer"

New-Item -ItemType Directory -Force "$S\Config","$R\Skyboxes","$R\SkyConfigs","$S\Scripts","$S\Logs" | Out-Null

# Небеса
Move-Item "$E\skyboxes\*" "$R\Skyboxes\"
Remove-Item "$E\skyboxes"

# Настройки небес (.bak - по желанию)
Move-Item "$T\Skies\*.json" "$R\SkyConfigs\"

# Скрипты и их тумблеры
Move-Item "$T\scripts\*" "$S\Scripts\"
Move-Item "$T\TweakerScripts.cfg" "$S\Config\scripts.cfg"

# Оверлей
Move-Item "$T\TweakerPlugin.overlay.cfg" "$S\Config\overlay.cfg"

# Плагин - после Ф2 (ранняя загрузка). Пока хост не переведён на новую схему (Ф5), копия в папке TweakerUI
# ему ещё нужна: он инжектит её, а при DLL в channels\ инжектированная копия остаётся инертной.
# Copy-Item "$T\TweakerPlugin.dll" "$E\channels\"
```

`TweakerPlugin.skybox.cfg` не переносится: из него вручную пишется `$R\module.json`. Для текущего
содержимого файла (`sky_program=...\engine\skyboxes\ODC_VolTex.sky`, остальное по умолчанию):

```json
{
  "enabled": true,
  "sky": { "kind": "package", "id": "ODC_VolTex.sky" },
  "cubemap": { "hdr_exposure": 1.0, "min_face_size": 0 },
  "orientation": { "yaw_degrees": 0.0, "pitch_degrees": 0.0, "z_up": false },
  "shader": { "quality": 100 }
}
```

После этого старый `TweakerPlugin.skybox.cfg` удаляется. Оба живых пакета (`ODC_VolTex.sky`,
`OurDraftsCollides.sky`) — папки, `kind` у них `package`; три `.hlsl` из бывшего `skyboxes\` выбираются как
`shader_file`. Скрипты, совпадающие с поставкой, первая установка из TweakerUI просто внесёт в манифест
(§6.3, строка «хеш = поставке»).
