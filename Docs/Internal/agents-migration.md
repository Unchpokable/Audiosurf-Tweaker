# Переезд инструкций агентов с Claude Code на общий формат

Дата аудита и уточнений владельца: **31.10.2026**. Статус: **выполнение разрешено владельцем; результаты реализации и приёмки фиксируются в §10**. Исходные предложения ниже сохраняют историю проекта; фактическое выполнение сверять с §10.

Корневой `AGENTS.md` станет короткой общей точкой входа. Все нормативные документы, на которые он непосредственно ссылается, размещаются в **`Docs/AgentWorkflow/`** — по решению владельца. `Docs/Internal/` остаётся местом внутренних планов, журналов, истории и этого аудита. Настройки конкретных клиентов и машины держатся отдельно. Память Claude нужно разобрать по смыслу, сохранив решения владельца и происхождение фактов. Простое переименование нынешнего `CLAUDE.md` проблему не решит: получится тот же большой, противоречивый документ под новым именем.

Также нельзя потерять CgrPy, локальные харнессы, UiStand и резервный путь Ghidra, часть которого сейчас находится внутри `.claude`.

## 3. Что мешает сейчас

### 3.1. Слишком большая общая инструкция

В одном автоматически читаемом файле находятся вводная, карта десятков документов, подробная карта C++-файлов, команды, история решений, изменчивые статусы и пересказ конфигурации форматтера. Например, карта `src/*` занимает строки 440–644, а правила стиля — значительную часть строк 711–908 [корневого файла][root]. Это полезный справочный материал, но он нужен по теме задачи, а не целиком при каждом старте.

Для Codex это также техническая проблема: по [официальной OpenAI documentation об AGENTS.md][oa-agents] стандартный общий лимит проектных инструкций — 32 КиБ; `CLAUDE.md` не входит в стандартный набор имён без настройки fallback. Поэтому ни сохранение только старого имени, ни буквальное копирование 100 КБ в `AGENTS.md` не дают надёжной точки входа.

Предлагаемый бюджет корневого `AGENTS.md` — **6–10 КиБ**, ориентировочно до 150 строк. Это наш проектный ориентир, а не ограничение платформы. В нём должны остаться обязательные правила и ссылки с условиями чтения. Увеличение лимита клиента не заменяет редактирование документа.

### 3.2. Решения и статусы живут в нескольких местах

`MEMORY.md`, `audiosurf-phase-workflow.md`, специальные файлы памяти, корневой `CLAUDE.md` и шапки планов повторяют одни и те же состояния. Их даты и содержание расходятся. Часть памяти уже сама говорит «смотрите текущую шапку плана» — это правильное направление, но рядом продолжает хранить длинную копию шапки.

Особенно опасны старые повелительные фразы: ожидание приёмки конкретного бага может остановить любую новую задачу; «ничего не закоммичено» может восприниматься как актуальная инструкция; «это не ошибка» — скрыть новое падение харнесса. Конкретные элементы для исключения из действующих правил перечислены в §5, противоречия — в §6.

### 3.3. Часть общей памяти существует только на этой машине

[`TweakerPlugin/harness` и `Temp/` исключены из Git][ignore], память — в профиле Claude, IDA — в пользовательском кеше плагинов, Ghidra-экспортёр — в `.claude/skills`. Новый агент или новый клон не получают всё необходимое из репозитория.

Владелец решил сохранить **весь harness в отдельном приватном Git-репозитории**, подключённом к проекту как субрепозиторий; реализация уже запланирована им отдельно (Q10). Это не разрешение публиковать его в основном репозитории. Для игры, исследовательских баз, профиля Claude и остальных локальных зависимостей нужен отдельный реестр хранения и восстановления; переносить их в публичный Git автоматически нельзя.

### 3.4. Рабочие процедуры привязаны к оболочке и названиям инструментов Claude

В памяти встречаются `Edit`, `Write`, `Read`, scratchpad, `cmd //c` и особенности Git Bash. Часть наблюдений применима шире — например, сохранение CRLF, подготовка vcvarsall и проверка типа сборки. Часть описывает конкретную цепочку передачи текста старым агентом.

Общая инструкция должна задавать результат: сохранять байты и окончания строк, безопасно передавать пути, проверять diff. Инструкции для PowerShell, cmd и Git Bash нужно документировать отдельно. Здесь текущая оболочка — PowerShell; Git Bash при этом остаётся полноценным рабочим окружением владельца, а не объявляется устаревшим.

## 5. Что исключить из действующих инструкций: конкретные цитаты

«Исключить» здесь означает не переносить в постоянные правила. Исторический факт, полезный для расследования, можно оставить в датированном архиве. Перемещение подробностей отдельно от корня также не означает потерю самого требования.

### D1. Обращение исключительно к Claude Code

> This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Источник: [CLAUDE.md:3][root]. Эта фраза не задаёт норм разработки. В общем AGENTS её заменить на область действия — весь репозиторий. Имя клиента оставить только в тонком адаптере CLAUDE, если Claude продолжит использоваться.

### D2. Обязательное ожидание старого бага перед любой работой

> wait for the owner's verdict on item 10 before starting anything else

Источник: [tweakerui-knownbugs-progress.md:18][m-ui-progress]. Фраза относится к старому разбору и буквально запрещает даже текущую новую задачу. Убрать её из рабочего процесса. По решению Q7 KnownBugs — личный блокнот владельца: агент не ведёт его статусы и не рассматривает его пункты как свою очередь работы без отдельного поручения.

### D3. Гарантия, что красный harness всегда безобиден

> harness run.bat always prints "FAILED: lua/ljtest lua/shimtest"

Источник: [plugin-offline-mode-plan.md:17][m-offline]. Слово `always` и отнесение этого к «не ошибкам» опасны: агент может пропустить новое падение. В действующий справочник переносить только датированный диагностический случай с ожидаемым выводом, кодом возврата и способом отличить дефект runner от сбоя теста. Автоматического разрешения игнорировать красный результат быть не должно; актуальность проблемы — Q10.

### D4. Исторический снимок индекса Git как текущее состояние

> **Состояние рабочей копии:** ничего не закоммичено, коммиты владелец режет сам. В индексе только две записи Ф1

Источник: [dev-bundle-roadmap.md:17–18][bundle]. В начале этого аудита дерево и индекс были чистыми; это уже не описание текущей копии. Снять такой блок с роли текущего состояния, оставив при необходимости датированную историю. Частью общей Git-политики его считать нельзя — Q1.

### D5. Универсальное «свойство Bash», выведенное из старого сбоя агента

> `cat > f <<'EOF'` does *not* keep the source literal here

> a heredoc much past ~200 lines gets truncated mid-file

Источник: [tweakerplugin-build-and-check.md:34–39][m-build]. Формулировки описывают прежнее окружение передачи текста и не устанавливают общий предел Bash или Codex. Не переносить их как запрет на синтаксис. ## 6. Решения владельца по Q1–Q12

Все двенадцать вопросов получили ответ владельца 31.10.2026. Исторические расхождения оставлены с источниками, чтобы было понятно, какие прежние формулировки заменить. Действующие решения ниже имеют приоритет над этими цитатами. Детали, которые предстоит проверить инструментально при реализации, не означают повторного согласования уже принятых правил.

### Q1. Кто коммитит, может ли агент менять локальную историю, как указывать авторство?

- [CLAUDE.md:357–358][root]: «**Агент коммитит сам**, закончив логический шаг».
- [tweakerui-knownbugs-progress.md:15][m-ui-progress]: «Nothing committed by me - **the owner commits**»; [audiosurf-phase-workflow.md:15][m-workflow] и [dev-bundle-roadmap.md:17][bundle] также отдают нарезку владельцу.
- [CLAUDE.md:376][root] разрешает свободные amend/fixup/rebase до push; строка 386 требует `Co-Authored-By`, но не определяет значение для Codex.

**Решение владельца:** коммит делает агент **после подтверждения владельцем, что фича реализована и работает, и после Code Review владельца**. Автокоммиты после каждого логического шага отменяются. Базовая ветка — `Revive`; **каждая новая фича начинается в новой ветке**. Исключение — работы, уже начатые в `Revive`: переносить их в отдельные ветки задним числом не требуется. Инструменты — Git CLI и при необходимости GitHub CLI (`gh`).

Push/release по-прежнему требуют команды владельца. Значение `Co-Authored-By` для Codex и отдельное разрешение переписывать историю этим ответом не определены: не придумывать attribution и не переносить прежнее «локальная история правится свободно» как новое общее разрешение. Эти детали не блокируют подготовку документов.

### Q2. Что разрешено устанавливать в рабочую игру?

- [plugin-offline-mode-plan.md:13][m-offline]: «**no automation may write into the live game folder**».
- Более поздняя [audiosurf-phase-workflow.md:17][m-workflow]: «install the script there with `twllink --install`, **never the plugin** — the owner deploys plugin builds».

**Решение владельца:** в реальную Steam-установку можно устанавливать **скрипты и скайбоксы**, если их там прежде не было, либо после явного разрешения или прямой просьбы владельца. Перед записью проверить наличие целевого материала; существующее без соответствующего разрешения не перезаписывать. Это правило относится ко всем таким материалам, а не только к PuzzlePRO HUD. Разрешение не распространяется на автоматическую установку DLL плагина: его развёртывание остаётся за владельцем. Исследовательскую копию, рабочую игру и установку Tweaker описывать отдельно.

### Q3. Можно ли по-прежнему перезаписывать любые существующие базы IDA?

- [game-copy-is-mine.md:11][m-game]: базы «**old and empty or junk**», разрешены изменения и работа без копий.
- [CLAUDE.md:137–142][root] требует накапливать понимание через rename/comments/types и сохранять базы.

**Решение владельца:** `Audiosurf_Steam/` — исследовательская копия. Базы IDA в ней уже могут содержать актуальные и корректные результаты нескольких крупных работ Claude. Указание «пустые или мусор» **неактуально и удаляется из действующих инструкций**. Работать с существующими базами и сохранять накопленные знания; не выводить разрешение уничтожать/пересоздавать их из прежней характеристики копии. Для приёмочного теста использовать выделенную тестовую базу, сохраняя исследовательские базы.

### Q4. Как точно сформулировать правило syscalls и синхронизации?

- [render-thread-syscall-rule.md:11–15][m-render] запрещает syscalls в покадровых путях и заканчивается «**atomics only**».
- [CLAUDE.md:427–429][root] разрешает инициализацию на том же потоке; строки 590–592 описывают спин-лок; строки 490 и 745 упоминают try_lock и минимизацию блокировок.
- Поздний [script-tabs-roadmap.md:714][tabs-old] описывает первое обращение к хранилищу после загрузки как один системный вызов.

**Решение владельца:** в TweakerPlugin запрещено **покадрово донимать систему тяжёлыми системными вызовами или I/O-bound нагрузкой**. Это не blanket-запрет всех системных вызовов и не правило «только атомики». Загрузку файлов и тяжёлые фоновые задачи, например компиляцию шейдеров, выполнять через **`plugin::bg_work`**, покадрово проверяя готовность результата без блокирующего ожидания в кадре.

Игровой **WndProc/IPC работает синхронно в движке**: `EngineLoop` сначала выполняет `pump()` всех сообщений, затем синхронно просчитывает граф объектов. В новой документации нельзя оправдывать тяжёлую работу из обработчика сообщения тем, что она якобы идёт на независимом IPC-потоке. Устаревшие описания потоков сверить с этим порядком при переносе процедур.

### Q5. Какую архитектурную вводную считать действующей?

- [CLAUDE.md:9–10][root]: управление «снаружи … **не встраиваясь в неё как библиотека**».
- Там же [строки 223–225, 412–434][root]: внутриигровой DLL-плагин, работающий и без хоста.
- [overview.md:5, 19, 24][overview] одновременно описывает внешнее управление как единственный способ и плагин как «тонкий клиент»; при этом заявляет 9 проектов, а CLAUDE — 11. В текущей `.sln` действительно 11 записей проектов.

**Решение владельца:** актуальная архитектура — **три приложения/компонента исполнения**:

| Компонент | Назначение |
|---|---|
| **TweakerUI** | Внешний клиент на .NET/AvaloniaUI. |
| **asbridge** | 32-битный мост для IPC через WndProc. |
| **TweakerPlugin** | Внедряемый модуль, активно вмешивающийся в работу игры и управляющий ею, в том числе через встроенный Lua-движок. Имеет механизмы синхронизации с хост-приложением, но **не является тонким клиентом**. |

**Installer** — устаревший артефакт, подлежащий удалению отдельной работой; не включать его в целевую архитектуру. **LegacyDataConverter** — обязательный инструмент совместимости (Q11), а не устаревший модуль для удаления. Счёт проектов `.sln` не заменяет это описание трёх исполняемых частей. В этой документационной задаче Installer не удаляется.

### Q6. Какая команда является базовой проверкой сборки?

- [CLAUDE.md:261][root] предлагает `dotnet build "Audiosurf SkinChanger.sln"` как сборку всей managed-стороны.
- Там же [строки 266–268][root] и [память offline:17][m-offline] говорят, что LegacyDataConverter/Installer требуют полного MSBuild.
- [`.vscode/tasks.json`][vscode-tasks] также запускает dotnet build/publish на `.sln`; [launch.json][vscode-launch] указывает несуществующий в корне каталог `AudiosurfTweaker` вместо текущего `TweakerUI`.
- [`.github/workflows/build.yml`][ci] реагирует на push в `master`, тогда как корневые правила и текущая ветка указывают `Revive`. Workflow описывает Sonar-анализ и MSBuild, но не запускает перечисленные NUnit/нативные проверки. Его нельзя считать подтверждением всего набора проверок агента.

**Решение владельца:** для **полного билда эталонны действующие скрипты Deploy** и выполняемая ими последовательность. Для локальной проверки новых модулей TweakerUI и его компонентов подходят `dotnet build` / `dotnet run` по соответствующему проекту. Не выдавать `dotnet build` всей `.sln` за эквивалент Deploy.

Матрицу команд в `Docs/AgentWorkflow/development.md` составить по скриптам Deploy, сохранив парные `.ps1`/`.sh`; локальные нативные проверки описать отдельно. Плагин best-effort при сборке UI не даёт права считать его проверенным без отдельного подтверждения. **GitHub workflow устарел и требует отдельного аудита**: не использовать его как нормативный процесс сборки. Исправление CI и IDE-задач не входит в текущую документационную задачу.

### Q8. Как архивировать старые планы и сохранять ссылки?

### Q9. Что делать с несовпадением стиля, примеров и версии formatter?

- [CLAUDE.md:822–833][root] объявляет конфигурацию источником истины и требует `{` у class на той же строке.
- Пример в [строках 864–866][root] ставит `{` класса на следующую строку; [`.clang-format:31`][clang-format] содержит `AfterClass: false`.
- [tweakerplugin-build-and-check.md:50–70][m-build] советует установленным formatter только смотреть diff и следовать окружению, поскольку версия инструмента расходится с прежним форматированием дерева.
- `.clang-format` требует CRLF, а `.gitattributes` явно фиксирует окончания только у двух запускалок CgrPy, оставляя остальное на `text=auto`.

**Решение владельца:** **`.clang-format` — источник правды, EOL — CRLF, язык проекта — C++23, не C++20**. Следование случайному окружающему форматированию или старому примеру не должно перекрывать конфигурацию. При переносе примеров привести их к конфигурации; массовое форматирование кода не является частью миграции инструкций.

Найденный `Standard: c++20` в настройках formatter сохранить в аудите как фактический старый параметр, но не как версию языка проекта. При будущей проверке конфигурации подобрать поддерживаемое установленным clang-format обозначение нужного стандарта; это не повод понизить стандарт компиляции. Конкретная версия formatter ещё подлежит технической проверке, без повторного вопроса о C++23/CRLF.

### Q10. Какие локальные проверки должны стать воспроизводимыми из клона?

[CLAUDE.md:679–709][root] требует harness, но [`.gitignore:12`][ignore] исключает его целиком, включая `vcenv.bat`. Память [harness-not-in-repo.md:14–17][m-harness] предполагает причину, а [CLAUDE.md:393–395][root] уже объясняет её историей разовых проб и допускает предложение вернуть стабильные сюиты. Дополнительно память требует игнорировать конкретный FAILED, не подтверждённый прогоном сейчас.

**Решение владельца:** **сохранить весь harness**, а не отобранные стабильные сюиты. Он будет оформлен как **отдельный Git-субрепозиторий с приватным доступом**; у владельца уже есть план этой работы. Сейчас только зафиксировать зависимость и предстоящий способ хранения. Не создавать репозиторий, не публиковать файлы, не менять `.gitignore` и не выбирать механизм подключения вместо владельца.

После реализации отдельного плана описать получение доступа и восстановление harness в `Docs/AgentWorkflow/development.md`. До этого недоступность проверки новому клону отмечать явно. Актуальность старого дефекта runner проверить при работе с harness; красный результат не игнорировать автоматически. Тесты в этом аудите не запускались.

### Q11. Сохраняются ли временные ограничения unreleased-проекта?

[plugin-offline-mode-plan.md:15][m-offline] запрещает обратную совместимость и автоматические миграции, кроме LegacyDataConverter. Это важное решение владельца, но оно завязано на состояние «project is unreleased» и не отражено как отдельная датированная политика верхнего уровня.

**Решение владельца:** старая опубликованная версия Tweaker содержит **только Skin Changer**. Поэтому **LegacyDataConverter обязателен**, а каждое изменение формата скинов должно сохранять перенос данных из старого формата, который читает LegacyDataConverter. Общее правило «проект не в релизе, совместимости нет» неверно и не переносится.

**Скрипты и скайбоксы ещё не в релизе:** breaking changes в них не требуют никакой обратной совместимости. В `project-principles.md` разделить эти две области явно; в проверках изменения формата скинов предусмотреть путь конвертации из legacy-формата. Не распространять свободу breaking changes скриптов/неба на Skin Changer.

### Q12. Как принимать IDA MCP и где хранить независимую установку?

Локально найден прежний сторонний пакет и его Codex-адаптер (§8), но реальное соединение Codex → idalib не проверено. Установочный реестр содержит revision, тогда как имя каталога кеша не гарантирует неизменность всех его файлов.

**Решение владельца:** **личная установка стороннего IDA MCP вне кеша Claude**. Сохранить рабочий сервер mrexodia для **IDA Pro 9.3**; переход на Hex-Rays MCP сейчас невозможен, поскольку обновление IDA до 9.4 недоступно. Нативный Codex-адаптер в старом пакете — полезный справочный материал, но новое рабочее подключение не должно зависеть от кеша Claude.

Точный личный каталог выбрать при реализации, зафиксировать рабочий снимок и зависимости, подключить Codex и выполнить §8.3. Это технический этап, а не новый выбор между уже рассмотренными вариантами. Без успешной приёмки IDA нельзя закрывать всю миграцию.

Корневой AGENTS — переносимый текст, но не обещание автоматической поддержки каждым AI-клиентом. Для Codex это штатная точка входа; другие клиенты должны получить собственный проверенный механизм чтения того же текста. Не нужно создавать вложенные AGENTS или копировать скиллы AgentKit в корень в рамках этого этапа. Такие изменения потребуют отдельного аудита их области действия. Проектные skills можно выделить позже, если для повторяемой процедуры действительно нужны вспомогательные материалы; ядро инструкций не должно зависеть от marketplace или конкретного набора встроенных инструментов.

### Где хранить состояние и локальные данные

- **Правило:** что делать и почему; хранится один раз в `Docs/AgentWorkflow/`, обязательный минимум — в корневом AGENTS.
- **Факт реверса:** бинарь/группа, адрес или индекс, команда/метод, результат, статус доказательства; хранится в журнале `Docs/Internal/`.
- **Состояние работы:** сделано, проверено офлайн, ожидает владельца, следующий разрешённый шаг; хранится в документе этой работы в `Docs/Internal/`. Личный KnownBugs к таким документам агента не относится.
- **Локальное окружение:** реальные пути игры/SDK/IDA/Ghidra и текущие установки инструментов; локальный файл, явно исключённый из Git, плюс переносимый шаблон. Точное место выбрать при реализации; не рассчитывать на автоматическую загрузку произвольного имени `AGENTS.local.md`.
- **Конфигурация клиента:** команды MCP и профиль клиента; вне общей смысловой инструкции. Наличие записи не равно успешному подключению.

Карта документации не дублирует живые статусы. При новом противоречии источников агент записывает обе ссылки и вопрос владельцу; не выбирает победителя только по дате файла. Уже разрешённые Q1–Q12 не задаются повторно из-за найденной старой цитаты. Текущий запрос владельца определяет задачу и может уточнять старую договорённость; ограничения среды и разрешения инструментов остаются действующими.

### 8.2. Предлагаемый перенос

1. Зафиксировать рабочий пакет: revision из реестра + снимок фактических файлов, lock и профиль инструментов. Сохранить зависимости/способ восстановления, не копируя лицензию IDA в репозиторий. Не запускать обновление «до latest» одновременно с миграцией клиента.
2. Подготовить **личную установку вне кеша Claude**, как выбрал владелец. Поставляемый Codex-адаптер использовать как справочный образец, не как причину оставлять зависимость от кеша. Старую установку оставить до приёмки. Не использовать команды удаления/переустановки из README как обязательный шаг переноса.
3. Описать сервер, cwd, зависимости, активацию и параметры `IDA_MCP_*` в `Docs/AgentWorkflow/reverse-engineering-tools.md`/локальном профиле. `CLAUDE_PLUGIN_ROOT` заменить на явно определённый путь нового окружения; сам символ не является переносимой переменной Codex.
4. Подключить к Codex и выполнить приёмку ниже. Только после неё убирать зависимость от кеша Claude. **Существующие исследовательские базы сохранять по Q3**: тестировать запись на выделенной базе, не пересоздавать накопленные базы ради настройки клиента.

По [официальной OpenAI documentation MCP][oa-mcp], Codex поддерживает STDIO-серверы и конфигурацию `[mcp_servers.<name>]` в `config.toml`, включая command, args, cwd и env. Для выбранной владельцем независимой личной установки **пример прямого подключения** выглядит так:

```toml
# Пример для будущей настройки. Здесь ничего не применено.
# Путь заменить на зафиксированную независимую установку.
[mcp_servers.idalib]
command = "uv"
args = ["run", "--locked", "--project", "C:/Tools/ida-pro-mcp", "idalib-mcp", "--stdio"]
cwd = "C:/Tools/ida-pro-mcp"
```

`--locked` — предложенная защита lock, а не часть прежней команды. Исполнимость примера, наличие `uv` в окружении клиента, таймаут и права на локальные базы нужно проверить на машине. Путь `C:/Tools/ida-pro-mcp` — **пример, такого переноса сейчас не сделано**. Конфигурацию с реальными личными путями хранить в пользовательском профиле, а в `Docs/AgentWorkflow/` — инструкцию и шаблон. Не регистрировать одновременно второй такой же сервер через плагин.

### 8.3. Приёмка IDA MCP

| Проверка | Что считается успехом |
|---|---|
| Обнаружение | В новой сессии Codex видны инструменты `idalib`; понятно, каким пакетом и командой запущен сервер. |
| Открытие | Открывается выбранная экспериментальная база/бинарь из `Audiosurf_Steam/`; рабочая игра не используется. |
| Нативный код | Декомпиляция известной x86-функции, xrefs и поиск работают; x64 отдельно проверить, если нужен как сохранённая возможность прежней установки. |
| Данные | `get_int`/`read_struct` либо эквиваленты реально читают известную таблицу/vtable. Одной декомпиляции недостаточно. |
| База знаний | В выделенной тестовой базе выполнить rename/comment/type, закрыть с сохранением, переоткрыть и увидеть изменения. Рабочие исследовательские аннотации не стирать ради теста. |
| Жизненный цикл | После закрытия освобождена база/сеанс; понятно, как закрывать зависший worker и не потерять сохранённое. Проверить актуальную семантику `idb_close` по схеме инструментов. |
| Воспроизводимость | Задокументированы пакет/отпечаток, Python, idapro, запуск и способ повторного подключения без CLI/кеша Claude. |

При отсутствии IDA допускается продолжать подходящее исследование CgrPy/Ghidra с явным указанием ограничения. Это резервный режим, **не основание объявлять перенос IDA выполненным**. Предупреждение об ICF и единственном имени IDA на склеенном адресе сохранить [из CLAUDE.md:142–144][root].

### Проверки качества результата

- Каждому существенному правилу из корня и 14 тематических записей памяти назначено место или явное решение владельца; удалённые элементы имеют цитату и причину.
- Прямые ссылки корневого AGENTS на нормативные документы ведут в `Docs/AgentWorkflow/`. В `Docs/Internal/` не добавлены новые общие workflow-руководства; внутренние планы и журналы доступны адресно через карту документации.
- Ссылки на существующие файлы/разделы работают; при переносе сохранены важные `§N` либо составлен полный список обновлений. Новые ссылки не ведут в JSONL или персональные кеши за нормативным содержанием.
- Корневой AGENTS помещается в выбранный бюджет. Для новой сессии проверены реальные источники инструкций; вложенный файл не выдаётся за инструкцию всего репозитория. Не рассчитывать, что обычная Markdown-ссылка автоматически импортирует весь документ.
- На примерах «изменить `tw.*`», «исправить Avalonia UI», «исследовать канал» агент выбирает правильные документы и проверки, не читает весь архив подряд. В рабочую игру устанавливаются только новые скрипты/скайбоксы либо материалы с явным разрешением/просьбой владельца; существующее без разрешения не заменяется.
- Матрица сборки берёт полный билд из Deploy, локальный managed-билд — из соответствующего dotnet-проекта, отдельно описывает Ninja x86 и best-effort сборку плагина. Устаревший GitHub workflow не выдаётся за действующий эталон. Skipped-тесты/отсутствующий приватный harness не записываются как полный успех.
- Сохраняются парные shell-процедуры, CRLF и C++23; `.clang-format` имеет приоритет над старыми примерами. UTF-8/русский текст и пути с пробелами проверены на чтение в PowerShell; массовой смены окончаний строк нет.
- Правила TweakerPlugin используют `plugin::bg_work` для тяжёлой работы, описывают покадровую проверку готовности и синхронный порядок pump → расчёт графа. Нет предположения, что игровой WndProc/IPC вынесен на независимый поток.
- Совместимость разделена: LegacyDataConverter обязателен, изменения формата скинов сохраняют перенос из legacy-формата; для скриптов и скайбоксов breaking changes не требуют совместимости.
- IDA MCP проходит §8.3; новый клиент действительно сохраняет и повторно читает аннотации. CgrPy/Ghidra остаются доступными независимо от удаления старого клиента.
- Новая фича начинается в новой ветке от `Revive`, уже начатые в ней работы не переносятся автоматически. Коммит выполняется агентом после подтверждения владельцем работоспособности и его Code Review; push/release — по команде. Личный KnownBugs не создаёт ожиданий приёмки агента.

Для документационной части достаточно проверки diff, ссылок, полноты переноса и загрузки инструкций чистыми сессиями. Сборка приложения сама по себе не проверяет качество инструкций; проверки из матрицы нужны для подтверждения конкретных процедур при их переносе. Полную миграцию закрывать только после приёмки инструментов и фиксации оставшихся вопросов, а не после одного появления `AGENTS.md`.
