## 1. Что сейчас и чего не хватает

Формат закончен и задокументирован, плагин читает обе формы пакета (каталог с `Config.json` и его zip с
расширением `.sky`), горячая перезагрузка работает. Но весь путь автора — руками:

- создать папку, написать `Config.json` и шейдер с нуля по `getting-started.md`;
- положить её в `engine\TweakerStuff\SkyboxReplacer\Skyboxes\` или зазиповать (`Compress-Archive` пишет только
  `.zip` — переименовывать руками, `Skyboxes/README.md`);
- выбрать небо — только в оверлее; TweakerUI про небо не знает ничего. Комментарии `skybox.hxx` и
  `skybox_config.hxx` прямо говорят «не часть `TW_OVL`, не состояние хоста» — это решение план **меняет**, и в
  шапках это надо будет переписать.

Ровно та ситуация, в которой были скрипты до Script Dev: инструменты и документация есть, автоматизации нет.

## 2. Цели и не-цели

**Цели**

1. Проекты пакетов неба: создать по шаблону, открыть папку как проект, переименовать, удалить (в Корзину).
   Рабочие папки — рядом с TweakerUI, `DevTools\SkySources\`.
2. Шаблоны с рабочим содержимым: манифест и простой штатный `.hlsl`, который сразу рисует небо (§5.2).
3. Открыть проект в редакторе — **общий** с Script Dev модуль; отличается только окружение процесса: скайбоксам
   ничего не добавляется в `PATH` (§4.1).
4. Установка одной кнопкой: проверить ссылки манифеста, упаковать zip, положить как `<имя>.sky` в `Skyboxes\`
   игры; «установить и включить»; «устанавливать по сохранению».
5. Управление установленным: список небес игры, выбрать активное, удалить свой пакет, включить/выключить
   реплейсер. Без игры — тоже, через `module.json` (§6.4).
6. Окружение для работы с шейдерами в проекте: копия `sky_common.hlsli` и конфиг HLSL Tools, чтобы `#include`,
   `sky_in`, `g_music*` и прочее резолвились в редакторе (§5.5).
7. Протокол `SKY_*`: включён ли реплейсер, какое небо активно, список доступных, выбрать, включить/выключить,
   пересканировать.

**Не-цели** (решение владельца в постановке задачи)

- Параметры шейдеров, свет, генераторы, разрешение рендера — **только в игре**. Ни одной ручки неба в TweakerUI
  и в протоколе.
- Компиляция HLSL на хосте. Ошибки шейдера — панель диагностики во вкладке Skybox оверлея; хосту — максимум
  одна строка «не загрузилось, вот первая строка причины» (§9, вопрос 3).
- Установка в форме каталога и ссылки (junction) из `Skyboxes\` на папку проекта — см. §8.4.
- Набор для AI-агентов для проектов неба (`AgentKit` — про скрипты). Возможное продолжение, §10.
- Удаление поставляемых небес. Только вместе с парным «вернуть поставляемое на место» — оба в §10.

## 3. Раскладка на диске

### Хост

```
<TweakerUI>\DevTools\
  SkySources\<имя>\            проекты, созданные здесь; папка проекта = каталог пакета (Config.json в корне)
  recent-sky-projects.txt      проекты, открытые откуда угодно ещё (как recent-projects.txt у скриптов)
```

`Core/DevTools` получает два свойства; больше никто раскладку не знает (`script-manager.md` §6).

### Проект

```
My Sky/
  Config.json                  манифест пакета — он же признак проекта
  shaders/sky.hlsl
  scripts/clouds.lua           у шаблона с облаками
  textures/...                 что автор добавит
  README.md                    по желанию, едет в пакет
  shadertoolsconfig.json       конфиг HLSL Tools (§5.5), в пакет НЕ едет
  .tweaker/include/            sky_common.hlsli для редактора (§5.5), в пакет НЕ едет
```

**Отдельного файла проекта нет.** Проект — это папка с `Config.json` в корне, то есть ровно каталожная форма
пакета: её можно положить в `Skyboxes\` руками, и она заработает с горячей перезагрузкой, как сейчас. Второй
манифест рядом с первым был бы вторым источником правды (урок `sky-package.md`).

### Игра

```
engine\TweakerStuff\SkyboxReplacer\
  module.json                  enabled + sky — владелец плагин, без игры правит хост (§6.4)
  Skyboxes\<имя>.sky           установленный пакет — zip, Config.json в корне архива
  SkyConfigs\<имя>.json        настройки игрока; ключ — имя без расширения; хост не трогает
```

## 4. Общий модуль с Script Dev (рефакторинг, без смены поведения)

Сначала вынести из Script Dev то, что нужно обеим вкладкам, и только потом строить вторую. Проверка рефакторинга —
`Tools/UiStand scriptdev` и снимки до/после совпадают попиксельно.

### 4.1 Редакторы

- `TweakerCore/Scripting/ScriptEditors.cs` → `TweakerCore/DevProjects/Editors.cs` (`ProjectEditor`,
  `EditorSearch`, `Editors.Detect`, `Editors.Launch`). Таблица редакторов не меняется.
- `StartInfo(editor, project, file, line, column, EditorEnvironment env)`, где `EditorEnvironment` — список папок в
  начало `PATH` и словарь переменных. Script Dev отдаёт `DevTools.ToolFolders` + `AUDIOSURF_DIR`, вкладка неба —
  **пустое** окружение: процесс редактора наследует окружение Tweaker как есть.
- **Предупреждение «редактор уже запущен» зависит от окружения.** Оно существует только потому, что уже запущенный
  VS Code/Cursor не увидит наш `PATH` (`script-manager.md` §8.3). С пустым окружением видеть нечего — для неба
  предупреждения нет. Условие переезжает из `ScriptEditor.TerminalMissesPathWhenRunning` в вызывающего:
  «окружение непустое **и** редактор держит один процесс с терминалом».
- В TweakerUI — `ViewModels/EditorPickerViewModel` (найденные редакторы, выбранный, запоминание, `_launched`,
  `_warnedRunning`, `OpenAsync(root, file, line, column)`) и `Views/EditorPickerView` — карточка Editor целиком.
  Обе вкладки держат свой экземпляр и показывают его через `ContentControl` (резолвит `ViewLocator`). Поиск — при
  показе вкладки, как сейчас.
- Выбранный редактор — **одна** настройка на обе вкладки (§9, вопрос 5). Ключ `ScriptEditor` в
  `ConfigurationManager.Bindings` оставить как есть, чтобы не потерять выбор владельца.

### 4.2 Наблюдатель «по сохранению»

Из `ScriptDevViewModel` (`Watch`, `Ignored`, `RestartRebuild`, поколение, «изменения во время сборки — одна сборка
после») → `TweakerUI/Core/ProjectWatcher`: папка, список игнорируемых верхних папок, пауза тишины, колбэк
`Func<Task>`. Правила §8.16 сохраняются (`Task.Delay` с поколением, не `DispatcherTimer`; событие «изменилась
папка» не считается). Script Dev игнорирует свой набор папок, небо — служебные (`.git`, `.vscode`, `.vs`, `.idea`,
`.tweaker`) и ничего больше: у пакета нет `build\`.

### 4.3 Список проектов и правка JSON

- `ScriptProjects` → общий `TweakerCore/DevProjects/ProjectList` с параметрами «имя файла-признака» и «папка
  Sources»; `ScriptProjects` и новый `SkyProjects` — тонкие обёртки со своим чтением манифеста. Поведение списка
  (недавние сверху, не больше 20, перечитывание файла на каждом вызове, `IsMissing`, сломанный манифест не прячет
  проект) — общее.
- Правка значений с сохранением текста — из `ProjectManifest.Update/Edit` в `TweakerCore/DevProjects/JsonTextEdit`
  (спаны `Utf8JsonReader`). Для `Config.json` включить комментарии и висячие запятые — плагин читает манифест с
  `YYJSON_READ_ALLOW_COMMENTS | YYJSON_READ_ALLOW_TRAILING_COMMAS`, и поставляемые небеса комментариями
  пользуются вовсю (`manifest.md`: «A manifest is a document»). Перезапись через `JsonNode` их бы стёрла.
- Удаление в Корзину и «открыть папку» — две маленькие общие функции, не копия.

## 5. Модель — `TweakerCore/Skyboxes`

Без UI и без связи с игрой. Всё, что читает файлы игры, читает их **как плагин** — иначе список в TweakerUI
разойдётся с вкладкой оверлея (тот же принцип, что `script-manager.md` §4).

### 5.1 Имя пакета

У проекта неба одно имя, видимое всем, — **имя файла** `<имя>.sky`: его показывает список в оверлее
(`catalog_entry.display_name` у пакета — это stem, а не `name` из манифеста), по нему плагин ключует настройки
игрока (`SkyConfigs\<имя>.json`), его же `getting-started.md` советует давать архиву («Name the zip
`My Sky.sky`»).

Имя файла берётся из поля **`name` в `Config.json`**, а не из имени папки проекта (решение владельца 29.10, «пока
так, дальше посмотрим»). Тогда проект переносим (клон репозитория в папку `my-sky-repo` ставится как
`My Sky.sky`), а форма правки одна. Цена — на `name` ложатся правила имени файла.

- Правила имени — правила `sky_paths::skybox_path` плюс Windows: не пусто, без `\ / : * ? " < > |` и управляющих
  символов, не `.`/`..`, без точки или пробела в конце, не зарезервированное имя устройства (`CON`, `NUL`, …), не
  длиннее 64 символов. Регистр не важен — плагин сравнивает имена на диске без учёта регистра.
- **Переименование — это новое небо**: старый `.sky` в игре остаётся, настройки игрока (ключ — имя) не переезжают.
  Форма правки говорит это до сохранения, как `IdChangeWarning` в Script Dev.
- `version` в манифесте — не semver, а поколение раскладки ручек, и оно входит в ключ настроек
  (`manifest.md`). В форме правки поле есть, с пояснением «поднимать только если вы поменяли смысл ручек — у
  игроков сбросятся настройки».

### 5.2 Шаблоны

Gradient, Music, Clouds и Minimal — пресеты генератора проектов в TweakerUI,
а не заранее существующие устанавливаемые пакеты или элементы каталога игры. В Н1 подготовлены
исходники шаблонов и модель создания проектов; в Н4 добавлен пользовательский путь генерации.
Для проверки пресета сначала нужно создать из него проект на странице Projects и установить его;
самого пакета с названием пресета в поставке по-прежнему нет.

Встроены в `TweakerCore` ресурсами (как шаблоны `twllink --new` — в самом компоновщике): создание проекта — часть
кода, а не файлы, которые могут потеряться из поставки. Исходники — `TweakerCore/Skyboxes/Templates/<шаблон>/`.

| Шаблон | Что внутри | Зачем |
|---|---|---|
| **Gradient** (по умолчанию) | `fullsky`-слой, `shaders/sky.hlsl`: градиент зенит → горизонт → земля и диск солнца от `lights.primary`; свет `primary` с bearing/elevation/color/intensity; ручки цветов и размера диска в `params` | рабочее небо, в котором видны все три механизма манифеста: свет, привязки, ручки |
| **Music** | Gradient + реакция на `g_music.y` / `g_music_slow` (`c208`, `c211`) с ручкой силы | показать регистры движка (`music.md`), чтобы автору не пришлось начинать с них |
| **Clouds** | Gradient + слой `sprites` со встроенной парой шейдеров, `scripts/clouds.lua` с `place()` и встроенной заливкой | геометрический слой — самое сложное место формата, `clouds.md` |
| **Minimal** | ровно пакет из `getting-started.md` («The smallest package that works») | для тех, кто читает документацию и хочет пустой лист |

- Имя из формы подставляется в `name` манифеста; `author` — если указан; `format: 1`, `version: 1`.
- Шейдеры шаблонов берут общее из `sky_common.hlsli` (`#include`, плагин отдаёт его сам) и **не трогают
  `c208`…`c223`** иначе как через объявленные там `g_music*` (`sky_abi`).
- **Шаблоны проверяются с обеих сторон**: `TweakerCore.Tests` — что каждый проходит проверку ссылок §5.3 и
  упаковывается; харнесс плагина `harness/skyload` — что каждый грузится настоящим `sky_package`, а шейдеры
  компилируются в ps_3_0 (как `harness/music`). Иначе шаблон, сломанный правкой формата, заметит первый пользователь.

### 5.3 Упаковка и проверка — `SkyPackager`

**Что едет в zip:** всё дерево проекта, кроме записей, начинающихся с точки (`.git`, `.vscode`, `.tweaker`, …),
`shadertoolsconfig.json` в корне (§5.5) и мусора ОС (`Thumbs.db`, `desktop.ini`). Список исключений — одно место в
`SkyPackager`, и тест упаковки шаблона сверяет, что ни один служебный файл в архив не попал. `Config.json` — в корне архива (плоская раскладка; срезание общей
верхней папки плагин умеет, но плоская проще и однозначна). Имена в архиве — с `/`.

**Проверка перед упаковкой** — только то, что дёшево и однозначно, правила формата остаются за плагином:

- `Config.json` разбирается (JSONC), `format > 1` отклоняется, `layers` непуст; проверяются `id` слоёв
  и `kind` ∈ {`fullsky`, `sprites`}. Повторяющиеся `id` дают предупреждение;
- каждый путь из манифеста — безопасное относительное имя (то же правило, что `sky_vfs::is_safe_relative_name`)
  и **существует** в проекте: `shader` (у `sprites` — пара `<stem>.vs.hlsl`/`<stem>.ps.hlsl`), `textures[].path`
  (`.dds`), `generator`, `fill.generator`, файлы заливки. Сравнение без учёта регистра, как индекс zip в плагине;
- предупреждение, а не ошибка: архив больше 64 МБ. Плагин читает архив в память целиком
  (`skybox-replacer-roadmap.md`, Шаг 6), а игра — 32-битный процесс без `LARGEADDRESSAWARE`; 64 МБ сжатого — уже
  верхняя граница, за которой надо смотреть, сколько и каких картинок в пакете (решение владельца 29.10). Текст
  предупреждения называет три самых больших файла.

Ошибка проверки — не устанавливается, в игре остаётся прежний пакет (как у `twllink`: сборка с ошибками не
ставится). Результат — список записей «важность, файл, сообщение»; двойной клик открывает `Config.json` в
редакторе (номер строки знать неоткуда — без него).

Уровень сжатия: `Fastest` при установке (на пересборке по сохранению `.dds`-объём в 8 МБ жмётся каждый раз),
`Optimal` при экспорте.

**Запись в игру — атомарная:** временный файл в той же папке (`.<имя>.sky.partial` — каталог плагина такое имя не
возьмёт: расширение не `.sky` и не картинка), затем `File.Move(..., overwrite: true)` (`MoveFileEx`
`REPLACE_EXISTING`). Плагин читает архив в память на открытии и файл не держит, но может читать в момент замены —
поэтому до трёх повторов с паузой при нарушении совместного доступа. Полузаписанный архив с правильным именем
горячая перезагрузка (она смотрит на время записи архива) подхватила бы посреди записи.

**Конфликты при установке:**

| В `Skyboxes\` уже есть | Что делаем |
|---|---|
| ничего | пишем |
| файл `<имя>.sky` | перезаписываем молча — как Script Dev перезаписывает свой `.lua` |
| **папка** `<имя>.sky` (каталожная форма — в том числе поставляемые `OurDraftsCollides.sky`, `ODC_VolTex.sky`) | **отказ** с объяснением: файл и папку с одним именем Windows не держит, а переименовывать или двигать чужую папку — не наше дело. Предложить переименовать пакет или убрать папку («показать в Проводнике») |
| папка шести граней или что-то ещё с тем же именем | то же — отказ |

**Экспорт** («Pack to file…») — тот же zip в выбранное место, для того чтобы поделиться. Маленький, но
естественный: ровно то, что `getting-started.md` описывает в «Shipping it».

### 5.4 Небеса в игре — `GameSkies`

Список для раздела «в игре» (§7.2) без связи с плагином. Порт `sky_catalog.cxx: add_directory_entries` — те же
правила в том же порядке: папка с `Config.json` → пакет (манифест побеждает грани); папка с гранями → `face_dir`;
файл `.sky` → пакет; `.hlsl` → `shader_file`; картинка 4:3 (крест) или 2:1 (панорама) → `file`, размер грани — из
заголовка (SkiaSharp `SKCodec`, без декодирования). Про каждое:

- поставляемое ли (по `.deploy.json` — путь записи или любой файл под папкой; как `GameScripts.IsShipped`);
- из какого проекта (имя совпадает с пакетом проекта из списка — «From project <имя>»);
- активно ли (по `module.json` или слову плагина).

Встроенные в DLL небеса (`program`, `packed`) хост без связи не знает и не выдумывает: их список приходит от
плагина (§6). Без игры они не показываются, кроме одного случая — если `module.json` выбирает встроенное, строка
«Active: built-in <id>» есть.

### 5.5 Окружение для шейдеров и служебное в проекте

Задача: открыв проект в VS Code с расширением HLSL Tools (`timgjones.hlsltools`), автор видит, что такое `sky_in`,
`sky_gradient`, `g_music_slow`, а `#include "sky_common.hlsli"` не подчёркнут как ошибка. Плагин отдаёт этот
заголовок пакету сам (`shaders.md`: «resolved against the plugin's own packed headers first»), поэтому в пакете его
нет и быть не должно — копия нужна только редактору.

- **Заголовки.** `TweakerCore.csproj` вшивает ресурсом **все** `TweakerPlugin/assets/shaders/*.hlsli` (сейчас
  один — `sky_common.hlsli`) ссылкой на файлы плагина, а не копией: заголовок, который видит редактор, — ровно
  тот, который собран в DLL этой же сборки. Хост раскладывает их в `.tweaker\include\` проекта.
- **Конфиг HLSL Tools** — `shadertoolsconfig.json` в корне проекта (расширение ищет его от файла шейдера вверх):
  `"hlsl.additionalIncludeDirectories": [".tweaker/include"]`. Корень, а не `.tweaker\`, потому что иначе
  расширение его не найдёт; поэтому он отдельной строкой в исключениях упаковки (§5.3).
- **Когда пишется.** `.tweaker\include\` — хоста целиком: перезаписывается при создании проекта, при открытии
  (выборе в списке) и перед каждой установкой, только если содержимое отличается (иначе Install on save получал
  бы запись на каждое открытие — та же ловушка, что `WriteLocal` у `AgentSetup`). `shadertoolsconfig.json` —
  пользователя: пишется при создании и дописывается, только если файла нет; существующий не трогается.
- **Рекомендация расширения** — `.vscode/extensions.json` с `timgjones.hlsltools`, только при создании проекта и
  только если файла нет. Другие редакторы: Sublime/Neovim/Vim подсказок HLSL «из коробки» не дают, файлы им не
  мешают.
- **`.gitignore`** — строку `.tweaker/` создание дописывает, только если её нет (как `AgentSetup`): копию
  заголовка коммитить незачем, хост её восстановит.
- **Проверка.** Тест `TweakerCore.Tests` — что вшитые заголовки совпадают с файлами в `assets/shaders` байт в байт
  и что раскладка повторно ничего не пишет. Что HLSL Tools действительно резолвит `#include` и `g_music*` — только
  руками владельцем в VS Code (один раз, в Н4).

### 5.6 `module.json` без игры — `SkyModuleConfig`

Чтение — как в плагине: JSONC, неизвестное игнорируется, повреждённый файл → значения по умолчанию.
Правка — **только двух полей** `enabled` и `sky { kind, id }` через `JsonTextEdit` (§4.3), остальное (`cubemap`,
`orientation`, `shader`) остаётся байт в байт. Повреждённый файл хост **не** перезаписывает (правило плагина:
«a typo costs you nothing you had») — переключатель говорит, что файл не читается, и предлагает открыть папку.
Писать можно только при остановленной игре; это проверяет вызывающий (§6.4).

### 5.7 `SkyWire`

Грамматика `SKY_*` хоста (§6) — без транспорта и состояния, чтобы проверяться юнит-тестами против тех же строк,
что харнесс плагина. Как `ScriptWire`.

## 6. Протокол `SKY_*`

Отдельный документ грамматики — `overlay-skybox.md` (по образцу `overlay-scripts.md`), строка в таблице
`overlay-protocol.md`. Транспорт не меняется. **Протокол 4** (`k_protocol_version` в `overlay_ipc.cxx`,
`ExpectedProtocolVersion` в `OverlayHelper.cs`); обратной совместимости нет — хост и плагин ставятся вместе.

### 6.1 Токены

- **Вид** — написание `module.json`, `config::kind_key`: `program`, `packed`, `shader_file`, `file`, `face_dir`,
  `package`. Пара «вид + id» — ровно то, что хранит конфиг и что листит каталог, поэтому сопоставление — сравнение.
- **Id** — `catalog_entry.id`, percent-encoded UTF-8 (`ui/wire_text` ↔ `Uri.EscapeDataString`). Для дисковых —
  имя записи в `Skyboxes\`, сравнение без учёта регистра.
- **Имя** — `display_name`, percent-encoded.
- **Статус** активного неба — одно слово: `off` (реплейсер выключен), `waiting` (игра ещё не рисовала небо),
  `compiling`, `ready`, `failed` (не загрузилось / не скомпилировалось; игра рисует своё или прежнее),
  `missing` (выбор называет то, чего каталог не нашёл).
- **Сообщение** — первая строка причины для `failed`, до 400 байт, percent-encoded. Полный текст — панель
  диагностики оверлея.

### 6.2 Операции

| OP | Направление | Токены | Смысл |
|---|---|---|---|
| `SKY_ENABLE` | хост → плагин | `<true\|false>` | `skybox::set_enabled`; `module.json` пишет плагин. Ответ — `SKY_STATE` **всегда** (подтверждение) |
| `SKY_SELECT` | хост → плагин | `<вид> <id>` | `skybox::select`. Незнакомый дисковый id — сначала пересканировать каталог (не чаще раза за кадр); не нашёлся и после — всё равно выбрать (конфиг примет), статус `missing`. **Выбор уже активного неба — перезагрузка с диска** (§6.3). Ответ — `SKY_STATE` всегда |
| `SKY_RESCAN` | хост → плагин | — | `refresh_catalog()`. Ответ — полный список: `SKY_ENTRY`… `SKY_SYNCED`, затем `SKY_STATE` |
| `SKY_ENTRY` | плагин → хост | `<вид> <id> <имя> [размер грани]` | одна строка каталога, в порядке каталога |
| `SKY_SYNCED` | плагин → хост | `<число>` | конец полного списка |
| `SKY_STATE` | плагин → хост | `<включён> <вид> <id> <статус> [сообщение]` | реплейсер и активное небо. Шлётся: после рукопожатия и `SKY_RESCAN`; при каждом **изменении** (включение, выбор — из оверлея тоже, смена статуса); всегда в ответ на `SKY_ENABLE`/`SKY_SELECT` |

Полный список (каталог + состояние) уходит после рукопожатия и после `SKY_RESCAN`, а также когда каталог
изменился по другой причине (кнопка Rescan в оверлее — `catalog_generation()` сдвинулся).

**Чего нет — сознательно:** ручек, света, разрешения рендера, диагностики целиком, времени кадра — это вкладка
оверлея (не-цели, §2). Операции «удалить небо» — удаляет хост, плагин узнаёт по `SKY_RESCAN`. Отдельного ACK —
подтверждение это `SKY_STATE`.

### 6.3 Плагин

- **Новый модуль `src/skybox/sky_remote`** — по устройству `lua_remote` (`script-manager.md` §8.15): синхронный
  обработчик `WM_COPYDATA` только кладёт команду в ящик (мьютекс + вектор + атомарный флаг); `pump()` исполняет её
  позднее на том же игровом потоке, при отрисовке оверлея. Отдельного потока обработки сообщений нет.
  Место вызова — начало `tw::skybox::ui::update()` (`ui_main.cxx` зовёт его каждый кадр, до
  `menu::update`, независимо от того, открыто ли меню; там же сейчас идёт `poll_reload`). `select()` и
  `request_reload()` требуют именно этот поток с привязанным устройством — его же и получают.
- `overlay_ipc.cxx`: строки с префиксом `SKY_` → `tw::skybox::remote::handle_op`, как `SCRIPT_` и `QP_`.
  `request_sync()` — после рукопожатия, рядом с `lua::remote::request_sync()`.
- **Счётчик `skybox::revision()`** — двигают `set_enabled`, `select`, смена статуса загрузки (компиляция
  закончилась, упала, небо впервые увидено). `pump()` сравнивает с отправленным, как `registry::revision()`.
  Горячий путь платит одним инкрементом.
- **Вкладка Skybox оверлея должна видеть чужие изменения.** Сейчас `g_enabled_toggle` выставляется один раз
  (`g_widgets_ready`), а выделение списка — только на пересборке строк по `catalog_generation()`. Обе вещи
  переводятся на `revision()`: переключатель и выделение перечитываются, когда счётчик сдвинулся. Иначе
  TweakerUI переключил небо, а оверлей показывает старое.
- **Перезагрузка без двойной компиляции.** Хост после установки активного пакета шлёт `SKY_SELECT` того же неба.
  Если меню открыто, горячая перезагрузка плагина могла уже заметить новый архив и начать компиляцию сама. Чтобы
  не компилировать дважды, `SKY_SELECT` и наблюдение используют один модуль `skybox::reload`. В фоне он сравнивает
  существование, время записи и размер каждого наблюдаемого файла; неизменившийся снимок не загружает повторно.
  Максимума `newest_write_time` недостаточно: он скрывает удаление зависимости и изменение файла, чьё время
  меньше максимального. Для архива наблюдается сам архив; для каталога — манифест и его зависимости,
  включая отсутствующие. Чтение пакета и исходников компиляции выполняет `bg_work`.
- Шапки `skybox.hxx` и `skybox_config.hxx` («Nothing here is wired to TW_OVL») переписать: теперь хост может
  попросить включить, выключить и выбрать; всё остальное по-прежнему только плагин.
- Без хоста ничего не шлётся и не запоминается.

### 6.4 Хост

- `OverlayHelper`: событие `SkyboxMessageReceived` для строк с префиксом `SKY_` и `SendSkybox`, как у скриптов.
- `TweakerUI/Core/SkyboxOverlayBridge` — статический, инициализируется в `MainWindowViewModel` рядом со
  `ScriptsOverlayBridge`, подписан **всегда** (полный список приходит один раз). Кэш каталога и состояния,
  `IsLive`, `IsSynced`, ожидающие `RequestEnable`/`RequestSelect` (ответ — любой `SKY_STATE`, таймаут 5 с на
  `Task.Delay` с поколением, повторный клик заменяет ожидание), `Rescan`, события `Changed` и `RequestTimedOut`;
  `UseTransport`/`Receive` для стенда.
- После перехода связи в Connected мост запрашивает `SKY_RESCAN`: исходный список после рукопожатия может
  опередить асинхронное завершение handshake на хосте. Это однократная синхронизация при подключении;
  пакеты она не компилирует. Полный каталог применяется по `SKY_SYNCED` только при совпадении числа записей.
- **Три режима**, как у переключателя скриптов (`script-manager.md` §5, §8.4):

  | Игра | Переключатель реплейсера и выбор неба |
  |---|---|
  | не запущена | пишут `module.json` через `SkyModuleConfig` |
  | запущена и подключена | `SKY_ENABLE` / `SKY_SELECT`, сразу показывают новое положение, ждут `SKY_STATE` до 5 с, без ответа — откат и уведомление; `module.json` пишет плагин |
  | запущена, связи нет | заперты; баннер — во вкладку Skybox оверлея |

  Установка и удаление файлов работают во всех трёх режимах — это файлы, а не состояние плагина; при связи после
  них — `SKY_RESCAN` (и `SKY_SELECT`, если тронуто активное небо).

### 7.2 Страница Game

- **Карточка реплейсера:** переключатель «Replace the sky sphere»; строка активного неба — имя, статус, при связи
  «· live from the game»; при `failed` — первая строка причины красным и «полный текст — во вкладке Skybox

- **Список установленного:** при связи — каталог плагина (включая встроенные), без связи — `GameSkies` (§5.4).

  отменяется кликом по другой строке, `sky_ui.cxx`).
- **Удалить** — только своё (`Yours`, `From project …`): в Корзину, с подтверждением. Активное — с
  предупреждением, что в этой сессии игра продолжит его показывать, а при следующем запуске вернётся к небу по
  умолчанию. После — `SKY_RESCAN` при связи. Поставляемые и встроенные удалить нельзя: удаление поставляемого
  делается только вместе с «вернуть поставляемое» (решение владельца 29.10, §10) — иначе по правилу
  `PluginInstallation` удалённое пользователем не вернёт даже обновление.
- **Refresh** — перечитать папку; при связи ещё и `SKY_RESCAN` (одна кнопка, как в Scripts, §8.9 там).
- **Пока страница на экране:** опрос «запущена ли игра» раз в 2 с, наблюдатель на `Skyboxes\` и на
  `module.json` (переключение в оверлее без связи) с паузой 300 мс.
- **Пустые состояния и баннеры:** папка игры неизвестна; плагин не установлен (небо не заменится); игра запущена
  без связи; `module.json` не читается.

- **Левая колонка:** проекты — недавние, затем `SkySources` (§4.3). «Новый», «открыть папку как проект» (без
  `Config.json` — отказ), «перечитать». Сломанный манифест — проект в списке с причиной.
- **Новый проект** — форма на месте подробностей: **Name** (оно же имя файла, §5.1, с подписью «Installs as
  `<имя>.sky`»), **Author**, шаблон с пояснениями (§5.2), Create/Cancel. Папка — `SkySources\<имя>\`.
- **Выбранный проект:** имя, «Installs as», версия, автор, путь; «открыть папку», «убрать из списка» (для
  открытых извне), «удалить проект» (в Корзину; установленный пакет остаётся — его удаляют на странице Game).
- **Правка манифеста** («карандаш»): name, author, version — правкой текста (§4.3), с проверкой имени по мере
  ввода и предупреждениями о переименовании и о `version` (§5.1).
- **Install** и **Install and use**: проверка → упаковка → запись в игру (§5.3); «and use» — ещё и выбор неба
  (при связи `SKY_SELECT`, без игры — `module.json`). Если установленный пакет — активное небо подключённой игры,
  `SKY_SELECT` уходит и после простого Install: игра должна показать новое. Строка итога: «Installed at …»,
  «Installed and selected at …», «Installed; the game reloaded it at …», «Not installed: N problems», под ней
  список проблем проверки.
- **Install on save** — `ProjectWatcher` (§4.2) на папку выбранного проекта, работает и когда вкладка не на
  экране (как Rebuild on save: включил человек, смотрит он в редактор). Каждое сохранение → проверка → упаковка
  → установка → `SKY_SELECT`, если небо активно. Это и есть цикл автора «сохранил — увидел» поверх zip-формы.
- **Экспорт** («Pack to file…») — §5.3.
- **Карточка Editor** — `EditorPickerView` (§4.1), открывает папку проекта; двойной клик по проблеме проверки —
  `Config.json`.

## 8. Решения и почему

### 8.1 Одна вкладка, две страницы

У скриптов две вкладки потому, что у игрока и автора разные предметы и много действий у каждого
(`script-manager.md` §8.2). У неба часть игрока — переключатель и список: на отдельную вкладку меню её мало, а
девятый пункт меню ради одного списка — шум. Две страницы внутри одной вкладки сохраняют разделение предметов,
не раздувая меню. Принято владельцем 29.10.

### 8.2 Проект — это каталог пакета, без второго манифеста

Папку проекта можно отдать плагину как есть, и она заработает; всё, что знает хост, читается из `Config.json`.
Служебное — в `.tweaker\`, который не едет в пакет.

### 8.3 В игру — только zip

Постановка задачи; плюс один файл не приезжает наполовину (`getting-started.md`, «Ship the zip»). Цикл
«сохранил — увидел» сохраняется через Install on save: перепаковка занимает миллисекунды до сотни мс, а плагин
перечитывает активный пакет по `SKY_SELECT` (или сам, если открыто меню, — он следит за временем записи архива).

### 8.4 Отвергнуто: ссылка из `Skyboxes\` на папку проекта

Junction дал бы горячую перезагрузку по каждому файлу без перепаковки, но: в игру поехали бы `.git` и служебное;
каталог плагина видел бы папку, а установка «как пакет» — нет; удаление «пакета» на странице Game удаляло бы
проект. Цена несоразмерна выигрышу в сотню миллисекунд.

### 8.5 Проверка на хосте — только ссылки

Правила манифеста живут в плагине (`sky_package`), и полная копия на хосте разошлась бы с ним при первой правке
формата. Хост проверяет то, что однозначно и что иначе выглядит как «небо не появилось» или «чёрное небо»:
разбор JSON, наличие слоёв и существование файлов. Всё остальное — диагностика плагина в оверлее.

### 8.6 Редактору неба `PATH` не нужен

Небу не нужны ни `twllink`, ни `cgrpy`. Пустое окружение заодно снимает предупреждение «редактор уже запущен» —
оно имело смысл только из-за `PATH` (§4.1).

### 8.7 Владелец `module.json` — плагин, пока игра запущена; без игры выбирает хост

То же, что `scripts.cfg` (`script-manager.md` §8.4): плагин читает файл на старте и переписывает при каждом
переключении; хост просит по IPC. Без игры гонки нет — пишет хост, только два поля и правкой текста.

Выбор неба без запущенной игры нужен не только для удобства: он понадобится запланированному расширенному
формату скинов со встроенной поддержкой скайбоксов (решение владельца 29.10). Поэтому `SkyModuleConfig` —
самостоятельный кусок модели, которым сможет пользоваться установка скина, а не деталь вкладки.

### 8.8 Протокол — изменения, не лента

Как у скриптов (§8.5 там): хост не видит покадрового — ни времени отрисовки, ни ручек, ни компиляции целиком.
Только «включён ли», «что выбрано», «загрузилось ли» и каталог.

### Н2 — результат реализации (01.11.2026)

`sky_remote` подключён к `overlay_ipc` и покадровому `sky_ui::update`; номер протокола поднят до 4
с обеих сторон. [Грамматика и поведение](overlay-skybox.md) описаны отдельно. Хостовый `SkyboxBridge`
и вкладка TweakerUI остаются следующими фазами.

- `current_load_status()` описывает выбранное небо отдельно от успешно рисующегося fallback. Учитываются
  ошибки чтения пакета, компиляция всех активных слоёв (включая vertex stage), ошибки ресурсов и генераторов.
  Ошибка последней компиляции сохраняется даже при пригодном старом bytecode.
- `revision()` обновляет сообщения хосту, переключатель и выделение в оверлее. Полный каталог отправляется
  при подключении, пересканировании и изменении поколения; команды выбора/включения всегда подтверждаются.
- `sky_reload` объединяет первоначальную загрузку, наблюдение и повторный выбор пакета. Работает через
  `bg_work`; новый выбор отбрасывает устаревшую задачу. Штампы файлов описаны в §6.3. Старый
  `newest_write_time()` не используется этим механизмом: одного максимума недостаточно.
- Встроенные шейдеры слоёв пакета исключены из списка самостоятельных встроенных небес при Rescan.
- По уточнению владельца `format > 1` теперь отклоняется и native-загрузчиком, и `SkyPackager`.
  Версия формата остаётся 1; дубликаты id по-прежнему дают предупреждение. Тест проверяет, что отказ
  упаковщика не перезаписывает ранее установленный архив.
- Проверены `wndproc_hub::install/subscribe`: доставка синхронная, отдельного обработчика сообщений
  в фоне нет. Ящики Lua/Sky переносят выполнение к кадру на том же потоке. IPC watchdog не обрабатывает
  сообщения; это ранее согласованный R-14 (`plugin-offline-mode.md`, коммит `363cfbe`). Комментарии исправлены.

**Проверки:**

- Native x86 Release — сборка успешна. Полная сборка `TweakerUI` с native-зависимостями успешна
  (`-p:UsedAvaloniaProducts=` отключает служебную телеметрию Avalonia; CMake/MSVC потребовал запуск вне sandbox).
- `TweakerCore.Tests`, фильтр `Skyboxes` — 64 passed, 0 failed, 0 skipped. NUnit потребовал доступ
  вне sandbox при обнаружении расширений, до этого тесты не запускались.
- Приватный локальный `harness/skyremote`: 21 проверка протокола; 17 проверок настоящего
  асинхронного загрузчика: одинаковые запросы, закрытое меню, изменение ниже максимального timestamp,
  удаление/восстановление зависимости, сломанный манифест и исправление, будущий формат, пропавший источник,
  смена выбора при незавершённой задаче, замена архива и повторный запрос. Протокольный стенд подменяет
  рендерер/каталог, поэтому сам по себе не проверяет D3D-состояния.

**Исправления по проверке:**

- `skybox::reload` хранит единственное состояние в anonymous namespace `.cxx`. Класса загрузчика нет;
  заголовок содержит публичный результат и функции, приватные типы и функции скрыты в TU.
  Замечания по разделению блоков и многострочным enum исправлены в `sky_reload`, `sky_remote`,
  `skybox.cxx` и `skybox.hxx`.
- Результат перезагрузки теперь относится ко всему небу: завершение одного слоя не выдаёт успех,
  пока остальные компилируются. После завершения всех слоёв отправляется один результат;
  успешный слой не скрывает неуспешный.
- У пары vertex/pixel обе стадии принимаются вместе только после успеха обеих компиляций. Ранее
  одна новая стадия могла попасть в активную программу до ошибки другой, создавая смешанную пару.
  При неудаче одиночного shader продолжает работать его собственный последний успешный bytecode.
  Повторный выбор уже загруженного shader также использует его запись в кэше программ; выбранное имя
  и исходник с ошибкой не означают, что ошибочный исходник исполняется. При отсутствии успешного bytecode
  шейдер рисовать не может.
- Новый локальный `harness/skyremote/lifecycle` — 15 проверок с настоящими `D3DCompile`, `sky_program`
  и `skybox::poll_reload`: компилятор с ошибкой возвращает диагностику без bytecode; неудача каждой
  стадии сохраняет всю старую пару; более ранняя готовность vertex не меняет активный bytecode;
  исправление устанавливает пару и сбрасывает ошибку; несколько слоёв завершают одно уведомление,
  поздний успешный слой не маскирует ошибку раннего. Устройство D3D в стенде не создаётся.
- После исправлений: x86 Release собран; lifecycle — 15/15, протокол — 21/21, загрузчик после

## 12. Риски

- **Двойная перезагрузка** при открытом меню (§6.3) — если сравнения времени записи окажется мало, плагину нужен
  явный признак «загружено с этой версии архива».
- **Замена архива, который плагин в этот момент читает** — повторы при нарушении доступа (§5.3); вживую не
  проверено.
- **`GameSkies` против `sky_catalog`** — порт правил каталога; разойдутся при правке каталога в плагине. Тест на
  общих раскладках и комментарий в обоих местах «правится парой».
- **Рефакторинг Script Dev** (Н0) трогает принятый модуль — поэтому отдельной фазой и со снимками до/после.
