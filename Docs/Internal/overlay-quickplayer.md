# Quick Player во внутриигровом оверлее

**Статус: этапы 1–6 реализованы, обе стороны собираются, вкладка отрисовывается.** Проверено:
разбор `QP_*` — отдельным прогоном парсера на синтетических payload'ах (35 проверок, включая
усечённые и заведомо битые сообщения); вкладка Player — в `smoke_test`, где живёт полноценный
фейковый хост, отвечающий на все `QP_NOTIFY_*` настоящими `QP_*`-ответами.

**На реальной игре не проверено** — как и весь остальной оверлей, это за пользователем. Отдельно не
проверено под нагрузкой ввода: контекстное меню трека (ПКМ) открывается только кликом, поэтому
вложенность `popup_menu` → `tab_view` → `BeginChild`/`list_view` прогонялась чтением кода и
инвариантами виджетов, а не запуском.

Формат записи трека и несколько архитектурных мест разошлись с первой редакцией по ходу реализации;
разошедшееся описано ниже по факту, а не по замыслу.

## Что это и зачем

Четвёртая вкладка меню оверлея (рядом со Skins / Tweaks / Settings) — управление Quick Player'ом
изнутри игры: выбрать плейлист, запустить трек, переключить режим воспроизведения и момент
автоперехода, поправить теги/моды/персонажа конкретного трека. Смысл ровно тот же, что у всего
оверлея: менять конфигурацию тулзы, не сворачивая игру.

Фаза 7 (`Docs/Internal/roadmap.md`, `overlay-protocol.md`) сознательно оставила Quick Player за
скобками. Фаза 6 при этом уже сделала под него хостовую половину: `PlaybackController.GetUpcoming`/
`GetRecent`/`CurrentMode`/`PlaybackOrderChanged` существуют именно для того, чтобы очередь можно было
**пушить**, а не опрашивать из `EndScene`. Ядро (`QuickPlayerCore`) этим заходом не меняется.

Читать вместе с:
- `Docs/Internal/overlay-protocol.md` — L1/L2/L3, инжект, reverse-sync твиков/скинов. Всё, что здесь
  описано, — это новые L3-операции поверх уже готового транспорта; L1/L2 не меняются вообще.
- `Docs/Internal/tweaker-plugin-widgets.md` — набор виджетов и правила их использования.

## Принятые решения и почему

| Вопрос | Решение | Почему |
|---|---|---|
| Объём снимка | **Ленивая подгрузка**: каталог плейлистов пушится сразу, состав — только у открытого | 100 плейлистов по 1000 треков — реальный сценарий; пуш всего сразу это секунды на инициализации плагина и мегабайты через `WM_COPYDATA` |
| Каталог тегов | **Захардкожен в плагине** | Список фиксирован игрой и не растёт; хост уже поддерживает всё, что игра понимает. Экономим целую операцию протокола |
| Каталог модов | **Переиспользуем существующий** `overlay_state::tweak_*` | «Моды» трека — это те же 7 твиков (`ModOptionViewModel` строится из `GameTweakCatalog`). Нового каталога не нужно вообще |
| Параметризованные теги | **Редактируются**, нужен виджет числового ввода | В immediate-mode ImGui это дешевле, чем в retained-mode Avalonia |
| Персонаж | **И per-track override, и глобальный default** | Обе настройки осмысленны на ходу |
| UI персонажа | Строка текста + `popup_menu` со списком | Сетка 14 кнопок из десктопа в оверлее не нужна — там она занимает пол-панели |
| `AdvanceTrigger` | **Есть в оверлее** | Меняется на ходу, это и есть смысл модуля |
| Правка состава плейлистов | **Нет** (ни создать/удалить/переименовать плейлист, ни удалить/переставить трек) | Оверкилл для первого захода |
| Служебные данные трека | **Нет** (длительность, битрейт, формат, кодек) | Сервисные данные, мусорят экран поверх игры |
| Скрытая очередь shuffle | **Плагин её знает, но нигде не рисует** | Заготовка под кастомный аннонсер песен поверх внутриигрового |
| Размер окна меню | Померить контент и растянуть окно под него при открытии вкладки | Отдельное окно под плеер — оверкилл |
| Хоткеи транспорта | **Нет** | Отдельная задача в перспективе: общая система кейбиндов оверлея, где любой кнопке/тогглу меню можно назначить клавишу |

## Протокол — новые L3-операции

Все — namespace `QP_`. Транспорт (L1 `OVERLAY_SEND`/`OVERLAY_FORWARD`, L2 `TW_OVL `-конверт) не
меняется ни на байт.

**`overlay_ipc.cxx` эти операции не разбирает.** Он проверяет префикс и форвардит payload целиком:

```cpp
if(op.starts_with("QP_")) {
    tw::ui::qp::handle_op(op, rest);
    return;
}
```

Так `ipc/` остаётся транспортом, а вся грамматика Quick Player живёт в одном месте. Симметрично на
хосте: `OverlayHelper` поднимает событие для `QP_NOTIFY_*`, а разбирает их отдельный класс — по той
же причине, по которой плеер не селится в `menu.cxx`.

Строковые токены — percent-encoded UTF-8, как и везде в L3. Guid'ы — формат `"N"` (32 символа без
дефисов). Имена режимов, персонажей и тегов на проводе — имена соответствующих C#-enum'ов
(`PascalCase`), той же конвенцией, что и wire-имена твиков.

### host → plugin

| OP | Токены | Смысл |
|---|---|---|
| `QP_CATALOG` | `<n> [<playlistId> <name> <trackCount>] × n` | Снимок списка плейлистов. Заменяет целиком, не патчит |
| `QP_TRACKS` | `<playlistId> <n> [<record>] × n` | Полный состав **одного** плейлиста (ответ на `QP_NOTIFY_SELECT` или эхо правки) |
| `QP_ORDER` | `<playlistId> <mode> <advanceOn> <currentEntryId\|-> <n> [<entryId>] × n` | Режим, момент автоперехода, позиция и **очередь ближайших треков** |
| `QP_NOWPLAYING` | `<playlistId> <entryId>` | Трек реально стартовал (`EntryStarted`) |
| `QP_STOPPED` | — | Плеер встал (`EntryEnded` без продолжения, `Stop`) |
| `QP_DEFAULT_CHARACTER` | `<character>` | Глобальный персонаж по умолчанию |

`<record>` — самоописывающийся, разбирается чисто последовательно, без разделителей:

```
<entryId> <artist> <title> <character|-> <tagCount> [<tagWireName> <param|->] × tagCount <modCount> [<modWireName>] × modCount
```

Счётчики вместо разделителей — потому что `split_fixed_tokens` закапан на 3 токена (арность самой
широкой операции `TWEAK_SET`), и вместо изобретения рекордных разделителей достаточно маленького
курсорного `token_reader` (`next()` → `string_view`), который одинаково обслуживает и `QP_TRACKS`, и
`QP_ORDER`.

**Параметр тега — отдельный токен, а не `Имя:12`.** Первая редакция склеивала их через `:`;
отброшено при реализации: составной токен требует, чтобы разделитель пережил percent-кодирование, и
тогда одна половина токена кодируется, а другая нет. Весь смысл кодека в том, что вызывающему не
надо помнить, какие символы структурные. Два токена на тег снимают вопрос целиком.

**Пустых токенов на проводе не бывает.** Токены разделены пробелами, поэтому пустое поле не «едет
пустым» — оно исчезает и сдвигает все последующие. Реальный случай: трек без тега артиста сдвинул бы
свой заголовок в поле персонажа и развалил разбор всей записи. Хост поэтому подставляет
percent-кодированный пробел (`%20`) вместо пустого текста. Сам `-` для этого не годится: дефис
входит в unreserved-набор, и настоящий заголовок `"-"` закодировался бы в тот же токен.

**Очередь в `QP_ORDER` ограничена по длине** (25 записей, `GetUpcoming(25)`). `QP_ORDER` летит на
каждый старт трека, и без ограничения он тащил бы весь остаток прохода — 200 Guid'ов ≈ 6.4 КБ на
событие. `GetUpcoming` не зря принимает `count`.

**`QP_ORDER` описывает плейлист, открытый в оверлее, а не тот, что играет.** Режим и момент
автоперехода — свойства плейлиста, и оверлею они нужны для того, на который смотрит пользователь.
Позиция (`currentEntryId`) и очередь заполняются только когда это один и тот же плейлист; иначе `-`
и пустой список — ровно та же семантика, что у `PlaybackController.CurrentIndexIn`. Чтобы отличить
один случай от другого, контроллеру добавлено `public Guid? CurrentPlaylistId` — спутник
`CurrentEntry`, переживающий окончание трека по той же причине, что и позиция.

### plugin → host

| OP | Токены | Подтверждающее эхо |
|---|---|---|
| `QP_NOTIFY_SELECT` | `<playlistId>` | `QP_TRACKS` этого `playlistId` |
| `QP_NOTIFY_PLAY` | `<playlistId> <entryId>` | `QP_NOWPLAYING` с этим `entryId` |
| `QP_NOTIFY_TRANSPORT` | `<stop\|next\|prev>` | `QP_NOWPLAYING` с ожидаемым `entryId` / `QP_STOPPED` |
| `QP_NOTIFY_MODE` | `<playlistId> <mode>` | `QP_ORDER` с новым режимом |
| `QP_NOTIFY_ADVANCE` | `<playlistId> <auto\|manual>` | `QP_ORDER` с новым `advanceOn` |
| `QP_NOTIFY_TAG` | `<entryId> <token> <true\|false> [param]` | `QP_TRACKS` с новым составом тегов |
| `QP_NOTIFY_MOD` | `<entryId> <wireName> <true\|false>` | `QP_TRACKS` |
| `QP_NOTIFY_CHARACTER` | `<entryId> <character\|->` | `QP_TRACKS` |
| `QP_NOTIFY_DEFAULT_CHARACTER` | `<character>` | `QP_DEFAULT_CHARACTER` |

Отдельного ACK-опа снова нет и не нужно — ровно та же схема, что у `TWEAK_SET`/`CURRENT_SKIN`
(см. «Reverse-sync» в `overlay-protocol.md`): подтверждением служит следующий авторитетный снимок.

Для `next`/`prev` подтверждение **точное**, а не «любой ответ»: плагин держит очередь ближайших
треков из `QP_ORDER`, поэтому знает ожидаемый `entryId` заранее. Это и есть первая практическая
польза от того, что очередь пушится, хотя и не рисуется.

### Выбор плейлиста в оверлее двигает выбор в десктопе

Принятое поведение, а не побочный эффект: `QP_NOTIFY_SELECT` меняет `SelectedPlaylistRow` в
`QuickPlayerViewModel`. Причина — правки трека обязаны идти через `TrackCardViewModel`, а он
существует только для выбранного плейлиста (`Queue` пересобирается на смене выбора). Альтернатива —
править `PlaylistEntry` напрямую в обход VM — оставила бы бейджи десктопной карточки протухшими до
следующего переключения плейлиста. Одна выбранная сущность на два UI проще и честнее двух.

## Хостовая сторона (C#)

- **`OverlayHelper`** — ровно два добавления: `SendQuickPlayer(string opLine)` (проверка готовности
  канала + `OverlayCommand`) и событие `QuickPlayerRequested` для всего, что начинается с
  `QP_NOTIFY_`. Не набор типизированных `PushQuickPlayer*`, как предполагалось: каждый такой метод
  был бы вторым местом, где живёт формат операции. Грамматику плеера этот файл не знает вообще —
  иначе он, где уже 430 плотных строк инжект-гарда и хендшейка, превратится в то же самое, чем
  грозил `menu.cxx`.
- **`TweakerUI/Core/QuickPlayerOverlayBridge.cs`** (новый) — сериализация снимков, разбор
  `QP_NOTIFY_*`, применение действий. Владелец — `QuickPlayerViewModel`, ровно как
  `SkinChangerViewModel` сам подписывается на `OverlayReady`/`SkinRequested`.
- **`QuickPlayerViewModel`** — нужен один сигнал, которого нет: «состав или настройки плейлиста
  изменились». Все мутации (`OnTagsOrModsChanged`, `ApplyCharacterOverride`, `AddFilesAsync`,
  `RemoveCard`, `MoveTrack`, `SetPlaybackMode`, `SetAdvanceTrigger`) уже сходятся в
  `SaveCurrentPlaylist()` — там и поднимаем событие. Плюс `OnDefaultCharacterChanged` как точка
  пуша `QP_DEFAULT_CHARACTER`.
- Источники пушей: `PlaybackOrderChanged` → `QP_ORDER`; `EntryStarted` → `QP_NOWPLAYING`;
  `EntryEnded` → `QP_STOPPED`; `Playlists.CollectionChanged` → `QP_CATALOG`.
- Действия из оверлея трогают `ObservableCollection` — обернуть в `Dispatcher.UIThread.Post`.
  `AudiosurfHandle` захватывает `SynchronizationContext` и постит события через него, но
  полагаться на это молча не стоит.
- `EnsureConnected()` в VM показывает десктопный диалог ошибки — из оверлея он бесполезен (игрок
  в игре). Впрочем, живой оверлей означает подключённую игру по построению, так что путь
  недостижим; отдельной обработки не требует, но и звать его из bridge'а не надо.

## Сторона плагина

```
src/ui/wire_text.hxx/.cxx  percent-кодек L3 (общий) — этап 1, сделано
src/ui/qp/
  qp_catalog.hxx/.cxx   каталоги: 19 тегов, 14 персонажей, 6 режимов — этап 1, сделано
  qp_state.hxx/.cxx     модель + writer (IPC-тред) + cache/refresh (рендер-тред) — этап 1, сделано
  qp_wire.hxx/.cxx      разбор QP_*, token_reader; вызывается из overlay_ipc — этап 1, сделано
  qp_pending.hxx/.cxx   optimistic reverse-sync действий плеера — этап 4
src/ui/plugins/interactive/player.hxx/.cxx   сама вкладка — этап 3
```

`wire_text` — не планировался, но появился сразу: percent-декодер лежал приватно в `overlay_ipc`,
энкодер — приватно в `pending_actions`, и Quick Player стал бы третьей копией. Обе половины обязаны
совпадать байт в байт с `Uri.EscapeDataString`/`UnescapeDataString` на хосте, а три частные копии
такого кодека — готовый способ разъехаться. Обе прежние копии удалены, оба файла переведены на общий.

Всё это renderer-agnostic (без PCH плагина, без D3D9) и уезжает в статическую `tweaker_ui` — значит
`smoke_test` сможет засеять `qp_state` фейковым плейлистом и рисовать реальную вкладку без игры и без
инжекта. Для панели такого размера это единственный вменяемый способ отладки.

`qp_state` повторяет схему `overlay_state` один в один: писатель (IPC-тред) берёт блокирующий
`lock_guard`, читатель (`refresh(cache&)`, раз в кадр) — неблокирующий `try_lock`, копирование только
при смене `generation`. `menu.cxx` получает четвёртую вкладку и один вызов
`player::draw(overlay_snapshot, qp_snapshot)`; `ui_main.cxx` обновляет второй кэш и тикает
`qp_pending::update()` каждый кадр независимо от видимости меню (как сейчас `pending_actions`).
Сигнатура `menu::update` становится двухаргументной — придётся поправить `smoke/main.cxx`.

`qp_pending` — тот же паттерн, что `pending_actions` (оптимистичное отображение → таймаут → тихий
откат → notefeed при неудаче), но собственный модуль: существующий жёстко заточен под фиксированный
`std::array` из 7 твиков и один скин, расширению не поддаётся.

### Обязательство синхронизации каталогов

Каталог тегов захардкожен в плагине сознательно (см. решения выше). Это создаёт обязанность держать
две стороны в синхроне — так же, как это уже сделано для семи твиков:

| Что | Источник правды | Зеркало в плагине |
|---|---|---|
| 19 тегов песни | `QuickPlayerCore/Audiosurf/SongTagCatalog.cs` (`SongTagToken` + формат + min/max) | `src/ui/qp/qp_catalog.cxx` |
| 7 модов трека | `AudiosurfInterface/GameTweakCatalog.cs` | **зеркала нет** — переиспользуется `overlay_state::tweak_wire_name`/`tweak_display_name`/`resolve_tweak_id` |
| 14 персонажей | `AudiosurfInterface/GameCharacter.cs` + `CharacterRoster.RealCharacters` | `src/ui/qp/qp_catalog.cxx` |

Wire-имена тегов — имена членов `SongTagToken` (`FourLanes`, `MinimumMatchSize`, …), а не сами
бракет-строки (`[as-4lane]`): по проводу едет пользовательский смысл, а не деталь формата названия
файла — та же логика, что у wire-имён твиков.

Отдельно стоит отметить: `SidewinderCamera`/`BankingCamera` в модели живут как **моды**
(`ConfigOverrides`), а не как теги, хотя формально есть и в `SongTagCatalog` — `TagOptionViewModel`
прячет их из списка тегов ровно поэтому. Плагин обязан повторять это разделение, иначе тег, попавший
в `Tags`, будет молча стёрт при первой же правке трека в десктопе.

## Новые виджеты

| Виджет | Зачем |
|---|---|
| `segmented` | Ряд взаимоисключающих чипов — прямой аналог `RadioButton.QPSegmentButton` из десктопа. Шесть режимов воспроизведения + пара Auto/Manual. Собирать это из шести `button` вручную в двух местах — то же самое, только дважды |
| `number_input` | Параметризованные теги (`[as-msz12]`, `[as-wb50]`, `[as-monopt3]` — 7 из 19). С clamp по min/max из каталога |
| иконка в `button` | Транспорт (play/stop/next/prev) иконочный. Расширить существующий `button` опциональным `icon_key`, а не заводить `icon_button`: анимации hover/press и hit-test переиспользуются целиком |
| `list_view::set_selected` | Не планировалось. Открытый плейлист — ответ хоста, а не история кликов виджета, и без сеттера левый список не подсвечивал плейлист, который вкладка усыновила сама |
| `tab_view::set_selected_tab` | Не планировалось. Нужен смоуку, чтобы стартовать сразу на разрабатываемой вкладке вместо двух кликов на каждый запуск |

**`list_view` для списка треков использовать нельзя.** Он создаёт по `list_item` на запись и гоняет
`ButtonBehavior` + шаг tween'а для каждой каждый кадр, без клиппера (см. `widgets/list_view.cxx`).
На плейлисте в 1000 треков это неприемлемо в `EndScene`. Список треков рисуется внутри модуля плеера
и не оформляется в виджет: виртуализация завязана на конкретную раскладку строки (заголовок с
текущими бейджами + артист), а не на общий случай.

`ImGuiListClipper` тоже не подходит — его простой режим предполагает одинаковую высоту строк, а
строки растут под бейджи. Вместо него — **префиксная сумма высот**: обе границы видимого диапазона
находятся бинарным поиском, курсор двигается на смещение первой видимой строки, а в конце ставится
на полную высоту, чтобы скроллбар отражал весь плейлист. `ItemSpacing.y` на время строк обнуляется:
все зазоры уже заложены в высоты, из которых собрана сумма, и спейсинг ImGui поверх них развёл бы
раскладку с суммой. Раскладка пересчитывается при смене состава или ширины колонки, а не каждый кадр
— она меряет каждый бейдж каждого трека.

**Анимации строк — не по строке, а по роли.** Состояние tween'а, привязанное к индексу строки, в
виртуализованном списке анимирует то, что вкатилось в этот слот, а не строку под курсором — поэтому
первый заход обошёлся вообще без анимаций, и это было заметно. Но в каждый момент времени наведённая
строка ровно одна и выбранная ровно одна, так что анимация принадлежит **им**: пара
предыдущая/текущая плюс один `float` на каждую, ровно как `tab_view` делает для своего контента.
Заливки складываются, а не заменяют друг друга — наведение на выбранную строку углубляет её, а не
подменяет подсветку. Шаг tween'ов делается один раз на весь список, а не на строку.

Новые SVG-иконки (монохром, `viewBox="0 0 24 24"`, правила — `tweaker-plugin-widgets.md`):
`play`, `stop`, `next`, `prev`, `music`.

## Раскладка вкладки

```
┌ Playlists ───────────┬──────────────────────────────────────────────────────┐
│ Mixtape          (3) │  Title                                                │
│ Grind          (250) │  Artist  [as-4lane] [Invisible Road] [Ninja Mono]     │  ← ПКМ по строке
│ Freeride         (0) │  Title                                                │
│                      │  Artist                                               │
└──────────────────────┴──────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────────────────────┐
│ Character: Ninja Mono                                                        │
└──────────────────────────────────────────────────────────────────────────────┘
 [◀◀][▶][■][▶▶] │ MODE  Auto │ Manual  │ PLAYBACK  Single │ In order │ Shuffle …
```

- Плейлисты — **`list_view`, а не `tab_view`**, вопреки первой редакции. Причина прямо в ответе на
  вопрос об объёме: сто плейлистов — заявленный сценарий, а nav-колонка `tab_view` не скроллится и
  физически не может показать столько. Клик по строке шлёт `QP_NOTIFY_SELECT`, состав приезжает
  следующим сообщением. Открытый плейлист пушится обратно в список через `list_view::set_selected` —
  авторитетен ответ хоста, а не история кликов виджета.
- **Подвал повторяет транспортную панель десктопа** после её mockup-прохода: одна строка
  `кнопки │ MODE Auto/Manual │ PLAYBACK <шесть чипов>`, разделители-линейки, подписи — инлайновые
  микрокапсы рядом со своей группой, а не над ней; свободная ширина растекается по четырём зазорам
  между группами, а не копится справа. Первый заход был тремя центрированными строками с подписями
  сверху и стоил двух строк высоты, которые нужны списку треков (`Fuckups/playback_control_template_miss.png`).
  Чипы режимов — **глифы**, как у десктопа: шесть иконок это построчный порт его же геометрий
  `IconQPMode*` в SVG, так что оба UI показывают одно семейство знаков для одних и тех же режимов.
  Имя режима живёт в тултипе (имя, затем пояснение — та же форма, что у `PlaybackModeOptionViewModel.Tooltip`).
- **Ширина строки распределяется по четырём зазорам**, как четыре star-колонки у десктопа. Первая
  версия делила запас на четыре, но тратила его только на двух разделителях — половина запаса всё
  равно копилась справа, из-за чего выглядело так, будто распределения нет вовсе.
- **Окно нельзя ужать уже, чем нужно вкладке.** Содержимое вкладки не переносится: транспортная
  строка это фиксированная композиция кнопок, линеек и полос, и в узком окне она не уплотняется, а
  просто вылезает за край. Минимум размера теперь зависит от выбранной вкладки (`g_active_min_size`)
  — Player поднимает его под свою ширину, остальные три остаются на прежнем `k_min_size`.
- «Default character» — одна кнопка на всю ширину с текстом `Character: <имя>`. Отдельная подпись
  слева от кнопки была на фиксированном отступе, который оказался уже текста, и наезжала на неё;
  подпись внутри самой кнопки убирает измерение из задачи целиком.
- **Высота подвала считается точно** (`footer_height()`), включая `ItemSpacing`, и между строками
  подвала нет распорок-`Dummy`. Приблизительная оценка давала несколько пикселей переполнения, а с
  ними — постоянный скроллбар на всей вкладке и контент за ним; скроллбар при этом ещё и съедает
  ширину у каждой строки. Список треков сжимается, если окно правда низкое, но обёртки со скроллом
  вокруг всего больше нет.
- Строка трека — только артист и название плюс бейджи активных тегов/модов/персонажа. Обложек нет.
  Бейджи — настоящие пилюли: 8px по горизонтали, 3px по вертикали, отступ от правого края строки, и
  вертикальное центрирование по своей строке текста. С прежними 6/2 они читались как текст с
  подсветкой, а последний упирался в край подложки (`Fuckups/tags_too_small.png`).
- **Строка растёт под бейджи, а не отбрасывает лишние.** Первый заход просто переставал их рисовать,
  когда кончалась ширина (`Fuckups/tags_did_not_fits.png`). Теперь бейджи текут от строки заголовка
  вниз, как `WrapPanel` в десктопной карточке: первый ряд делит строку с названием, следующие ряды
  начинаются от текстового поля и получают всю ширину (иначе длинное название зажимало бы бейджи в
  колонку по одному). Артист всегда последняя строка.
- Название трека и имя плейлиста обрезаются **многоточием**, а не жёстким клипом по краю
  (`Fuckups/playlist_name_too_long.png`) — `detail::add_text_ellipsis`.
- Слева от списка треков — имя открытого плейлиста, как заголовок карточки очереди в десктопе. Без
  него правая колонка нигде не говорит, что именно открыто.
- Строки бокового списка плейлистов — две строчки: имя и, помельче, количество треков. «(6)» в одну
  строку с именем конкурировало с ним за и без того короткую ширину. Второй строкой заведует
  `list_item_content::subtext`.
- ПКМ по строке → `popup_menu`, внутри которого `tab_view` с тремя вкладками Character / Tags /
  Mods, по смыслу совпадающий с RMB-меню `TrackCardViewModel` в десктопе. Три вкладки, а не одна
  колонка: полный набор это 14 персонажей + 17 тегов + 7 модов, и разом их не покажет никакой popup.
  Меню помнит только `entry_id` и **перерезолвливает трек из снимка каждый кадр** — вектор строк
  пересобирается при каждом эхе от хоста, то есть при первой же правке, которую сделало само это
  меню, захваченный указатель протух бы.
- Подписи тегов — целые предложения очень разной длины («Mono all greys - scores start at 1000 and
  go down with each hit»), поэтому popup шире (460px) и подписи **переносятся**, а не обрезаются.
  Числовое поле параметризованного тега стоит отдельной строкой с отступом, а не справа от подписи:
  на одной строке пришлось бы либо резать подпись, либо резервировать ширину, которую 10 из 17 тегов
  не используют.
- Из 19 тегов в меню предлагаются 17: `SidewinderCamera`/`BankingCamera` отфильтрованы флагом
  `tag_definition::selectable` ровно так же, как `TagOptionViewModel` прячет их из десктопного
  списка Tags — на обеих поверхностях они живут среди модов.
- «Default character» — строка текста + `popup_menu` со списком 14 персонажей, а не сетка кнопок.
- Пока `QP_CATALOG` ни разу не пришёл — пустое состояние («Quick Player is not connected»), а не
  пустой список.

**Размер окна.** `k_min_size = {320, 260}`, дефолт `{420, 520}`, размер персистится в
`overlay_config`. Вкладке Player этого мало, поэтому `menu.cxx::grow_to_fit` на переходе в неё
**один раз** растягивает `g_size` до нужного, если оно меньше: не каждый кадр, не уменьшая обратно
(размер принадлежит пользователю), с клампом к вьюпорту.

Нужный размер считается **из метрик шрифта, а не из прошлого кадра** (`player::desired_content_size`):
растянуть окно надо на том самом кадре, когда вкладку открыли впервые, а измерять там ещё нечего —
предыдущего кадра этой вкладки не существует. Ширину задаёт самый широкий фиксированный элемент,
строка режимов воспроизведения. Вызывается это **после** `ImGui::End()`: метрики шрифта валидны
только внутри кадра.

## Потоки и производительность

Ничего принципиально нового: `QP_*` разбираются синхронно на том потоке, которому Windows доставит
`WM_COPYDATA` (см. «Многопоточность» в `overlay-protocol.md`). Отличие от твиков только в размере —
разбор снимка на 1000 треков с percent-decode это тысячи мелких аллокаций на потоке оконных сообщений
игры. Всё ещё редко (открытие плейлиста, правка трека) и всё ещё не hot-path по определению проекта,
но это **второй аргумент за ленивую подгрузку**: пуш всего каталога сразу означал бы этот же разбор,
умноженный на число плейлистов, единым куском на старте.

Отрисовка hot-path'ная и подчиняется общим правилам: чтение `qp_state::cache` раз в кадр, никаких
аллокаций в цикле строк, клиппер обязателен.

## Этапы

1. **Протокол — сделано.** `wire_text`, `qp_catalog`, `qp_state`, `qp_wire` + ветка `QP_` в
   `overlay_ipc`; на хосте `SendQuickPlayer`/`QuickPlayerRequested` в `OverlayHelper`,
   `QuickPlayerOverlayBridge`, событие `QuickPlayerViewModel.PlaylistChanged` (поднимается из
   `SaveCurrentPlaylist`, куда все правки уже сходятся) и `PlaybackController.CurrentPlaylistId`.

   Обратное направление в этот этап вошло **одной** операцией — `QP_NOTIFY_SELECT`. Без неё
   `QP_TRACKS` не отправляется никогда: выдача треков ленивая, и запрос на открытие плейлиста и есть
   её единственный триггер. Остальные `QP_NOTIFY_*` — этапы 4–5.
2. **Виджеты — сделано.** `segmented`, `number_input`, иконка в `button`, пять SVG-ассетов
   (`play`/`stop`/`next`/`prev`/`music`), группа `Controls` в `smoke/main.cxx`. Попутно добавлены
   `list_view::set_selected` и `tab_view::set_selected_tab` — обоим виджетам не хватало
   программной установки значения, которое живёт снаружи.
3. **Вкладка Player — сделано.** Плейлисты, клиппованный список треков, бейджи, «сейчас играет»,
   растягивание окна, `menu::show_tab`. В `smoke/main.cxx` — **полноценный фейковый хост**: он
   собирает настоящие `QP_*`-payload'ы и скармливает их настоящему парсеру, а на `QP_NOTIFY_*`
   отвечает так же, как ответил бы реальный. Три плейлиста, один из них на 250 треков — иначе
   регрессию клиппера нечем заметить.
4. **`qp_pending` + reverse-sync транспорта — сделано.** Play / stop / next / prev, режим,
   advance-trigger, default character.
5. **Reverse-sync правок трека — сделано.** Теги (включая параметризованные), моды, персонаж — через
   ПКМ-меню; на хосте все `QP_NOTIFY_*` применяются через те же view models, что и десктопный UI.
6. **Документация — сделано.** Ссылка на `QP_*` и общий percent-кодек в `overlay-protocol.md`,
   `segmented`/`number_input`/иконка в `button`/`set_selected`/`set_selected_tab` в
   `tweaker-plugin-widgets.md`, этот файл актуализирован по факту.

Ручная проверка на реальной игре — за пользователем, как и всё остальное в оверлее и Quick Player.
В первую очередь: ленивая подгрузка на большом каталоге, ПКМ-меню трека и то, что правка из оверлея
доезжает до десктопной карточки (бейджи должны обновиться сразу, не по переоткрытию плейлиста).

## Сознательно вне объёма

- **Правка состава плейлистов из оверлея** — создание/удаление/переименование плейлиста, удаление
  трека, drag&drop-перестановка. Ядро к этому готово (`RebuildOrder` — публичный API ровно под такие
  правки), протокол расширяется парой `QP_NOTIFY_MOVE`/`QP_NOTIFY_REMOVE`, но в первый заход не идёт.
- **Отрисовка очереди shuffle.** Плагин её получает и хранит; UI для неё не делается. Она —
  заготовка под кастомный аннонсер песен поверх внутриигрового.
- **Хоткеи транспорта и пин «Now playing» на HUD.** Хоткеи — часть будущей общей системы кейбиндов
  оверлея (любой кнопке/тогглу меню можно назначить клавишу), а не пять захардкоженных подписок на
  `wndproc_hub`, которые потом придётся выпиливать.
- **Служебные данные трека** (длительность, битрейт, формат) — их нет в снимке, и хост их не читает
  при пуше. Если понадобятся, это поле в `<record>` и вызов `MetadataReader` на весь плейлист при
  сериализации — не бесплатно, отсюда и решение.
