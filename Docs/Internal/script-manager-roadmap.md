## 1. Как мы сюда пришли

В плагине давно был встроенный LuaJIT со скриптами поверх графа каналов игры (`lua-scripting.md`), но он
был прототипом: скрипты стартовали в недогруженной игре, один упавший скрипт гасил все, писать
что-то крупнее одного файла было нечем. План `lua-engine-fix-roadmap.md` превратил его в инструмент
(все фазы закрыты и проверены на игре к 27.09.2026):

| Фаза | Что дала | Что из этого важно для UI |
|---|---|---|
| Ф1 | покадровая спина — детур на `EngineControl::EngineLoop`, `tw.on_tick` | — |
| Ф2 | жизненный цикл движка; колбэки скриптов не зовутся, пока игра не загрузилась; группы каналов переживают выгрузку | — |
| Ф3 | доступ к каналам разложен по семействам (`src/engine/family/`) | — |
| Ф4 | **единица отказа — скрипт**: свой `xpcall` на колбэк, бюджеты ошибок и времени, приостановка, дедуплицирующая диагностика, вкладка Scripts в оверлее со статусами | состояние скриптов живёт **в игре**; хосту оно сейчас не видно |
| Ф5a | **`twllink`** — компоновщик: проект из модулей → один `.lua` + `.lua.map`; плагин по карте показывает ошибки в строках модулей; `puzzlepro_hud` стал проектом из 17 модулей | UI работает с проектами и с `twllink` |
| Ф5b | единый источник API (`api.json` из пролога), проверки при сборке, `--install`/`--new` (и `--watch`, убранный в С1), определения для редактора (`tw.def.lua`), версия API (`@api`) | весь контракт CLI, который UI будет вызывать, готов |

Модуль управления скриптами в хосте был заявлен раньше, в Ф8 `plugin-offline-mode.md`: кнопке
«Восстановить поставляемые скрипты» нужен список того, что поставляется, что стоит у пользователя, что он
правил (`.old`) и что удалил. План Lua-движка учитывал модуль только как потребителя CLI (§9.11 там) и
проектировал контракт `twllink` под него. Проверив Ф5b, владелец подтвердил: из голого терминала
пользоваться неудобно — это и есть задача.

## 2. Скрипты на стороне игры — с чем будет работать UI

Всё — от папки `engine\` игры; в `TweakerUI` она уже есть: `PluginService.EngineDirectory` (родитель
`SettingsProvider.GameTexturesPath`, проверка `PluginInstallation.IsValidEngineFolder`).

```
engine\TweakerStuff\
  Scripts\*.lua              скрипты; плагин сканирует НЕРЕКУРСИВНО, при старте
  Scripts\*.lua.map          карта строк собранного скрипта (необязательна)
  Scripts\*.lua.old[.N]      версия пользователя, отодвинутая обновлением поставки (PluginInstallation, Р-2)
  Config\scripts.cfg         какие скрипты ВЫКЛЮЧЕНЫ (только исключения; ключ — имя файла)
  .deploy.json               манифест того, что положила установка, с хешами (PluginInstallation)
```

- **Идентичность скрипта — имя файла.** По нему `scripts.cfg` помнит «выключен». Переименованный файл —
  новый скрипт, старый остаётся рядом.
- **Шапка** читается без запуска файла: первые строки-комментарии до первой строки кода,
  `-- @name`, `@author`, `@version`, `@description`, `@api`. У собранного скрипта шапку пишет `twllink` из
  манифеста; плюс `@bundle twllink 1.1, N modules` — признак «собран из проекта».
- **`@api`**: скрипт, которому нужен API новее, чем у плагина (`tw.api_version`, сейчас `1`), плагин не
  запускает и пишет об этом в строке скрипта.
- **Плагин не следит за файлами.** Новый/изменённый скрипт подхватывается по кнопке Reload (или
  выкл/вкл) во вкладке Scripts оверлея либо при перезапуске игры.
- **Вкладка Scripts оверлея** (`src/lua/lua_ui.cxx`) уже показывает всё живое: состояние (off, running,
  suspended, failed, waiting), стоимость в мс, хуки, сообщения с позициями в модулях, кнопки
  вкл/выкл, Resume, Reload. Хост этого не видит — канала нет (см. вопросы).
- **Поставляемые скрипты** — `TweakerPlugin/assets/scripts/*.lua` (+ `.lua.map`) → `PluginPayload\TweakerStuff\Scripts\`
  (`CopyTweakerPlugin` в `TweakerUI.csproj`) → игра (`PluginInstallation`). Подпапка `dev/` не
  поставляется. Часть поставляемых скриптов — сами собраны из проектов в
  `TweakerPlugin/assets/script-projects/` (`puzzlepro_hud`); проекты не поставляются, только их бандлы.
- **`PluginInstallation`** (`TweakerCore/PluginInstall/`) обновляет поставку по манифесту: не менявшийся
  файл перезаписывает молча, изменённый пользователем отодвигает в `.old`, удалённый пользователем
  **не** возвращает (для этого и нужна будущая «Восстановить»). Требует, чтобы игра не была запущена.

## 3. `twllink` — краткое руководство

Консольный `twllink.exe`. Лежит в `<TweakerUI>\DevTools\Binaries\` (С1): в поставке — Native AOT, один
файл без рантайма (публикуют все четыре скрипта деплоя); в дев-сборке — обычная сборка компоновщика,
которую туда кладёт `dotnet build` самого `TweakerUI` (target `CopyTwllink`).

### Проект

```
my_hud/
  twproject.json        манифест, имя фиксированное
  src/main.lua          точка входа, имя фиксированное
  src/draw/rail.lua     require("draw.rail")
  .luarc.json           настройки Lua Language Server (пишет --new)
  .twllink/             tw.def.lua + схема манифеста для редактора; каждая сборка освежает, если есть
  build/                результат по умолчанию: <id>.lua и <id>.lua.map
```

```jsonc
{
  "$schema": ".twllink/twproject.schema.json",
  "format": 1,
  "id": "my_hud",            // [a-z0-9_]{1,64}; имя файла в Scripts\ — идентичность, не менять
  "name": "My HUD",          // в одну строку
  "author": "you",
  "version": "0.1.0",        // строго MAJOR.MINOR.PATCH
  "description": "One line.",
  "api": 1,
  "build": { "comments": "keep", "embed": ["LICENSE"] },          // необязательно
  "diagnostics": { "warnings_as_errors": false, "suppress": [] }  // необязательно
}
```

Списка исходников нет: в бандл попадает то, до чего дошёл граф `require` от `main`. Манифест не знает
ничего о машине (ни пути к игре, ни к редактору).

### Команды

| Команда | Что делает |
|---|---|
| `twllink` | собрать проект текущего каталога в `build/` |
| `twllink --project <dir\|twproject.json>` | собрать указанный проект |
| `--out <file.lua\|dir\>` | куда писать; `.map` кладётся рядом |
| `--install [--game <dir>]` | собрать и скопировать `.lua` + `.map` в `engine\TweakerStuff\Scripts\`; `--game` — корень Audiosurf **или** его `engine\`; без `--game` — переменная `AUDIOSURF_DIR`. Нет `TweakerStuff\` — отказ «плагин не установлен» |
| `--json` | результат JSON в stdout вместо текста |
| `--api <api.json>` | проверять по другому описанию API (для разработки самого API) |
| `--new <hud\|hook\|empty> <dir>` | создать проект в новом/пустом каталоге; `id` из имени каталога; только текст, с другими флагами — ошибка использования |
| `--version`, `--help` | |

Файлы пишутся только при изменении содержимого (дата не трогается).

### Коды возврата — контракт для UI

| Код | Значит | Где подробности |
|---|---|---|
| 0 | собрано (и установлено, если просили) | stdout |
| 1 | в проекте ошибки (или не удалась установка / запись) | stdout — текст или JSON с диагностикой |
| 2 | ошибка командной строки (нет проекта, неверный флаг, плохой `--api`, `--new` в непустой каталог) | **stderr, только текст** `twllink: ...` — JSON не выдаётся |
| 3 | сбой самого `twllink` | stderr, текст со стеком |

### `--json`

```json
{
  "twllink": "1.1",
  "success": false,
  "project": "C:\\...\\my_hud",
  "id": "my_hud", "name": "My HUD", "version": "0.1.0",
  "output": null, "map": null, "installed": null,
  "modules": [ { "name": "main", "file": "src/main.lua" } ],
  "diagnostics": [
    { "severity": "error", "code": "TW0302", "file": "src/main.lua", "line": 3, "column": 11,
      "message": "'tw.hud.txt' does not exist in API 1 - did you mean 'tw.hud.text'?" }
  ],
  "errors": 1, "warnings": 0
}
```

`file` — от корня проекта, прямыми слэшами; пусто — сообщение о проекте целиком. `line`/`column` с 1,
`0` — неизвестно. `id`/`name`/`version` нет, если манифест не прочитался. Человекочитаемый вывод —
тот же список в виде `file(line,col): error TW0302: ...`; тест сверяет, что они совпадают.

### Коды диагностик

Номера не переиспользуются; полная таблица для авторов — `Docs/scripting/authoring.md` (тест сверяет её
с кодом). Диапазоны: **TW00xx** манифест и вшиваемые файлы, **TW01xx** исходники и граф `require`,
**TW02xx** запись результата и установка (TW0203 — `--install` не смог), **TW03xx** песочница, имена
`tw.*`, глобалы. Предупреждения: TW0010, 0015, 0109, 0303, 0305, 0306, 0307; остальное — ошибки.

## 4. Уже решено — не переоткрывать без нового аргумента

- Бандл — одна форма (шим `require`, модули как функции); режим «прямого связывания» вычеркнут
  (решение владельца, `lua-engine-fix-roadmap.md` §17.2).
- Имена `twproject.json` и `src/main.lua` фиксированы; `version` — строгий semver; `id` — идентичность.
- Манифест описывает проект, а не машину: путь к игре передаёт тот, кто вызывает (`--game`).
- Разборщик — Loretta; публикация — Native AOT, запасной путь — `PublishSingleFile`, свой парсер не пишем.
- `Nullable=enable` в проектах компоновщика — утверждено; в остальном решении политика не менялась.
- API `tw.*` правится по порядку из CLAUDE.md («Пользовательская документация»): `tw.api_version`,
  `ljtest` с `TW_API_UPDATE=1`, `api-reference.md`, тесты с `TWLLINK_UPDATE_DEFS=1`, пересборка `twllink`.

## 5. Решения владельца по UI (27.09.2026)

Номера — прежних открытых вопросов. Под каждым решением — что из него следует в коде и что нашлось при
сверке с кодом.

1. **Где `TweakerUI` берёт `twllink.exe`.** Как и все компоненты, `twllink` собирается как часть сборки
   `TweakerUI`. Инструменты разработчика живут рядом с приложением: `<TweakerUI>\DevTools\Binaries\`
   (`twllink.exe`), `<TweakerUI>\DevTools\Sources\` (проекты по умолчанию, п. 3).
   - В дев-сборке — обычная (не AOT) сборка компоновщика, скопированная в `bin\...\DevTools\Binaries\`:
     AOT-публикация на каждый `dotnet build` стоила бы десятков секунд и требовала бы MSVC. В поставке —
     Native AOT, её по-прежнему делают скрипты деплоя, только кладут в `DevTools\Binaries\`.
2. **Две вкладки.**
   - **Scripts** — для игрока: скрипты в папке игры, поставляемые и свои. Вкл/выкл, «восстановить
     поставляемые», что из поставки пользователь правил (`.old`) или удалил.
   - **Script Dev** — для разработчика: список **проектов**, действия «открыть папку как проект», «создать
     новый» (шаблоны `--new`), собрать, установить; выбор рабочего окружения.
   - **Окружение** — список редакторов: TweakerUI ищет установленные в стандартных местах и добавляет их
     сам. «Открыть проект» запускает выбранный с `DevTools\Binaries` в `PATH` дочернего процесса — чтобы
     `twllink` работал из терминала редактора.
   - **Список редакторов (решено 28.09.2026):** VSCode, **Cursor**, Sublime Text, **Notepad++**, vim, neovim.
     Atom отпал — GitHub закрыл его в декабре 2022. VSCodium и Zed пока не нужны: добавить редактор —
     правка пары функций. Notepad++ без LSP, подсказок по `tw.*` в нём не будет.
   - **`PATH` дочернего процесса не доходит до уже запущенного GUI-редактора.** VSCode, Cursor и Sublime
     работают одним процессом: повторный запуск передаёт папку уже открытому, а встроенный терминал
     наследует окружение первого. **Решение владельца:** системный `PATH` пользователя не трогаем (засорять
     его ради редко нужного инструмента некрасиво, а уже запущенный редактор всё равно его не увидит).
     Вместо этого «открыть проект» замечает, что редактор уже запущен, и предупреждает: «Редактор уже
     запущен, и его PATH может остаться старым — twllink из его терминала может быть недоступен. Если
     он нужен, закройте редактор и откройте проект отсюда».
3. **Где живут проекты.** По умолчанию — `<TweakerUI>\DevTools\Sources\`. Плюс «открыть папку как проект»
   в любом месте: папка с `twproject.json` запоминается в списке недавних (текстовый файл рядом с
   приложением), файлы пользователя никуда не переносятся — как «Open Folder» у VSCode.
4. **Живое состояние из игры в хосте — не нужно принципиально** (уточнено 01.10.2026; 27.09 было
   «отложено»). Lua-система — модуль плагина, а не хоста. Хочешь видеть, что скрипт делает прямо сейчас, —
   открой оверлей. Хост «сидит на стульчике и смотрит», а плагин отчитывается ему **только об изменении
   состояния**: включён/выключен, упал при загрузке (с ошибкой), приостановлен, пропал файл. Покадровые
   вещи — стоимость в мс, ожидание загрузки игры — в хост не идут никогда. Бывшая фаза С6 снята.
5. **Владелец `scripts.cfg` — плагин.** Хост просит по IPC «включи скрипт X», включает и пишет конфиг
   плагин.
   - **Когда игра не запущена**, плагина нет и спросить некого: тогда файл пишет хост, тем же форматом —
     гонки нет, плагин читает его только при старте.
   - **Игра запущена, а связи с ней нет** (хост не подключился): переключатели недоступны, с объяснением.
6. **`id` проекта совпадает с поставляемым скриптом** — предупреждение с подтверждением: «Имя
   puzzlepro_hud совпадает со скриптом из поставки Tweaker. Установка затрёт его и может помешать
   корректным обновлениям. Продолжить?» Поставляемое — то, что записано в `.deploy.json`.
7. **Ошибки сборки из TweakerUI** — списком из `--json`. Двойной клик — открыть проект в выбранном
   редакторе (с тем же `PATH`) на файле и строке записи, если редактор это умеет; не умеет — просто проект.
8. **`--watch` из компоновщика убрать.** Следить за папкой — дело хоста: TweakerUI заводит наблюдатель на
   папку активного проекта и сам зовёт `twllink`.
   - Для честности: такие флаги у компиляторов встречаются (`tsc --watch`, `esbuild --watch`,
     `sass --watch`). Но здесь хост и так запущен — он и открыл редактор, — и второй наблюдатель в
     компоновщике только дублирует его и держит лишний код и самый хрупкий тест.
9. **`--install` при запущенной игре → плагин пересканирует `Scripts\`.**
   - **Пересканирование в рантайме** — кнопкой во вкладке Scripts оверлея и IPC-командой.
   - **«Восстановить поставляемые»** — с предупреждением: «Ваши правки поставляемых скриптов будут
     перезаписаны. Продолжить?»
   - **Сверка с кодом.** Номер скрипта в реестре — его индекс, «never reordered or shrunk»
     (`lua_registry.hxx`). На этом держится проверка планировщика «может ли этот скрипт работать» на
     каждом вызове перехваченного канала. Поэтому пересканирование **дописывает** новые файлы в конец и
     помечает исчезнувшие как «нет файла» — не перестраивает список. Порядок строк во вкладке — дело
     отображения. Второе: сообщения IPC разбираются на потоке, на котором Windows доставила
     `WM_COPYDATA`, а реестр принадлежит только потоку движка. Командам нужен ящик, который поток движка
     разбирает раз в кадр (§8, С5).

Фазы по порядку; каждая заканчивается проверкой владельцем. Модель (без UI) — в `TweakerCore` с тестами в

проверка — `Tools/UiStand`.

- **С1 — `twllink` в сборке TweakerUI, раскладка `DevTools\`, без `--watch`.**
  - `TweakerUI.csproj` собирает компоновщик и кладёт его в `DevTools\Binaries\` своего выхода;
  - скрипты деплоя (все четыре) кладут AOT-`twllink.exe` туда же, а не в корень;

- **С2 — модель в `TweakerCore`.**
  - каталог скриптов игры: шапки (порт `read_header`), поставляемые/свои по `.deploy.json`, `.old`,

   - Даже на одном потоке `WndProc` приходит посреди чужого стека, а включение скрипта — это запуск его
     тела. Получился бы повторный вход в середине кадра.
   - Решение: разбор кладёт команду в ящик (мьютекс + маленький вектор), `lua_host` разбирает его раз в
     кадр **в `draw_frame` до диспетча** — там же, где сейчас срабатывают клики в оверлее. Пустой ящик —
     одна атомарная проверка за кадр.
3. **Пересканирования `Scripts\`.** Папка сейчас читается только в `registry::load_all` при старте.
   - Нужен `registry::rescan()`: новые файлы — **в конец** (номер скрипта = индекс, «never reordered or
     shrunk», на этом стоит проверка планировщика на каждом перехваченном вызове канала); исчезнувшие —
     выгрузить и пометить «нет файла»; заголовки всех — перечитать.
   - Вкладка оверлея сама перестраивает виджеты при смене числа скриптов (`lua_ui.cxx`, `g_built_for`).
4. **Хранилища с постоянными адресами.** Сейчас `std::vector<script> g_scripts`, а `find()` возвращает
   `&g_scripts[id]`, и заголовок обещает, что указатель стабилен весь сеанс. Сегодня это верно лишь потому,
   что вектор не растёт после `load_all` (`clear` + `reserve` при старте). Дописывание в конец его
   переаллоцирует. Все вызовы `find()` берут указатель на время одного вызова (проверено 01.10.2026:
   `lua_sched`, `lua_diag`, `lua_ui`, `lua_registry`), но контракт сломается.
   - **Решение владельца:** объект скрипта — в куче, в векторе — тонкие владеющие обёртки. Переаллокация
     двигает обёртки, а у вызывающих остаётся живой указатель. Аллокация при пересканировании — не горячий
     путь: оно по кнопке или после установки, а не каждый кадр. На доступе `->` у умного и сырого указателя
     в Release машинный код один.
   - **Выбрано `std::unique_ptr` (02.10.2026, владелец: «решения приняты»).** Владелец предложил `std::shared_ptr`. Моё предложение —
     `std::unique_ptr`: владелец у скрипта один (реестр), записи никогда не удаляются (пропавший файл —
     состояние, а не удаление), так что счётчик ссылок `shared_ptr` ничего не даёт. Его цена при этом не в
     `->`, а в атомарных инкрементах на каждой копии. Если где-то понадобится пережить удаление записи —
     тогда `shared_ptr`.
5. **Обратного канала** — `SCRIPT_STATE` (§9.4).
6. **Кнопки Rescan во вкладке Scripts оверлея** (§5 п. 9).

**Хост**
7. **`OverlayHelper`:** пропускать `SCRIPT_*` в обе стороны (событие и метод отправки, как у QP). Грамматику
   и ожидание подтверждений держать в отдельном классе по образцу `QuickPlayerOverlayBridge` (рабочее имя
   `ScriptsOverlayBridge`).
8. **Вкладка Scripts — три режима вместо двух:**
   - игры нет → пишем `scripts.cfg`, как сейчас;
   - связь есть (`LinkState == Connected`) → `SCRIPT_SET`, строка ждёт `SCRIPT_STATE`, через 5 с без ответа
     — откат и уведомление;
   - игра есть, связи нет (синхронизация выключена, плагин не подключился) → заблокировано, как сейчас.
   - Строка показывает статус из `SCRIPT_STATE`: упал (с ошибкой), приостановлен (с причиной).
9. **Script Dev и «Восстановить»:** после установки — `SCRIPT_RELOAD` затронутых файлов.
10. **Версия протокола `TW_OVL` 1 → 2** (`k_protocol_version` в `overlay_ipc.cxx`, `ExpectedProtocolVersion`
    в `OverlayHelper.cs`). Проект не выпущен, совместимость не держим (постоянное правило владельца). Хост
    требует точного совпадения, так что старая пара покажет «обновите плагин».

### 9.3 Решения владельца (01.10.2026)

1. **В хост — только изменения состояния**, никакого живого слежения (§5 п. 4). Статусы:
   - `off` — выключен;
   - `running` — включён и загрузился (в том числе пока ждёт загрузки игры: ожидание — покадровая вещь);
   - `failed` — включён, но упал при загрузке, с текстом ошибки;
   - `suspended` — приостановлен бюджетом ошибок или времени, с причиной;
   - `missing` — файла больше нет.

   Стоимость в мс и «ждёт загрузки» в хост не идут.
2. **Пересканирование — только когда оно нужно:** установили скрипт, удалили скрипт, восстановили
   поставку, пользователь явно попросил (кнопка). Не по каждому изменению папки: при копировании руками
   наблюдатель увидит файл недописанным.
3. **После сборки с установкой — `SCRIPT_RELOAD` автоматически**, в том числе на пересборке по сохранению с
   установкой. Скрипты выгружаются и обрабатывают ошибки без фейерверков. А тот, кто сидит во вкладке
   разработки посреди заезда, не играет, а пишет моды — скачки времени кадра его не волнуют.
4. **Длинное описание во вкладке Scripts оверлея** — сейчас обрезается по краю (`lua_ui.cxx`,
   `draw_clipped`). Варианты владельца:
   - (а) «…» вместо тупой обрезки и всплывающая подсказка с полным текстом — быстрее, плашки в пол-экрана
     некрасивы;
   - (б) клик по карточке скрипта (не по её элементам управления) открывает окно сбоку, как панель
     параметров неба (`skybox/sky_panel`), с макетом, похожим на описание в TweakerUI — красивее;
   - объединить оба — и красиво, и удобно, но сложнее.

   План: (а) входит в С5; (б) — следующим шагом после С5, если владелец подтвердит.

### 9.4 Протокол — коротко

Полностью — `overlay-scripts.md`.

| Операция | Направление | Смысл |
|---|---|---|
| `SCRIPT_SET <файл> <true\|false>` | хост → плагин | включить/выключить; `scripts.cfg` пишет плагин |
| `SCRIPT_RELOAD <файл>` | хост → плагин | перечитать с диска; незнакомый файл — сначала пересканировать; выключенный не запускается |
| `SCRIPT_RESCAN` | хост → плагин | подхватить новые и пропавшие файлы |
| `SCRIPT_STATE <файл> <true\|false> <статус> [сообщение]` | плагин → хост | одна строка на скрипт: при подключении и после пересканирования — по всем, затем при каждом изменении из любого источника |
| `SCRIPT_SYNCED <число>` | плагин → хост | конец полного списка: пересканирование закончено, список полон |

Имена на проводе — **имена файлов** в percent-кодировке, а не номера реестра: номер живёт один сеанс, а файл
— это идентичность скрипта и для хоста, и для `scripts.cfg`. Одна строка на скрипт держит сообщения
короткими независимо от §9.1; текст ошибки обрезается.

### 9.5 Потоки в плагине

- **Входящее:** `overlay_ipc` → модуль скриптовой грамматики (по образцу `qp_wire`; где ему жить — в
  `src/lua/` или `src/ipc/` — решить по зависимостям) → ящик → `lua_host::draw_frame` разбирает ящик до
  диспетча.
- **Исходящее:** `SCRIPT_STATE` шлётся с потока движка в момент изменения — так же, как `pending_actions`
  шлёт `NOTIFY_TWEAK` по клику. Это `SendMessageW` в окно `asbridge`, синхронный и межпроцессный, но
  по событию, а не каждый кадр. Правило рендер-потока (запрет системных вызовов) касается покадрового кода.
- **Изменение `suspended`** рождается в планировщике (`lua_sched`, бюджеты). Отправку оттуда не делать — там
  горячий путь. Планировщик только помечает «состояние скрипта изменилось», а `draw_frame` вне горячего пути
  отправляет помеченные.

### 9.7 Итоги С5a (02.10.2026): плагин, проверено офлайн, ждёт владельца

**Что сделано**

- **Реестр** (`src/lua/lua_registry`):

    текст;

**Отклонения от проекта и уточнения**

1. **`reload` больше ничего не пишет в `scripts.cfg`.** Раньше он шёл через `set_enabled(false)` +
   `set_enabled(true)`. Первый записывал «выкл.», второй при падении «вкл.» не возвращал. Итог: скрипт,
   упавший при перезагрузке, оказывался выключен в `scripts.cfg`, и следующая, исправленная, сборка его уже
   не запустит (перезагрузка выключенного только перечитывает шапку). Теперь перезагрузка — выгрузить и
   запустить без записи; упавший остаётся включённым и `failed`, как при старте игры. Кнопка Reload в оверлее
   зовёт ту же функцию и меняется в ту же сторону.

   **Уточнение после проверки владельцем (03.10.2026):** сборка с ошибкой до игры не доходит вовсе —
   `twllink` при ошибках не ставит, и в игре остаётся прежний рабочий файл; ругается только Script Dev (и IDE).
   Так что «упал при перезагрузке» — это не ошибка сборки, а скрипт, который собрался без ошибок, но упал
   при запуске (ошибка времени выполнения в теле, `@api` новее плагина). Правка остаётся нужной для этого
   случая и для кнопки Reload после правки файла руками.
2. **`failed` может прийти с `false`.** Неудачное включение переключателем (в оверлее или `SCRIPT_SET`)
   оставляет `enabled = false`: переключатель «отпрыгивает», `scripts.cfg` не трогается — это прежнее
   поведение оверлея. На проводе это `SCRIPT_STATE x false failed <ошибка>`: «просили включить, не вышло».
   Записано в `overlay-scripts.md`.
3. **Неявное пересканирование** при `SCRIPT_SET`/`SCRIPT_RELOAD` незнакомого или `missing` файла — не больше
   одного на пачку команд за кадр. Найденные при этом новые записи уходят хосту как изменения, без
   `SCRIPT_SYNCED`.
4. **VM не поднялась** (LuaJIT не стартовал) — ящик выбрасывается непрочитанным: переключать нечего. Хост
   увидит таймаут ожидания. Случай редкий, отдельного ответа не заводил.
5. **Без хоста** ничего не шлётся и не запоминается как отправленное; подключившийся хост получает полный
   список после рукопожатия.

  - Под описанием — строка статуса, только когда есть что сказать: «Failed: <ошибка>» красным,
