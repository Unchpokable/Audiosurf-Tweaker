# Протокол оверлея (`TW_OVL`)

## Что это и зачем

`TW_OVL` — протокол, по которому `TweakerUI` (хост) обменивается данными с `TweakerPlugin.dll` — модулем, инжектируемым в процесс игры (`QuestViewer.exe`) для внутриигрового оверлея (Skin Changer + Tweaker без alt-tab, см. Фазу 7 в `Docs/Internal/roadmap.md`).

Прямого канала хост ↔ плагин нет и не будет: единственный процесс, которому разрешено трогать Win32 (`WM_COPYDATA`, поиск окна игры), — `asbridge.exe` (см. `Docs/Internal/overview.md`, раздел «Почему так»). Поэтому `asbridge` не просто проксирует `ascommand`/`asconfig`/`asreport` игре, а расширен до **роутера** двух независимых потоков трафика: обычного игрового протокола (не меняется этим документом) и оверлейного (`TW_OVL`).

Три слоя, снизу вверх:

- **L1** — расширение текстового протокола `asbridge` (`CCOMMAND`/`SREPORT` по именованному пайпу) новыми типами сообщений `OVERLAY_*`.
- **L2** — конверт `TW_OVL <payload>` внутри `WM_COPYDATA`, которым `asbridge` и `TweakerPlugin` обмениваются напрямую через Win32.
- **L3** — сам мини-протокол оверлея: `<OP> [token1] [token2] ...`, который содержится внутри `<payload>` из L2.

Хост знает только про L1. Он ничего не знает про `WM_COPYDATA` и про то, что где-то в процессе игры сидит DLL — с его точки зрения это просто ещё один тип команд/репортов `asbridge`. `TweakerPlugin`, наоборот, ничего не знает про пайп — он видит только L2/L3.

## L1 — расширение протокола `asbridge`

Формат сообщений `asbridge` не меняется (`ЗАГОЛОВОК ТИП "деталь1" "деталь2" ...`, детали в двойных
кавычках, `\` и `"` внутри детали backslash-экранируются — см. `escape`/`quoted` в
`ASBridge/src/proto/message.cxx` и `AsBridgeProtocol.Escape` в
`AudiosurfInterface/Bridge/AsBridgeProtocol.cs`, обе стороны обязаны оставаться в синхроне).
Экранирование добавлено позже L1/L2/L3-дизайна ниже (реальный баг: неэкранированная кавычка внутри
детали ломала framing на приёмной стороне) — не влияет на сам протокол `TW_OVL`, `<payload>` как был
единым токеном, так и остаётся. Добавлены четыре новых `ТИП`:

| Направление | Заголовок | Тип | Смысл |
|---|---|---|---|
| хост → `asbridge` | `CCOMMAND` | `OVERLAY_SEND "<payload>"` | «Передай `<payload>` плагину как есть» |
| `asbridge` → хост | `SREPORT` | `OVERLAY_OK` | `OVERLAY_SEND` успешно доставлен в окно игры |
| `asbridge` → хост | `SREPORT` | `OVERLAY_FAILED "<reason>"` | Доставка не удалась (нет окна игры / `SendMessage` вернул 0) |
| `asbridge` → хост | `SREPORT` | `OVERLAY_FORWARD "<payload>"` | Плагин сам прислал `<payload>` — переслано хосту без изменений |

Симметрия с уже существующими `SEND`/`OK`/`FAILED`/`BROADCAST_FORWARD` намеренная — `OVERLAY_*` это ровно те же семантики, только для оверлейного трафика, чтобы не путать его с обычными игровыми `asreport`.

Реализация: `ASBridge/src/proto/message.hxx`/`.cxx` (enum `asbridge_msg_type`, парсинг/валидация), C#-зеркало — `AudiosurfInterface/Bridge/AsBridgeProtocol.cs` (`AsBridgeReportType`, `SerializeOverlaySend`). Публичный API для хоста — `AudiosurfInterface/AudiosurfHandle.cs`:

```csharp
audiosurfHandle.OverlayCommand("TWEAK_SET InvisibleRoad true global"); // отправить L3-payload
audiosurfHandle.OverlayMessageReceived += (_, payload) => { /* пришёл L3-payload от плагина */ };
```

`OverlayCommand` буферизует вызовы до подключения (та же логика, что у обычного `Command`) и переотправляет накопленное в `OnRegistered`.

## L2 — конверт `WM_COPYDATA`

И `asbridge`, и `TweakerPlugin` слушают `WM_COPYDATA` на своём собственном скрытом окне. Формат конверта одинаковый в обе стороны:

```
"TW_OVL " + <L3 payload>
```

(с завершающим `\0`, как того требует `COPYDATASTRUCT::cbData`). Префикс — `UPPER_SNAKE_CASE` для консистентности с остальными именами (`OVERLAY_SEND` и т.п.), с пробелом-разделителем, а не отдельным полем структуры — это ровно один `if` на префикс с обеих сторон, без изменения формата `COPYDATASTRUCT`.

Два независимых направления, разные окна-получатели:

- **Хост → игра.** `asbridge` получает `CCOMMAND OVERLAY_SEND "<payload>"` по пайпу, оборачивает `<payload>` в `TW_OVL `-конверт и шлёт `WM_COPYDATA` в уже известное окно игры (тот же кэшированный `HWND`, что используется для обычных `ascommand`). См. `ASBridge/src/service/service.cxx`, `handle_client_command`.
- **Игра (плагин) → asbridge.** `TweakerPlugin` оборачивает L3-payload в тот же конверт и шлёт `WM_COPYDATA` в окно `asbridge` (`g_bridge_hwnd` — как оно определяется, см. `HANDSHAKE_BEGIN` ниже). `asbridge` видит `TW_OVL `-префикс на входящем `WM_COPYDATA` в `process_wm_copydata` и рапортует его хосту как `SREPORT OVERLAY_FORWARD` — не заглядывая внутрь `<payload>`, транспорт полностью прозрачен для L3.

**Про `SendMessageW` с «узким» (`char*`) payload'ом:** это не баг. `WM_COPYDATA` — одно из немногих сообщений, для которых Windows не делает ANSI↔Unicode thunking полезной нагрузки (`COPYDATASTRUCT::lpData`/`cbData` передаются как непрозрачные байты независимо от того, `SendMessageA` или `SendMessageW` использован для доставки) — thunking трогает только сообщения, где текст лежит прямо в параметрах (`WM_SETTEXT` и подобные). Поэтому и `asbridge` (`send_ansi_copydata` в `service.cxx`), и плагин (`send_payload_to_bridge` в `overlay_ipc.cxx`) единообразно шлют узкий ANSI-текст через `SendMessageW` — это специально задокументированный в коде инвариант, трогать не нужно.

**Перехват на стороне плагина.** `TweakerPlugin` явно перехватывает `WM_COPYDATA` с `TW_OVL `-префиксом и не пускает его дальше в `WndProc` игры (возвращает `TRUE`, «сообщение обработано» — стандартная конвенция Win32 для `WM_COPYDATA`). Всё остальное (в первую очередь легаси `asreport`-широковещалка, которая тоже иногда бьётся `WM_COPYDATA` в то же окно) уходит в исходный `WndProc` без изменений — плагин не пытается фильтровать чужой трафик, только свой собственный префикс.

## L3 — сам протокол оверлея

Формат одной операции:

```
<OP> <token1> <token2> ...
```

Токены разделены одиночным пробелом, без кавычек (в отличие от L1 — там кавычки нужны на уровне пайпа, здесь `<payload>` — это уже один готовый токен для L1, кавычки ему не нужны). Строковые токены (имена скинов) — **percent-encoded UTF-8** (`%20` вместо пробела и т.п.), чтобы безопасно нести пробелы и спецсимволы без вложенного экранирования, которое было бы нужно при вложенных кавычках. Кодирование/декодирование — `percent_decode`/percent-encode на стороне отправителя в `TweakerPlugin/src/ipc/overlay_ipc.cxx`.

### Таблица операций

| OP | Направление | Токены | Смысл |
|---|---|---|---|
| `HANDSHAKE_BEGIN` | host → plugin | `<caption>` | `<caption>` — заголовок собственного окна `asbridge` (тот же, что уходит игре как `registerlistenerwindow`/`quickstartregisterwindow`). Плагин делает `FindWindowA(nullptr, caption)`, запоминает `HWND` как адрес для исходящих сообщений и отвечает `HANDSHAKE_ACK`. |
| `HANDSHAKE_ACK` | plugin → host | — | Ответ на `HANDSHAKE_BEGIN`: «адрес получен, канал в обе стороны открыт». |
| `HANDSHAKE_PING` | host → plugin | — | Задел на keepalive/переподключение. **v1: no-op**, плагин просто игнорирует. |
| `SKIN_LIST` | host → plugin | `<name1> <name2> ...` (percent-encoded, 0+ шт.) | Полный снимок каталога скинов — заменяет весь список у плагина, не патчит. |
| `TWEAK_SET` | host → plugin | `<TweakName> <true\|false\|1\|0> [global\|quick_player]` | Устанавливает effective-состояние одного твика и опционально его источник. Неизвестное имя твика — сообщение молча игнорируется. |
| `CURRENT_SKIN` | host → plugin | `<name>` (percent-encoded) | Какой скин сейчас применён. |
| `NOTIFY_TWEAK` | plugin → host | `<TweakName> <true\|false>` | Пользователь щёлкнул твик прямо в оверлее — просьба хосту применить это состояние. |
| `NOTIFY_SKIN` | plugin → host | `<name>` (percent-encoded) | Пользователь нажал «Apply» на выбранном скине в оверлее — просьба хосту установить его. |
| `QP_*` | обе стороны | см. `Docs/Internal/overlay-quickplayer.md` | Quick Player: каталог плейлистов, состав, очередь, транспорт, правки трека. |

**`QP_*` — отдельное семейство, описанное в `Docs/Internal/overlay-quickplayer.md`.** Оно живёт
поверх ровно этого же L1/L2 и ничего в них не меняет. Диспетчеризация обеих сторон устроена
одинаково: `overlay_ipc.cxx` проверяет префикс `QP_` и отдаёт payload целиком в
`tw::ui::qp::handle_op`, а `OverlayHelper` поднимает `QuickPlayerRequested` для всего, что
начинается с `QP_NOTIFY_`, и разбирает это `QuickPlayerOverlayBridge`. Ни транспортный слой, ни этот
документ грамматику Quick Player не знают — иначе оба выросли бы на дюжину операций.

**Percent-кодек — общий.** Раньше декодер лежал приватно в `ipc/overlay_ipc.cxx`, а энкодер —
приватно в `ui/pending_actions.cxx`; Quick Player стал бы третьей копией. Обе половины обязаны
совпадать байт в байт с `Uri.EscapeDataString`/`UnescapeDataString` на хосте, поэтому они вынесены в
`TweakerPlugin/src/ui/wire_text.hxx|.cxx`, а прежние копии удалены.

Нет операции «удалить один скин из списка» или «включить/выключить один твик без имени» — состояние либо целиком заменяется (`SKIN_LIST`, `CURRENT_SKIN`), либо адресуется по имени (`TWEAK_SET`), namespace для будущих операций открыт (`INSTALL_SKIN`, `APPLY_CONFIG` — см. «Чего пока нет»). Третий токен `TWEAK_SET` backward-compatible: старые плагины читают первые два токена и показывают правильное effective-значение без QP-маркера; отсутствие токена новый плагин трактует как `global`.

### Reverse-sync: `NOTIFY_TWEAK`/`NOTIFY_SKIN` и подтверждение без отдельного ACK

Оверлей отзывается на клик мгновенно (оптимистично — виджет сразу показывает новое состояние), но это состояние не подтверждено, пока хост его не применит. Специального ACK-опа для этого **нет и не нужно** — подтверждением служат уже существующие `TWEAK_SET`/`CURRENT_SKIN` (host → plugin). Твики пере-пушит `OverlayHelper`, подписанный на единый `GameConfigState.StateChanged`; скины — существующий путь `SkinChangerViewModel.OnCurrentInstalledSkinRawChanged`. Эхо поэтому одинаково приходит и после desktop-клика, и после входящего `NOTIFY_*`.

Логика на стороне плагина (`tw::ui::pending_actions`, `TweakerPlugin/src/ui/pending_actions.hxx/.cxx`):

1. Клик → виджет сразу показывает желаемое состояние (`pending_actions::request_tweak`/`request_skin`), плагин отправляет `NOTIFY_TWEAK`/`NOTIFY_SKIN` и запоминает запрос с дедлайном `now + 5s`.
2. Каждый кадр (`pending_actions::update`, не зависит от видимости меню) сверяет ожидающий запрос с последним снимком `overlay_state::cache`:
   - если снимок уже показывает желаемое значение — запрос считается подтверждённым, тихо снимается (без нотификации — виджет и так уже показывал нужное состояние);
   - если дедлайн истёк, а подтверждения не было — запрос снимается, и в notefeed летит уведомление о неудаче («Failed to enable/disable `<tweak>`» / «Failed to apply skin: `<name>`»).
3. Откат — не отдельная операция: пока запрос активен, отображение (меню/pins) берёт желаемое значение; как только запрос снят (по таймауту или по подтверждению), отображение просто возвращается к тому, что реально лежит в `overlay_state::cache` — если хост так и не применил изменение, там всё ещё старое значение.
4. Повторный клик по тому же твику/скину, пока предыдущий запрос ещё в подвесе, **заменяет** его (последний клик побеждает, дедлайн перезапускается), очередь не ведётся.

Установка скина — операция, реально распаковывающая файлы на хосте, а не мгновенный toggle, поэтому `NOTIFY_SKIN` не летит на каждый клик по элементу списка: выбор в списке лишь двигает локальную подсветку, а отправка происходит только по отдельной кнопке «Apply» в Skins-вкладке меню, которая блокируется на время ожидания подтверждения — иначе повторные клики могли бы поставить хосту в очередь несколько установок подряд.

`asbridge` не требует никаких изменений для этого направления — маршрут `plugin → asbridge (WM_COPYDATA) → SREPORT OVERLAY_FORWARD → host` уже полностью прозрачен для L3 (см. L2 выше, `asbridge` не заглядывает внутрь `<payload>`), `NOTIFY_TWEAK`/`NOTIFY_SKIN` идут по нему как есть.

**Хостовая сторона (C#).** `OverlayHelper.OnOverlayMessageReceived` разбирает `NOTIFY_TWEAK`/`NOTIFY_SKIN` и поднимает события `TweakRequested`/`SkinRequested` — сам `OverlayHelper` не знает про `TweakerViewModel`/`SkinChangerViewModel` (не переворачивает направление зависимости, см. `OverlayReady`), они сами подписываются в конструкторе. Скины по-прежнему проходят через `InstallSkin`. Твик проходит через глобальное свойство `TweakerViewModel`, после чего `GameConfigState.SetAndClearOverrides` закрепляет выбранное effective-значение и отменяет временный Quick Player override, даже если setter свойства был no-op. Подтверждающий `TWEAK_SET` теперь централизованно отправляет подписанный на `GameConfigState.StateChanged` `OverlayHelper`.

### Временные твики Quick Player

`GameConfigState` хранит отдельно глобальный baseline и effective-значение с LIFO-overrides. `PlaybackController` помечает свои overrides источником `QuickPlayer`; `OverlayHelper` конвертирует raw `asconfig` через `GameTweakCatalog` в human-state и шлёт `TWEAK_SET ... quick_player`. Плагин показывает такой active pin как `QP: <name>` отдельным accent-цветом и добавляет QP-маркер к строке меню.

Toggle в меню показывает именно effective-значение. Поэтому клик по нему означает «отменить QP override и сделать новое отображаемое значение глобальным». Desktop Tweaker, напротив, редактирует глобальный baseline: совпавшее с temporary effective значение поглощает override, противоположное запоминается и вступает в силу после окончания песни.

Из-за этого расхождения вкладка Tweaker в десктопном UI маркирует ровно то же состояние своим способом: `TweakerViewModel` подписан на тот же `GameConfigState.StateChanged` и держит семь `*OverriddenByQuickPlayer`-флагов, по которым в строке твика появляется бейдж `QP` (`Border.TWQuickPlayerBadge` в `TweakerStyles.axaml`) с тултипом, объясняющим обе половины правила выше. Акцент бейджа намеренно тот же, что у QP-пинов оверлея (`theme::accent_secondary`) — две поверхности должны читаться как одна конвенция. Переключатель при этом остаётся показывать global, а не effective: он его и редактирует.

### Имена твиков на проводе

Семь твиков — ровно те, что показывает `TweakerUI/ViewModels/TweakerViewModel.cs` (четыре «классических» + три Freeride). Имена на проводе — `PascalCase`, отдельные от строк `asconfig` (`GameProtocol.cs`) намеренно: L3 говорит на языке пользовательского смысла твика («что видит человек в UI»), а не на языке конкретного игрового конфиг-ключа — так плагин не привязан к деталям обратной стороны протокола игры.

| Wire-имя (`TW_OVL`) | `tweak_id` | Соответствующий `asconfig`-ключ игры | Инверсия? |
|---|---|---|---|
| `InvisibleRoad` | `invisible_road` | `roadvisible` | да (`true` в TW_OVL = `roadvisible false`) |
| `HiddenSongTitle` | `hidden_song_title` | `showsongname` | да |
| `SidewinderCamera` | `sidewinder_camera` | `sidewinder` | нет |
| `BankingCamera` | `banking_camera` | `usebankingcamera` | нет |
| `FreerideNoBlocks` | `freeride_no_blocks` | `freerideblocks` | да |
| `FreerideBlocksCaterpillars` | `freeride_blocks_caterpillars` | `freeridecaterpillars` | нет |
| `FreerideAutoAdvanceDisable` | `freeride_auto_advance_disable` | `freerideautoadvance` | да |

Столбец «инверсия» — это существующая логика на стороне `TweakerViewModel` (см. `On*TweakActiveChanged` в `TweakerUI/ViewModels/TweakerViewModel.cs`), а не что-то, что видит `TW_OVL`: значение, которое едет по проводу, — это уже человеческое «включён/выключен», в том виде, в котором его показывает `ModOptionViewModel`. Приведено здесь только чтобы не потерять соответствие при подключении хостовой стороны (Фаза 7a, ещё не сделана — см. ниже).

Маппинг wire-имя → `tweak_id` и обратная индексация в фиксированный массив — `TweakerPlugin/src/ui/overlay_state.cxx` (`resolve_tweak_id`/`tweak_index`). Список твиков заранее известен и конечен, поэтому строки конвертируются в `enum class tweak_id` сразу при разборе сообщения, а не хранятся как `std::string` ключи — линейная проверка 7 констант в разы быстрее хеширования строки под `std::unordered_map`.

### Лимиты и парсинг токенов

Две разные стратегии разбора на стороне плагина (`TweakerPlugin/src/ipc/overlay_ipc.cxx`):

- **Операции с фиксированной арностью** (`HANDSHAKE_BEGIN`, `TWEAK_SET`, `CURRENT_SKIN`) — разбираются через `split_fixed_tokens` в `std::array<std::string_view, 3>` без аллокаций. `3` — не случайное число: это число аргументов самой «широкой» операции, `TWEAK_SET <name> <bool> <source>`.
- **`SKIN_LIST`** — число токенов зависит от размера каталога скинов на хосте и заранее не известно, поэтому разбирается отдельным неограниченным итератором (`for_each_token`), пишущим прямо в `std::vector` результата — без промежуточного фиксированного массива и без риска молча обрезать список скинов, если их окажется больше какого-то захардкоженного лимита.

## Многопоточность

`TW_OVL`-сообщения разбираются **синхронно, в момент получения `WM_COPYDATA`** — то есть на том потоке, на котором Windows решит доставить сообщение окну игры (см. `TweakerPlugin/src/ipc/overlay_ipc.cxx: handle_copydata`). Очереди на приём/отправку не используется — разбор строки на токены, percent-decode и запись в состояние — это микросекунды и происходит редко (handshake один раз, смена твика — по клику пользователя, `SKIN_LIST`/`CURRENT_SKIN` — на подключение/установку скина), поэтому это не hot-path в терминах правил проекта (`EndScene`/`CallChannel`/что угодно, вызываемое каждый кадр — см. `TweakerPlugin/.cursor/rules/main-rules.mdc`).

Разобранное состояние живёт в `tw::ui::overlay_state` (`TweakerPlugin/src/ui/overlay_state.hxx`) — это данные UI, а не транспорта, поэтому они физически отдельны от `ipc/`. Синхронизация с рендер-потоком — не очередь и не полноценный воркер-поток, а простая схема «один писатель (IPC-поток), один читатель раз в кадр (рендер)»:

- Писатель (`set_tweak`/`set_skin_list`/`set_current_skin`) берёт обычный блокирующий `std::lock_guard` — критическая секция крошечная, ждать там нечего.
- Читатель (`refresh(cache&)`, вызывается раз в кадр из `ui_main.cxx: draw_frame`) берёт **неблокирующий** `try_lock` — если писатель как раз занят, читатель просто оставляет прошлый кадр как есть и не ждёт ни цикла. Рендер-поток никогда не может застопориться из-за IPC.
- Счётчик поколений (`g_generation`) избавляет от копирования списка скинов на каждый кадр «просто на всякий случай» — копия происходит только если поколение реально изменилось с прошлого успешного `refresh`, то есть почти всегда `refresh` — это `try_lock` + сравнение `uint32_t`, без единой аллокации.

Единый хук `WndProc` игры (`TweakerPlugin/src/framework/wndproc_hub.hxx`) — общая точка подписки для
всех, кому нужны оконные сообщения: IPC на `WM_COPYDATA`, D3D9-слой на `WM_ACTIVATEAPP` (минимизация
при потере фокуса, только для fullscreen-устройств), и меню/ImGui на клавиатурный ввод — а не
что-то приватное для IPC-модуля. Подписки регистрируются один раз при инициализации; сам хук
устанавливается/снимается синхронно с жизнью D3D9-устройства (`bind_device`/`unbind_device` в
`d3d9_hooks.cxx`), а не опросом раз в кадр. `WM_ACTIVATEAPP`-подписка регистрируется **до**
`DetourAttach`, не после — иначе рендер-поток мог успеть дойти до `hub_wndproc` и начать итерацию
по вектору подписчиков, пока `subscribe()` ещё пушил в него (гонка, поймана на реальной игре).

**Открытие меню оверлея и захват ввода игрой.** Хоткей открытия меню (Insert) — не
`GetAsyncKeyState`-поллинг, а подписка на `WM_KEYDOWN`/`WM_KEYUP` через `wndproc_hub`
(auto-repeat подавляется через бит 30 `lParam`, оба edge проглатываются, чтобы игра не увидела
непарный key-up). Пока меню закрыто, `ImGui_ImplWin32_WndProcHandler` **не получает** оконные
сообщения — он вызывает `SetCapture`/`ReleaseCapture`/`TrackMouseEvent`, которые иначе отбирали
мышь у игры; сквозь гейт всегда проходят только focus/IME/destroy-сообщения. Тот же гейт
(`imgui_backend::attach_input_gate`, завязан на `menu::is_visible`) сбрасывает ImGui-состояние
клавиш/мыши и снимает capture на обеих границах открытия/закрытия. Временные `IDirectInput8`/
`SysMouse`-объекты, которые дёргает `dinput8`-хук на определение состояния ввода, теперь **не
освобождаются** сразу — их `Release` возмущал per-process состояние `dinput8`, ловилось только на
реальной игре.

**Device lifecycle.** Хук `IDirect3DDevice9::Release` (пробовавший ловить смену устройства по
`refcount == 1`) убран: на реальной игре Quest3D крутит refcount тысячами раз за кадр (живой счётчик
> 3000), ветка `refs_before == 1` не срабатывала никогда — единственный реалистичный эффект пробника
был ложный `unbind_device()` в момент перехода в fullscreen. Смена устройства теперь замечается там,
где она реально видна: `bind_device()` отвязывает предыдущее устройство перед принятием нового (это
же чинит `Reset()`, меняющий focus-окно без смены указателя устройства — раньше `imgui_backend::
initialize()` рано выходил на неизменившемся указателе и продолжал целиться в старое окно). Создание
DX9 Dummy-устройства для bootstrap имеет fallback на `NULLREF`-device, если обычный создать не удалось.

## Защита от повторного инжекта

Вторая копия `TweakerPlugin.dll` в одном процессе игры — это второй набор Detours на
`EndScene`/`CallChannel` и вторая подписка на `WndProc`, то есть краш игры, а не деградация оверлея.
Поэтому инжект — **последнее средство**: к нему приходят, только когда на канале никто не отозвался и
при этом ничего не обнаружено в процессе.

### Сторона плагина: `claim_single_instance`

`TweakerPlugin/src/plugin/load.cxx`, самое первое действие в `load_thread` (после инициализации
логов и **до** любого хука): `CreateMutexW(nullptr, FALSE, L"Local\\AudiosurfTweaker.Overlay.<pid>")`.
`ERROR_ALREADY_EXISTS` — значит копия уже живёт в этом процессе, и текущая просто возвращается из
`load_thread`, оставаясь замапленной, но полностью инертной: ни хуков, ни потоков, ни состояния.

Имя мьютекса намеренно **не содержит ни версии, ни пути**: смысл в том, чтобы более новый хост опознал
более старый (и, возможно, переименованный на диске) плагин. Хендл никогда не освобождается — он умирает
вместе с процессом игры, что и есть охраняемое время жизни. `FreeLibraryAndExitThread` для выгрузки
лишней копии сознательно не используется: инертная замапленная DLL безвредна, а выгрузка себя из потока,
которого ждёт инжектор, — лишний класс отказов ради косметики.

### Сторона хоста: `OverlayHelper.EnsureOverlayInjectedAsync`

Три сигнала присутствия, от дешёвого к дорогому (`DetectLoadedPlugin`):

| Сигнал | Что ловит |
|---|---|
| `OpenMutex(Local\AudiosurfTweaker.Overlay.<gamePid>)` | Любой плагин актуальной сборки, **включая переименованный**. `ERROR_ACCESS_DENIED` (в отличие от «объект не найден») трактуется как «присутствует» — объект есть, просто недоступен; считать это отсутствием значило бы заинжектить вторую копию поверх живой. |
| Модуль по точному пути | Свой плагин из своей папки — быстрый happy path. |
| Модуль по basename в любом пути | Копия из другой инсталляции или из `Plugins`-папки старого твикера. |

Дальше:

1. **Обнаружен** → `HANDSHAKE_BEGIN` (таймаут 5с). ACK — усыновляем, инжекта нет: `HANDSHAKE_BEGIN`
   заодно и есть механизм усыновления, он заставляет плагин заново отрезолвить окно моста по caption
   (`FindWindowA`, см. таблицу опов) и тем самым перенацеливает плагин, оставшийся от прошлой сессии
   твикера, на текущий `asbridge`.
2. **Обнаружен, но не ответил** → `AudiosurfHandle.SuspendService`, см. ниже.
3. **Не обнаружен** → короткая проба тем же `HANDSHAKE_BEGIN` (1.5с). Детект умеет доказать присутствие,
   но не отсутствие: плагин, собранный до появления мьютекса **и** переименованный, не оставляет следов,
   видимых хосту. Одна проба против «чистого» процесса — это разница между усыновлением такого плагина и
   постановкой второго набора хуков поверх него. Ответил — усыновляем; молчит — инжектим и делаем полный
   handshake.

Остаточный риск, сознательно не закрытый: плагин старой сборки (без мьютекса) **и** переименованный
**и** мёртвый не опознаётся ничем — будет заинжектена вторая копия. Закрывается только чтением PE-таблицы
экспортов DLL с диска по пути модуля; не делается, пока не появится реальный случай.

### Мёртвый плагин → остановка всей службы

Плагин, который доказуемо загружен, но не отвечает на handshake, — это живые хуки внутри игры, до которых
нет способа достучаться. Под подозрением при этом не только оверлей: плагин сидит на рендер-цикле,
`WndProc` и вводе игры, — поэтому `AudiosurfInterface` останавливается целиком
(`AudiosurfHandle.SuspendService`), а не просто отключает оверлей. Технически `ascommand`-трафик (скины,
твики) продолжил бы работать — плагин глотает только `TW_OVL`-префикс, — но процесс игры в таком
состоянии считается непригодным, и честный ход здесь один: перестать с ним разговаривать.

`SuspendService` убивает мост, чистит очереди команд (они адресованы сессии игры, которую сейчас
перезапустят), переводит состояние в `ASHandleState.Suspended` и поднимает `ServiceSuspended` с текстом
для пользователя. Само по себе это состояние не восстанавливается — моста, который заметил бы перезапуск
игры, больше нет. Выход один: пользователь перезапускает Audiosurf и жмёт Reset рядом со статусом
подключения (`ReinitializeWndProcMessageService`, который для выхода из suspend передаёт мосту
`suppressAutoRegister: false` — у нового моста нет за спиной неотвеченной попытки регистрации, а игра
только что запущена, что и есть случай `quickstartregisterwindow`).

## Пример: полный цикл подключения и синхронизации твика

1. Игра запущена, `asbridge` находит её окно (как и раньше, для обычного `ascommand`-протокола).
2. Хост (`TweakerUI/Core/OverlayHelper.cs`) видит, что `AudiosurfHandle` подключился, проходит
   inject guard (см. «Защита от повторного инжекта» выше — в чистом процессе это проба на 1.5с и затем
   инжект `TweakerPlugin.dll` через `InjectHelper.exe`) и шлёт
   `audiosurfHandle.OverlayCommand($"HANDSHAKE_BEGIN {AudiosurfHandle.Instance.ListenerWindowCaption}")`
   — **не** `asbridge` сам по себе: хендшейк идёт по уже готовому generic-каналу `OVERLAY_SEND`
   (тот же путь, что и `TWEAK_SET` в шаге 6 ниже), отдельного кода в `asbridge` для инициации не
   понадобилось. `OverlayHelper` ждёт `HANDSHAKE_ACK` с таймаутом 5с (`HandshakeTimeout`).
3. `asbridge` получает `CCOMMAND OVERLAY_SEND "HANDSHAKE_BEGIN <caption>"` по пайпу, оборачивает
   в `TW_OVL `-конверт, шлёт `WM_COPYDATA` в окно игры.
4. `TweakerPlugin` перехватывает это в `handle_copydata`, резолвит `FindWindowA` → `g_bridge_hwnd`,
   шлёт назад `TW_OVL HANDSHAKE_ACK`.
5. `asbridge` видит входящий `TW_OVL`-`WM_COPYDATA` на своём окне → `SREPORT OVERLAY_FORWARD "HANDSHAKE_ACK"` хосту.
6. Хост получает `OverlayMessageReceived("HANDSHAKE_ACK")`, резолвит ожидающий `TaskCompletionSource`,
   `OverlayHelper` пушит снимок твиков из `GameConfigState`, а `OverlayReady` вызывает остальных
   подписчиков (`SkinChangerViewModel`) для снапшота скина/списка скинов — канал живой.
7. Пользователь кликает твик в `TweakerUI` → `GameConfigState` меняет effective state, и его подписчик вызывает `audiosurfHandle.OverlayCommand("TWEAK_SET InvisibleRoad true global")`.
8. `AsBridgeConnection.SendOverlay` → пайп → `asbridge` получает `CCOMMAND OVERLAY_SEND "TWEAK_SET InvisibleRoad true global"`.
9. `asbridge` оборачивает `TWEAK_SET InvisibleRoad true global` в `TW_OVL `-конверт, шлёт в окно игры, рапортует хосту `OVERLAY_OK`/`OVERLAY_FAILED` по результату `SendMessage`.
10. `TweakerPlugin` получает `WM_COPYDATA`, видит `TW_OVL `, разбирает `TWEAK_SET InvisibleRoad true global` синхронно в `handle_copydata`, зовёт `overlay_state::set_tweak(tweak_id::invisible_road, true, false)`.
11. На следующем кадре рендер-поток вызывает `overlay_state::refresh(g_overlay_cache)`, видит новое поколение, копирует состояние в свой кэш; ImGui-панель (menu/pins, Фаза 7c) отрисовывает твик как включённый из `g_overlay_cache`, ни разу не тронув `overlay_state` напрямую.

Весь цикл реализован end-to-end и проверен вручную на реальной запущенной игре (не только компиляция/юнит-тесты) — по ходу проверки был найден и исправлен ряд гонок и багов ввода, см. «Известные фиксы после первой реализации» в конце документа.

## Текущий статус

Весь описанный выше цикл (инжект → handshake → SKIN_LIST/CURRENT_SKIN/TWEAK_SET снапшот →
reverse-sync `NOTIFY_TWEAK`/`NOTIFY_SKIN`) реализован end-to-end и **проверен вручную на реальной
запущенной игре**, а не только собран/юнит-протестирован — по ходу этой проверки нашлись и были
исправлены реальные гонки/баги (см. «Многопоточность» выше и коммиты `4bf1112`…`70c1e32`). Handshake
инициируется хостом (`OverlayHelper.BeginHandshakeAsync`), а не `asbridge` — см. «Пример: полный цикл»
выше; более ранняя версия этого документа планировала инициацию со стороны `asbridge`, но
generic-канала `OVERLAY_SEND` хватило и без отдельного кода там.

ImGui-панели (menu/notefeed/pins/watermark, см. `Docs/Internal/tweaker-plugin-widgets.md`) подключены
и рисуют `overlay_state::cache` каждый кадр.

## Чего пока нет (сознательно вне текущего объёма)

- Операции за пределами reverse-sync твиков/скинов (`INSTALL_SKIN` как отдельный от `NOTIFY_SKIN`
  смысл, `APPLY_CONFIG`) по-прежнему не определены — установка скина остаётся кнопкой «Apply» в
  Skins-вкладке меню, не индивидуальным togglе на элементе списка.
- **`SkinChangerViewModel.InstallSkin` может показать интерактивный диалог подтверждения** (`AskForAction`, при небезопасном стейте текстур), пока ждёт ответа пользователя — если это займёт больше 5с, `pending_actions` на стороне плагина успеет решить, что запрос не подтверждён, и показать notefeed-уведомление о неудаче, даже если установка в итоге пройдёт. Не исправлено сознательно — редкий edge case, не блокирующий обычный сценарий.
- ~~Quick Player (play/next/prev) в оверлее~~ — **сделан отдельным заходом**, см.
  `Docs/Internal/overlay-quickplayer.md` (протокол `QP_*`, вкладка Player, reverse-sync правок
  трека). В этом документе он намеренно описан только ссылкой: транспортные слои L1/L2 он не
  трогает, а его собственная грамматика живёт в своём файле.
